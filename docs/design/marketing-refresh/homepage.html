Design notes

For the implementing agent. Each note: the claim, why it holds, and what it binds to. The information architecture is carried forward from docs/design/web-reposition/homepage-marketing.html and is not up for re-litigation here — what changed is the palette (dark Velvet Send) and the execution quality. Notes tagged never shipped are places where that earlier wireframe described something the live page does not do today; those are the gap this refresh closes.

1
The homepage header is transparent and floats over the hero — every other page gets the bar. HIDDEN_HEADER_PAGES = ['/'] in marketing-header.tsx already does this, and the mockup has to show it or the hero glow reads wrong: no background, no blur, no hairline, absolute over the radial. The nav links are the four the header ships (/gyms, /playlists, /about, /help) plus the sign-in entry and the app hand-off. There is deliberately no /boards link — that route does not exist and a link to it would be a site-wide 404. Binds: packages/web/app/components/site-chrome/marketing-header.tsx; packages/web/e2e/site-chrome.spec.ts asserts the marketing-header testid on /, one nav a per those four hrefs, a visible a[href="/auth/login"], a boardsesh.com app link, and zero a[href^="/boards"].
2
The h1 is the biggest thing on the page — one of them, and it says what Boardsesh is. never shipped The earlier wireframe drew a 38px marketing h1; what shipped is a 130px brand PNG above Typography variant="h5" component="h1", i.e. an h1 rendered at h5 size under an image. Semantically correct, visually a caption. This mockup restores the type scale (60px desktop, 34px at 390px) and drops the oversized mark — the wordmark in the floating header carries the brand. Exactly one h1 on the page, server-rendered, with real copy around it; no indexable spinner-only render. Binds: packages/web/app/__tests__/home-page-content.test.tsx → "homepage must render exactly one <h1>" with non-empty text; scripts/production-smoke.ts reads the real SSR body for /. Copy is marketing:home.hero.title / .subtitle, landed in all four locales in the same commit. Open: final h1 wording must survive the three glossaries — es "plafón" (never "tabla"), fr "enchaîné / croix" (never "envoyer"), de "Getoppt / Board beleuchten" (never "senden").
3
Two store CTAs side by side, and the amber spark is spent here. The hero is the measured install driver, so both stores stay above the fold rather than one platform-sniffed button. The App Store button carries the warm glow (0 8px 26px rgba(255,138,61,.38), the dark-palette sibling of HERO_CTA_SX's boxShadow); Google Play is the quiet --surface-2 variant so the pair does not read as two primaries. Amber is fill-only with #16111F ink and at most once per page — this glow is that one use, and nothing below the hero may take it. Binds: IOS_APP_STORE_URL / ANDROID_PLAY_STORE_URL in app/lib/store-urls.ts; both keep firing App Install Click with placement: 'hero' via buildAppInstallClickProperties — the test pins {platform, source, placement: 'hero', mode} exactly. Open: the live hero platform-sniffs to a single button (resolveHeroInstall) and has a third "update the app" mode for retired Capacitor stragglers. Showing both stores means deciding whether that update path becomes a hero variant or moves into a dismissible strip.
4
"Start climbing on the web" is a tertiary text link, not a second pill. Carried forward from the earlier wireframe unchanged: the web hand-off stays reachable but installs are what the hero is for. The live page has this backwards — StartClimbingButton is the hero's first and largest CTA, with the install button second and identically styled, so the two compete. Binds: packages/web/app/components/start-climbing-button.tsx (SSO hand-off to the Expo-web app when signed in). The same control also lives in the header and the footer. Open: install-first vs web-first is still unsettled — the web hand-off click is uninstrumented, so there is no number to decide on. Instrument it in the PR that moves it.
5
"Find a board near you" is a real search block, not a link card. never shipped The earlier wireframe specified a search field, a location button, facet chips and a row of gym result cards. What shipped is one OnboardingCard reading "find a gym" that links to /gyms. This restores the block: a plain GET form to /gyms, no drawer, no client JS needed to submit, SSR-friendly. Text search leads because a large minority of gym rows have no coordinates at all. Binds: searchGyms (free-text + PostGIS ST_DWithin, board-type facets, offset paging). Submits ?q= (+ near when geolocation is granted). The existing home.cards.gymTitle card and its /gyms href are asserted by the unit test — keep a crawlable /gyms anchor in this block so that assertion survives the card's removal. Open: which gyms populate the four teasers with no geolocation. Any default must not systematically bury sparse or unclaimed listings — university walls and garages are the long tail this directory exists for.
6
"Use my location" is optional and the fallback is visible before the prompt. Geolocation is an outlined secondary, never the only path: denial, an unsupported browser, or a desktop with no fix all land on typing a city. The hint line under the row says so in plain words so nobody has to trigger a permission dialog to find out. Binds: the existing useGeolocation hook + searchGyms(lat, lng, radiusKm); the city-geocode fallback pattern already in map-location-picker.tsx.
7
Facet chips point at the literal routes, never at query strings. /gyms/kilter is a page with its own copy and its own canonical; /gyms?board=kilter would self-canonicalise away and waste the crawl. The footer already makes this mistake impossible to repeat — its comment spells out why — and the chips here must follow it. Counts come from the live board mix, ordered by count, and are dynamic rather than hardcoded. Binds: packages/web/app/gyms/page.tsx (per-board routes and canonicals); site-footer.tsx link group gyms. Chip counts from the gym/board join. Open: the directory carries more board types than the four shown (Grasshopper, Decoy, So iLL, Touchstone). Four chips plus "All" fits 390px; the rest need a "More" affordance or horizontal scroll.
8
The sparse card is the default, and a gym with no pin ranks exactly the same. Carried forward verbatim from the earlier wireframe's note 6 and the gyms-directory design. Card renders only schema-real fields: name, claim state, boards with type and angle, and — only when present — an address and a distance. No photo, no logo, no description, no hours: those are empty for all but a handful of rows and the long tail will never fill them. A missing pin gets a muted line and a claim prompt that doubles as the fix, never a hidden or down-ranked listing. Binds: gyms.name, gyms.address, gyms.latitude/longitude, user_boards.board_type + angle, claim state from owner_id. Card title is a real anchor to /gym/<slug> — merged slugs 308-redirect and never 404, because printed QR codes exist in the field.
9
Popular board setups are the page's SEO spine — every card is a real anchor. This is the one block the live page genuinely delivers (PopularBoardRail), and the refresh only re-frames it: a four-up grid with the board thumbnail, human-readable config and a send count, instead of a rail squeezed beside a 420px column. The mockup prints the href under each card so the implementer can see the URL shape is unchanged. Cards must stay <a href> — never router.push, never a click handler on a div. Binds: getPopularBoardConfigs() (already SSR-fetched in app/page.tsx) rendered through constructClimbListWithSlugs(...); home-page-content.test.tsx → "renders one crawlable board link per SSR config", matching /^\/(kilter|tension|moonboard)\/.+\/list$/, and zero links with an empty config array without crashing.
10
Recent beta stays a rail, and it stays the LCP. Five 9:16 thumbnails, community signal directly under the fold. app/page.tsx already picks the LCP hint — a preconnect to the backend origin plus a single high-priority preload for the first beta thumbnail, falling back to the first board thumbnail when the rail is empty — so the rail must keep its position and its first-image identity or the hint points at nothing the browser paints. Binds: getRecentBetaLinks(), selectHomeLcpHints() in app/lib/popular-lcp-preload.ts, home-recent-beta-section.tsx. Thumbnails are cross-origin credentialed requests, hence the bare preconnect with no crossOrigin. Open: an empty rail (new install, no recent uploads) collapses the section entirely and moves the LCP to the board grid. Confirm the section heading disappears with it rather than leaving an empty "Recent beta".
11
The feature strip is three-up at 1440 — this is the single biggest thing the live page gets wrong. never shipped The earlier wireframe drew a three-column feature grid; the live page wraps its whole onboarding stack in maxWidth: 420, mx: 'auto', so a 1440px desktop shows a narrow ribbon of cards down the middle with empty violet on both sides. Same content, three columns, each with a portrait app screenshot, and the column only collapses below 760px. Copy keeps the existing voice ("Take turns without the awkward 'who's next?'") and describes what the climber gets. Binds: packages/web/app/home-page-content.tsx — the single 550-line 'use client' file; this block is the reason to split it into a app/(marketing)/home/sections/ directory with server components for everything that does not need the browser.
12
Three colour roles. The Material purples are gone. The live file hardcodes #9C27B0, #7B1FA2 and #6A1B9A across an accentSurface map of six accent variants, which reads as six unexplained category colours and none of them are Velvet tokens. This page uses exactly three roles and says so out loud: brand violet (--primary foreground for text/links/icons, --primary-fill for button fills — never collapsed into one token), amber spark (fill-only, dark #16111F ink, used once, on the hero CTA glow), and info (violet-slate #A5ABD6, the low-key chip role — unclaimed badges, the logbook icon chip).
brand violet · foreground brand violet · fill amber spark · fill-only, once info · violet-slate
Binds: darkTokens in packages/web/app/theme/theme-config.ts (info #A5ABD6, infoTint) and @boardsesh/velvet-tokens. No hardcoded hex in components — colours come from tokens, per the repo rule.
13
Every image on this page is a placeholder, and none of them may be generated. The only real captures that exist today are eight Play Store screenshots at app-stores/google/screenshots/pixel-2/ — Pixel 2 resolution, too small for an 880px hero shot and framed for a store listing rather than a web page. Real board and gym photography is being sourced and does not exist yet. Until it does, the hero shot and the feature screenshots need fresh captures from the screenshot pipeline, and the gym cards carry no imagery at all by design (note 8). Binds: vp run mobile:screenshots (iOS, locale-matched en/es/fr/de) and vp run mobile:android-shots; repo rule — no AI-generated images, real photos or diagrams only. Open: do the feature screenshots reuse App Store captures (already locale-matched) or get web-specific ones at desktop resolution? Reuse is cheaper but the store crops assume a phone viewport.
14
The footer is a fixed link contract, not a design surface. Three groups — Find a gym, Explore, Small print — exactly as site-footer.tsx ships them, plus the brand blurb and the "Start climbing" capsule. Restyling is fine; dropping or renaming an href is not, because /gyms is noindex, follow and out of the sitemap until the duplicate-gym queue drains, which makes these anchors the only crawl path into the directory. Binds: packages/web/e2e/site-chrome.spec.ts asserts the site-footer testid and exactly one anchor each for /, /about, /support, /help, /docs, /playlists, /aurora-migration, /legal, /privacy, /gyms, /gyms/kilter, /gyms/tension, /gyms/moonboard.
15
The trademark caption and the language switcher both live in the footer bottom bar. The switcher is the only way to change language anywhere on www — the user drawer that used to host it is gone — so it cannot be quietly dropped in a restyle. The trademark line describes compatibility and explicitly disclaims affiliation; capitalisation is MoonBoard, Kilter, Tension, and the wording never implies endorsement by Aurora Climbing, Moon Climbing or any manufacturer. Binds: CompactLanguageSwitcher in site-footer.tsx; common:footer.trademarkNote; e2e "keeps a locale switcher" asserts a visible button[name=/language/i] inside the footer. Locales: en-US root, plus /es, /fr, /de.
16
390px is a first-class width, and the document ends at the footer. Every grid collapses by CSS media query only — no JS breakpoint detection, no Grid.useBreakpoint(): gyms and boards go 4 → 2 → 1, beta 5 → 3 → 1, features 3 → 1 at 760px, footer 4 → 2 → 1. The hero drops to 34px and the store buttons go full-width and stack. Nothing below the footer may reserve space — the old chrome's --bottom-bar-height gutter is gone and must stay gone. Binds: packages/web/e2e/site-chrome.spec.ts → "ends at the footer on the home page" (<24px below the footer's bottom edge) and "defines no --bottom-bar-height custom property". Repo rule: CSS media queries for responsive design.
17
A support block, last thing before the footer. /support is currently reachable only from one footer link in the "Explore" group, which is where links go to be ignored. Putting the ask at the bottom of the homepage catches people who have just read what the app does and are already convinced — and it costs the hero nothing, because it is below every acquisition CTA. The paired "Not got money spare?" column is the same list /support carries, so the page never reads as money-only. Binds: app/support/page.tsx; site-footer.tsx link group explore; copy must clear the perks regex in donation-disclosure.test.ts and must not name a figure. Open: the "Chip in" label is deliberately not "Donate" — worth checking against whatever the App Store review guidelines allow on a page the mobile app can link to, since the same wording travels.
