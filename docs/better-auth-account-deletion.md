# Current-store account deletion

This is [PR #7307](https://github.com/boardsesh/boardsesh/pull/7307), an implementation slice of [BA-03 #6977](https://github.com/boardsesh/boardsesh/issues/6977) in [epic #6975](https://github.com/boardsesh/boardsesh/issues/6975). It adds independently selected security bookkeeping to the existing backend GraphQL account-deletion transaction. It does not activate an authority, migrate identities, change production privileges or delete a real account.

## Caller and authority boundary

The existing Expo flow is `DeleteAccountScreen` → `useDeleteAccount` → the shared `DELETE_ACCOUNT` GraphQL operation → `userMutations.deleteAccount`. Its input, Boolean response, confirmation UI and local sign-out behavior stay the same. No new web-to-backend credential command is needed: the mutation already belongs to the backend. The surviving web profile endpoint is read-only, and the profile mutation accepts cosmetic display-name/avatar fields rather than email changes.

`CURRENT_STORE_ACCOUNT_DELETION_MODE` defaults independently to `legacy`. The `reserved-staging` mode requires the exact configured current-store projection and writer epoch. Missing or malformed configuration must fail without falling back to legacy deletion. A normal legacy request must not read a projection or require current-store authority secrets.

The existing authenticated GraphQL principal supplies a server-established user ID. It does not prove recent authentication, a requesting-device session, or original authentication age. This slice preserves the existing deletion authorization rather than inventing any of those assurances. Production activation still needs an accepted sensitive-operation authentication contract.

## Transaction and lock order

Since BA-04 PR 3 the staged deletion transaction starts with the shared authority gate, `pg_advisory_xact_lock_shared(6975, 2)`, under the 5 s statement and 4 s lock limits, validates the enforced projection, and puts those two limits back to the connection's own. A stale authority fails there, before any content is touched; the separate preflight transaction is gone. It then takes the shared fixed-owner key and keeps the existing deletion order: spray-account lock, descending wall locks and board locks, followed by the target user update lock. A user update lock before the wall locks would deadlock a wall/version writer that holds a wall and needs a creator foreign-key key-share lock. No identity helper may move that user lock earlier.

The gate is shared, so holding it through content and the cascade makes no other command wait: commands never wait for each other on it, and no other climber's command shares a lock with this deletion. Only an authority switch, which takes the gate exclusively, waits for a deletion in flight, and it gives up after its own 2 s rather than land between content and bookkeeping. After the final user delete, the staged path applies the short limits, re-validates the projection (the gate is already held, so this never waits; a writer that skipped the gate fails it and rolls everything back), checks the reservation, reads the current security generation and records an `account-deletion` mutation for both first-party and partner domains. The cutoff, retained deletion tombstone, security event, reservation changes, content cleanup and actual user deletion share the same outer transaction. Existing foreign-key cascades remove credentials, provider accounts, sessions and mobile refresh rows. A failure anywhere, including in the bookkeeping after the delete, must restore all of them and the earlier content changes.

Content and the cascade run under the connection's ordinary limits, the same as legacy deletion. Only the gate wait at the start and the final bookkeeping use the short ones.

The deletion never waits for the gate while holding a row, so it cannot close a cycle through it. A staged command naming the account waits for the deletion's user row, then reports unavailable, or proceeds and finds the account gone if the deletion commits first. Writers that must win (reset, verify) wait up to 4 s; a sign-in, forgot-password or resend-verification gives up after 250 ms, so a burst of them cannot hold the backend's pool connections behind the deletion. A wrong password is answered at once without the lock. Every such command locks the climber's users row before the email reservation, the order the deletion's bookkeeping uses, so none holds the reservation while it waits and the deletion's reservation lock cannot cycle with it. The final-lock savepoint retry existed only for the old one-row manifest lock and is gone.

A request for an account whose deletion already committed reports success and writes nothing: the phone can lose the first response, and its token stays valid because validators do not yet check the tombstone. The check runs under the spray-account lock, which also parks a concurrent request for the same account until the first commits. An absent user with no tombstone remains an error.

A deleted account keeps only a keyed digest of each address it held (decision 1 on epic #6975). Every key it alone held, including aliases, is replaced by a `blocked_deleted` reservation whose key is `deleted-v1:` plus the HMAC-SHA256 of the normalized address under `CURRENT_STORE_DELETED_EMAIL_KEY`; the plaintext reservation and the account's memberships are deleted. Registration, provider sign-in and system identities look up that digest when the address has no reservation of its own, so the address stays blocked and still answers as taken. A collision group the account shared keeps its other members and stays `blocked_ambiguous`: deleting one member never elects a surviving owner, and the last member's deletion turns the key into a digest. The empty key holds no address and is left alone. The account's password-recovery and email-verification receipts are deleted; their purpose generations stay, so no old receipt snapshot can come back. The backend maintenance job removes digests 90 days after deletion, far past the one-hour and 24-hour lives of any link sent to the address. Legacy `verificationTokens` rows keyed by the address are not touched, as legacy deletion leaves them.

Turn the staged deletion mode on before `auth-authority prepare` runs. A legacy deletion after `prepare` deletes the user but leaves its `owned` plaintext reservation, holding the address, forever.

`CURRENT_STORE_DELETED_EMAIL_KEY` is required by every staged mode, checked when the mode's configuration is read: at least 32 bytes, no surrounding whitespace, and different from `NEXTAUTH_SECRET`, `CRON_SECRET` and the RPC secrets. Without it every staged command fails the same way at configuration, logging a line that names the variable, so a missing key cannot tell a known address from an unknown one; the staged deletion fails before any content runs. Changing it frees every address deleted in the last 90 days early, so it stays fixed once set.

A server-generated operation ID is captured once for the logical deletion request. The existing three-attempt retry remains limited to PostgreSQL deadlocks, whose transactions rolled back. A retry reuses the operation ID and re-reads generation. Unknown outcomes, configuration errors, permission failures and duplicate committed operation IDs must not become cached success or automatic retries. Every staged failure logs one fixed line carrying only its failure code: our own error code or a PostgreSQL SQLSTATE, never a driver message, SQL text or anything identifying the account.

PostHog erasure still uses the existing queue savepoint. Kiosk tombstone publication and spray-photo purge remain after the deletion commits; an aborted transaction must never start those effects. No provider network request is added inside the transaction.

## Limits and decisions

The short limits bound the gate wait at the start and the bookkeeping statements, not the whole request; content and the cascade keep the connection's ordinary limits (45 s per statement on the production backend), so a heavy account can still take as long as it does under legacy deletion and holds its own account's locks for that time. A 40,000-tick account's staged deletion took about 0.4 s against the local test database (`per-user-auth-locks.test.ts`); production's cold pages are slower, and large-account admission and total-work bounds remain activation gates. This implementation must not be described as having a proven end-to-end time budget.

Persisting an event does not make old web/native JWT validators, caches, WebSockets, exchanges or partner consumers enforce it. Complete issuer/validator adoption and a measured enforcement window remain BA-04/BA-07 work. The selector is not a database privilege fence; stale direct writers and deployed roles require separate proof.

The user's password policy is unchanged: authenticated password set/change keeps the proven requesting device while revoking other credentials; forgotten reset revokes every session. The current set-password route has only a legacy user ID. Positive web source/publication lineage, original authentication-age evidence, renewal/logout handling and reader adoption are prerequisites to implementing that policy. A callback timestamp, rolling JWT issue time or legacy session identifier cannot replace them.
