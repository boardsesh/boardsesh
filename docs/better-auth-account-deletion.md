# Current-store account deletion

This is [PR #7307](https://github.com/boardsesh/boardsesh/pull/7307), an implementation slice of [BA-03 #6977](https://github.com/boardsesh/boardsesh/issues/6977) in [epic #6975](https://github.com/boardsesh/boardsesh/issues/6975). It adds independently selected security bookkeeping to the existing backend GraphQL account-deletion transaction. It does not activate an authority, migrate identities, change production privileges or delete a real account.

## Caller and authority boundary

The existing Expo flow is `DeleteAccountScreen` → `useDeleteAccount` → the shared `DELETE_ACCOUNT` GraphQL operation → `userMutations.deleteAccount`. Its input, Boolean response, confirmation UI and local sign-out behavior stay the same. No new web-to-backend credential command is needed: the mutation already belongs to the backend. The surviving web profile endpoint is read-only, and the profile mutation accepts cosmetic display-name/avatar fields rather than email changes.

`CURRENT_STORE_ACCOUNT_DELETION_MODE` defaults independently to `legacy`. The `reserved-staging` mode requires the exact configured current-store projection and writer epoch. Missing or malformed configuration must fail without falling back to legacy deletion. A normal legacy request must not read a projection or require current-store authority secrets.

The existing authenticated GraphQL principal supplies a server-established user ID. It does not prove recent authentication, a requesting-device session, or original authentication age. This slice preserves the existing deletion authorization rather than inventing any of those assurances. Production activation still needs an accepted sensitive-operation authentication contract.

## Transaction and lock order

The staged path runs a short, separate preflight transaction first: it applies the 5 s statement and 4 s lock limits, locks the enforced projection, validates it and commits, so a stale authority fails before any content is touched. The deletion transaction then takes the shared fixed-owner key and keeps the existing deletion order: spray-account lock, descending wall locks and board locks, followed by the target user update lock. A user update lock before the wall locks would deadlock a wall/version writer that holds a wall and needs a creator foreign-key key-share lock. No identity helper may move that user lock earlier.

`auth_email_projection` is one row every staged auth command locks first, so the deletion must not hold it through work of unbounded length. The transaction takes it last. After the final user delete, the staged path applies the short limits, locks and re-validates the projection, checks the reservation, reads the current security generation and records an `account-deletion` mutation for both first-party and partner domains. A projection change during content or the cascade fails that re-validation and rolls the whole deletion back; once locked, the row cannot change before commit. The cutoff, retained deletion tombstone, security event, reservation changes, content cleanup and actual user deletion share the same outer transaction. Existing foreign-key cascades remove credentials, provider accounts, sessions and mobile refresh rows. A failure anywhere, including in the bookkeeping after the delete, must restore all of them and the earlier content changes.

Content and the cascade run under the connection's ordinary limits, the same as legacy deletion. Only the preflight and the final bookkeeping use the short ones.

Taking the projection last means the deletion can wait on it while holding the shared fixed-owner key and the target user's row. The key cannot form a cycle because it never queues: an identity authority holding the projection is rejected as busy instead of waiting. The user row can: a same-account auth command holding the projection and waiting for that row deadlocks with the deletion, and PostgreSQL aborts one side after `deadlock_timeout`. If that is the deletion, the deadlock retry runs it again. If it is the auth command, that request fails for an account that is being deleted. Until then, that command holds the projection for up to its 4 s lock limit, so a sign-in racing its own account's deletion can still delay other auth commands that long. The deletion itself no longer does.

A request for an account whose deletion already committed reports success and writes nothing: the phone can lose the first response, and its token stays valid because validators do not yet check the tombstone. The check runs under the spray-account lock, which also parks a concurrent request for the same account until the first commits. An absent user with no tombstone remains an error.

Owned email reservations become `blocked_deleted`. Ambiguous keys stay ambiguous and retain historical membership: deleting one collision member never elects a surviving owner. The implementation does not release keys, merge accounts, reassign ownership or consume legacy email-keyed links by selecting a current email owner. Retaining deleted keys is an implementation safety default, not approval of a permanent registration or privacy-retention policy.

A server-generated operation ID is captured once for the logical deletion request. The existing three-attempt retry remains limited to PostgreSQL deadlocks, whose transactions rolled back. A retry reuses the operation ID and re-reads generation. Unknown outcomes, configuration errors, permission failures and duplicate committed operation IDs must not become cached success or automatic retries.

PostHog erasure still uses the existing queue savepoint. Kiosk tombstone publication and spray-photo purge remain after the deletion commits; an aborted transaction must never start those effects. No provider network request is added inside the transaction.

## Limits and decisions

The short limits bound the preflight and bookkeeping statements, not the whole request; content and the cascade keep the connection's ordinary limits, so a heavy account can still take as long as it does under legacy deletion and holds its own account's locks for that time. The final projection wait keeps the 4 s limit, so a busy projection can fail a finished deletion and roll all of its work back. Large-account admission, total-work bounds, contention and failure measurements remain activation gates. This implementation must not be described as having a proven end-to-end time budget.

Persisting an event does not make old web/native JWT validators, caches, WebSockets, exchanges or partner consumers enforce it. Complete issuer/validator adoption and a measured enforcement window remain BA-04/BA-07 work. The selector is not a database privilege fence; stale direct writers and deployed roles require separate proof.

The user's password policy is unchanged: authenticated password set/change keeps the proven requesting device while revoking other credentials; forgotten reset revokes every session. The current set-password route has only a legacy user ID. Positive web source/publication lineage, original authentication-age evidence, renewal/logout handling and reader adoption are prerequisites to implementing that policy. A callback timestamp, rolling JWT issue time or legacy session identifier cannot replace them.
