# Staged verification bound to a user ID

Status: implemented for default-off staging, with dual-version PostgreSQL QA on 2026-11-05. This is the next bounded BA-03 slice after [web password delegation](./better-auth-web-password-delegation.md). Production activation remains **NO-GO**. This does not complete BA-03 or change the authentication authority.

## Scope and decisions

Move verification issuance, consumption and resend together through the existing default-off backend transport. Registration must issue the new receipt in its existing identity/reservation transaction. Password changes, resets, account deletion, OAuth adoption and production activation remain separate work.

The backend owns the new `auth_email_verification_tokens` and `auth_email_verification_state` tables. A receipt binds immutable user ID, purpose, exact delivered address, normalized email key, subject generation, issuance generation, token hash and the original deadline. Neither table cascades from `users`; the receipt references its durable purpose state with `RESTRICT`. The generated migration is `0292_auth_uid_email_verification`, with its Drizzle journal and snapshot. No production migration has been applied.

The existing `CURRENT_STORE_WEB_AUTH_MODE` remains `legacy` by default. `backend-staging` uses the existing `CURRENT_STORE_AUTH_RPC_SECRET`, `CURRENT_STORE_AUTH_BACKEND_ORIGIN`, `CURRENT_STORE_AUTH_PROJECTION_ID` and `CURRENT_STORE_AUTH_WRITER_EPOCH`. The existing enabled-mode guards, including rejecting parameter SQL logging through `DEBUG_SQL=true`, remain required. An enforced projection is not an operational writer fence: the owned LOGIN-role fixture proves only its synthetic capability transfer. There is no production activation command in this slice.

New tokens use `ev1_` followed by 43 base64url characters from 32 random bytes. Storage contains a SHA-256 hash with a verification-specific purpose prefix, never the raw secret. The private mail plan is tagged `kind: 'uid-email-verification-v1'` and contains only recipient, token and original ISO deadline. It has no legacy email-keyed identifier. Registration issues this plan in the same transaction as its user, profile, credentials, normalized reservation and command nonce.

The query email never selects the user for a versioned token. Consume by token hash, copy the immutable initial binding before awaiting the manifest, and compare it again with the locked receipt. Recheck current user/key, reservation owner and sole member, both generations, deletion and terminal state. A fresh PostgreSQL clock after waits and a conditional terminal update establish redemption; consuming, advancing the durable purpose generation and verifying only the bound user commit together. Preserve an existing verification timestamp; issue no session or authentication freshness. Terminal receipt cleanup does not reset purpose state. Re-inserting an old unconsumed receipt cannot restore its generation.

Resend may issue only for an unambiguous owned reservation. Its purpose generation is separate from security/session generation. Superseding one verification link does not revoke login sessions. Issuance explicitly supersedes only active receipts for that UID and purpose, including expired active rows, before inserting a successor. The partial uniqueness index uses terminal state, not a volatile clock expression. Already-consumed receipts retain their terminal evidence. One PostgreSQL clock value defines issuance and its exact 24-hour deadline.

The delivered address remains immutable provenance. A same-UID case/trim-only stored-address normalization does not invalidate the link when the accepted JS-normalized key, current reservation owner and both generations remain unchanged. A true key/ownership change fails closed. This introduces no email writer or production normalization change.

Require `protocolVersion: 2` in all four command JSON bodies and authenticated tagged replies, before nonce or identity writes. The four fixed private operations are `register`, `password`, `verify-email` and `resend-verification`; a path cannot execute another operation. A header alone is insufficient: the existing v1 backend ignores unknown headers but rejects unknown body fields. Disabled, malformed, mismatched or unavailable services do not fall back to local writes. The existing strict transport keeps its correlated operation/request ID/status/schema checks, 16 KiB request limit, streamed 64 KiB reply limit, eight-second deadline and no automatic retry. Nonce retention and trusted-caller limitations remain those documented in the password delegation slice.

Agent decision: anonymous resend keeps the same generic successful response after authoritative absent, already-verified or ambiguous outcomes and after an SMTP delivery failure. Backend, SQL and protocol uncertainty remain retryable unavailability. This follows the accepted generic recovery design; it is not a new user-selected policy. The existing 1.5-second floor is not proof of constant-time behavior.

Agent decision: a verification-link outage returns localized `text/plain` HTTP 503 at the same URL, with a 30-second retry instruction. Include no token, email, URL, implementation error code, redirect or session cookie in the response. Use private/CDN no-store, no-referrer, noindex and Content-Language headers. Resolve a supported locale cookie explicitly because API middleware selects English. Keep existing finite 307 success/invalid/expired destinations, with credential-response privacy headers. No new React route is needed.

Web SMTP and the shared template remain delivery adapters temporarily. The token is URL-encoded in the actual template; legacy UUID output is unchanged. Private plans never appear in public JSON, NextAuth user/session fields or reflected SMTP exceptions. Resend sends only after the authoritative transaction commits. A lost reply can leave an unsent successor that supersedes the old link; deliberately requesting another email creates a fresh successor, and neither an unknown acknowledgement nor a send failure revives the old one. SMTP duration remains unbounded and slow delivery can reveal timing differences. Deployed delivery and logging configuration remain unverified activation blockers.

## Legacy links and rollback

Existing legacy rows do not contain original issuance user IDs. In staging, exact old-row lookup never changes the row: an actually expired known row returns `expired` and an absent row returns `invalid_token`. Until BA-02 (#4847) makes Postgres keep one account per address, a live link returns `legacy_unbound`/503 and no current user is selected. Once a valid unique index on exactly `lower(email)` exists, a live link binds to the one account holding its exact address, under the same rules as a pre-switch reset link in the [password recovery doc](./better-auth-password-recovery.md): an `owned` reservation and no other matching row, its original deadline (at most 24 hours away, checked again after lock waits), one use through an append-only replay record, and death after any later recorded security mutation. The legacy `/api/internal/set-password` route records none, so a link issued before that kind of set still works, as it does in legacy. Resend preserves all such legacy rows and deadlines. Arbitrary historical raw secrets up to the transport bound receive the same treatment as UUIDs; UUID shape is not ownership evidence.

Known non-verification identifier prefixes (`ba03-web-auth:`, `password-reset:`, `ba03-flow:` and `ba03-lineage:`) are rejected before lookup or mutation of the submitted legacy record. The public web guard runs before RPC or local SQL, including in default-off mode. A valid authenticated backend envelope still commits its one transport nonce with this negative outcome: both an exact repeat and a changed payload using the same request ID are rejected as replay. Transport bookkeeping never resolves or changes the submitted protected record. Neither command nonces nor reset records can become email-verification records through query parameters. An unknown versioned token never falls back to legacy lookup. Active unversioned secrets longer than 256 characters return same-URL unavailability before RPC and remain untouched; historical format/deadline inventory is still required.

Production requires independently proven original-owner evidence, or adoption and fencing of every issuer followed by a wait covering the actual last possible unbound deadline and clock allowance. Measure outstanding expiries; do not assume every historical row used today's 24-hour lifetime.

Recognize versioned verification tokens before legacy/default-off dispatch. A supported versioned link with its consumer disabled must return retryable unavailable and retain its receipt. Actual old public replicas remain a deployment gate. Capable consumers must remain available through all issued deadlines even when new issuance stops. The shared flag alone is not a safe rollback plan.

Default-off unversioned legacy handling otherwise remains the released consumer, including its email-keyed behavior. It is not an owner-safe fallback for staging. Production adoption remains blocked on all issuer and reader replicas, actual writer IAM/fencing, legacy provenance or the measured expiry wait, operational rollback, and cleanup/retention policy for retained user IDs and email addresses. The password-verdict-to-cookie reset race and validator adoption documented in the preceding slice also remain open. OAuth, native, recovery, deletion and job writers have not all been centralized by this change.

## Required verification

1. Real PostgreSQL double consume, resend/verify races, supersession, deletion, changed email/key, generation changes, expiry after lock waits and rollback after verification writes.
2. Mixed protocol versions reject before writes; updated consumers in disabled mode and unsupported-version handling never fall back to legacy email-keyed SQL. Unmodified old public replicas remain a rollout gate.
3. Public routes preserve finite redirects and cookie state; localized outage responses keep the original URL and reveal no credentials.
4. Actual strict client, authenticated HTTP and database execution, including registration, captured email, public consumption and the selected user's login verdict.
5. Generic resend outcomes, private mail projection, actual template round trips, all-locale catalog parity and existing native/web compatibility regressions.

The real-client integration runs the actual server-only web strict client against authenticated loopback HTTP and a separate non-owner PostgreSQL LOGIN pool. With verification enabled it captures the actual shared plain-text/HTML template through an offline public Nodemailer stream transport, calls the actual public GET module through the public `tsx` loader with web alias resolution, and checks the selected UID's subsequent password verdict. Only SMTP I/O creation is substituted; the template, URL parsing, public NextRequest/Response and backend RPC remain real. Its synthetic sibling cookie is not changed. This route-function test does not cover Next's global response headers or deployed ingress; separate live Next checks cover that local framework boundary. It is not a browser or deployed-replica proof.

## Measured validation

Author PostgreSQL 18.6 runs passed all 63 cases: the final lifecycle file passed 32/32 in 23.05 seconds (17.51 seconds of cases), and the updated password file passed 31/31 in 18.79 seconds (13.53 seconds of cases). Independent PostgreSQL 15 runs passed both final files: 32/32 in 24.15 seconds (19.14 seconds of cases) and 31/31 in 21.29 seconds (13.68 seconds of cases). Both versions completed fixture cleanup. These tests use unique owned roles, actual LOGIN pools and real privilege transfer; they do not inventory production role inheritance, owners or issuer access.

The lifecycle regressions include two concurrent consumes, both resend/consume orderings and their race, expired-active supersession, terminal-generation survival after receipt cleanup, harmless address normalization, true key/owner/member/security-generation/deletion changes, immutable binding and caller-input changes across an observed manifest wait, and expiry observed before and after the PostgreSQL clock crosses the deadline. A real final-user CHECK violation is asserted as SQLSTATE `23514` with its exact fixture constraint; receipt consumption, purpose generation, command nonce and user verification all roll back before a successful fresh retry. The test retains UPDATE rights so this failure occurs after the earlier row locks rather than being mistaken for a post-write rollback proof.

The author frontend/protocol/email selection passed 248/248 across 13 files; an independent run passed 248/248 in 7.53 seconds. It covers actual public route exports with transport stubs, version/default-off dispatch, five-locale unavailable responses, unchanged cookies, private mail projection, generic resend outcomes and both template representations. The separate real-client child described above connects the actual public GET module to actual authenticated backend HTTP and PostgreSQL. Neither selection by itself is a deployed multi-replica or ingress test.

Backend TypeScript checking passed. The owned 11-file backend/schema/test selection passed formatting, lint and targeted type checking with zero warnings or errors.
