# Account, activity, session and home-board privacy

Implementation issue: [#6242](https://github.com/boardsesh/boardsesh/issues/6242), under the Boardz follow-up epic [#6238](https://github.com/boardsesh/boardsesh/issues/6238). Privacy applies independently of the Full/Minimal layout preference.

## What a climber chooses

| Setting | Choices | Default and effect |
| --- | --- | --- |
| Account | Public, Private | New accounts start private once controls are enabled, and switch in Settings → Privacy. Before rollout they retain the legacy public default. Existing accounts keep their setting until they choose. Private activity is visible to its author and accepted followers. |
| Social item | Public, Followers, Only me | Private accounts default to Followers. A public exception needs confirmation; a later switch to Private invalidates earlier exceptions. |
| Session | Public, Anyone with the link (Unlisted), Followers, Invite-only | Public accounts default to Public; private accounts to Followers, for explicit and inferred sessions alike. Followers means accepted followers of the host. An Invite-only link requests access. The legacy Private switch (`is_public = false`) means Unlisted: the session leaves the live listings, nearby discovery and kiosk previews, and its invite link still joins. |
| Home board | Public, Unlisted, Followers, Invite-only | New home boards start Invite-only without invitees. Unlisted permits a direct link, but excludes discovery. Owners may additionally inherit follower access. |
| Board location | Only me, Followers, Invited people, Everyone with board access | New boards hide location. Seeing a board does not necessarily reveal its address, coordinates, gym or distance. |

Account approval uses the existing `user_follows` relation for accepted followers and a separate pending request table. Following a private climber creates a request; it does not approve itself. Existing followers keep access when the account becomes private, and the climber can remove them. Approvals and removal use the target account's authority.

Item controls accompany tick, comment, climb, playlist and beta publication. Existing items have an editable audience indicator. Session posts use the session audience.

Activity follows its author. A tick is readable when its author's account privacy and the tick's own audience allow it; the session it was logged in and the board it was logged on never hide it. Board privacy hides the board's identity on the item instead: its name, location, gym, coordinates and distance are blank for a viewer who cannot see the board, and the row stays. An unlisted board is named only to people who already hold it, since a log is not a link. On logs, beta and feeds, holding it means owning it, an approved grant, or follower inheritance (`boardIdentityVisibleCondition`). The live-sessions rail and board sheet also count an unlisted board the viewer follows or has selected, because they reached it through its link. Their board projections apply the current audience and grants before returning a name or UUID, so a revoked board grant hides its identity while the session remains readable. A session on a named board (`/b/<slug>`) returns its board path as geometry (`/<type>/<layout>/<size>/<sets>/<angle>`) to a viewer who cannot see the board, so the invite link still joins without naming it. That covers the session payload, roster snapshots, `SessionBoardPathChanged` and nearby discovery. A soft-deleted board keeps its row, so its slug still resolves to geometry; only its owner and anyone holding an approved grant on it keep the named path. A slug no board row carries any more (renamed since, or its account deleted) comes back as the empty path. A public `userTicks` logbook returns a tick's `sessionId` only to the tick's climber, since a session id is its invite link. In a multi-user session each participant's ticks follow that participant's account; the session's name, notes and roster follow the session's own audience. A missing, unresolvable or soft-deleted parent board never hides the item, and never withholds a session's place. Its identity follows the same rule as any board the viewer cannot see: a deleted board is no longer named (its fields stay blank, and the row stays), except in its climber's own logbook. A comment's audience still cannot widen its thread, and a tick still cannot reveal a climb whose own audience has narrowed. Spray walls keep their separate wall rule. Joining a session or using Bluetooth does not approve access to another climber's activity. Profile name/avatar remain discoverable so someone can request a follow; activity, linked board identities and personal counts are withheld from unauthorized profile visitors.

Ticks continue contributing to numeric climb and board aggregates. Board history retains events with private attribution removed. Projections remove real account IDs, names, avatars, identifying comments and protected climb details. Where realtime protocols require participant IDs, the backend uses session-scoped opaque identifiers. An aggregate total is never a list of private climbers with stable pseudonyms.

## Enforcement and writes

`packages/shared/privacy` defines renderer-independent policy. `packages/db/src/queries/privacy.ts` expresses the policy inside queries, before pagination and counts. Backend runtime helpers in `services/privacy.ts` authorize individual resources. Policy reads use the primary database: a lagging replica cannot restore a revoked grant.

Session authorization reads the session's own policy only. Its primary and attached boards, and the boards named by legacy named-board and spray paths, are looked up for one purpose: a session's coordinates and distance are withheld unless every live board it names lets the viewer see its location. A missing or soft-deleted board on those paths withholds nothing. A local PostgreSQL `EXPLAIN (ANALYZE, BUFFERS)` fixture with 2,500 boards and 25 sessions measured the primary/attached-board lookup at 0.7 ms, compared with 317 ms for scanning the board registry first; the old estimated cost also triggered JIT compilation. An account/content count over 10,000 climbs (1,000 authored) took 27 ms and used the policy, profile and follow indexes. These are fixture measurements, not production latency targets; profile feed and sync plans on representative data before increasing rollout.

Migration `0261_account_resource_privacy.sql` adds account privacy revisions and onboarding completion, content policies, resource policies/grants and follow requests. Onboarding completion is no longer read: the forced setup screen is retired (see the release sequence), and the column waits for a later migration to drop it. Legacy rows remain supported. New native and web account creation choose private defaults only once controls are enabled; backend-first deployment keeps legacy public defaults until users can manage approvals. Existing private choices are never reset when the flag is disabled, and a missing profile on an existing account remains public for compatibility.

Comment references use a bounded recursive query: every intermediate comment must be readable, and a missing, cyclic or over-depth entity reference fails closed. A comment is its author's activity, read through its own audience and the audience of every reply ancestor above it, so a public reply never widens a private parent. Three exemptions sit on top (`commentPrivacyCondition`):

- The owner of the commented item reads every comment and like on it, whatever the commenter's account privacy: the tick's climber, the session's host, the climb's setter, the playlist's owner, a comment's author (for likes on it), and a live board's or gym's owner (`entityOwnerCondition`). That includes a comment whose own audience is Only me or Followers: the app's composer offers no audience, but an API caller can set one, and it never hides a comment from the owner of the item it is on. The spray wall rule and a climb's draft and listing rules still apply to owners. A proposal has no owner: it is moderation on someone else's climb, so its proposer reads other people's comments on it, and hears about its votes and outcome, by the same account rule as anyone else.
- An owner is notified only where Boardsesh already sends a notification. Comments and likes on your tick (`comment_on_tick`, `vote_on_tick`) and likes on your comment (`vote_on_comment`) arrive whatever the actor's account privacy. A reply to your comment (`comment_reply`) follows the replier's privacy, like any reply. Session hosts, climb setters, playlist owners and board or gym owners get no comment or like notifications, and `comment_on_climb` has no sender ([#6385](https://github.com/boardsesh/boardsesh/issues/6385)).
- Whoever replied in a thread reads every comment above their reply. The viewer's own replies are walked up to their roots once per statement (a hashed set, not a walk per row), so the parent they answered stays readable to them, and so do public replies beside theirs. A private reply beside theirs stays hidden, and so does everything under it. On a 200-comment thread this read takes 2.1 ms against 6.6 ms for a per-row walk. A read about one item (a thread, adding or editing a comment, a deleted-comment event) starts the walk from the viewer's comments on that item only, because a reply always shares its parent's item. Feeds and the inbox, which span items, walk from all of them. On a 600,000-comment fixture with production's planner settings, a viewer with 10,000 replies across the site paid 267 ms for the site-wide walk and 0.5 ms for the walk scoped to the thread.
- A reply ancestor that no longer exists is readable. Deleting an account cascades its comments; the replies under them stay readable instead of orphaned. A missing ancestor stops blocking the chain and nothing more: each surviving reply still follows its own author's account privacy and its own audience, exactly as it would under a live public ancestor.

Reply ancestry must still end at a root or a missing row within 32 ancestors. Cycles and longer chains fail closed for everyone, owners and authors included. The global comment feed disables PostgreSQL JIT only inside its read transaction. A small local fixture returned three comments in 105 ms rather than 11 seconds; `EXPLAIN ANALYZE` attributed 10.9 seconds to JIT compilation. Permissions and pagination still run in SQL, and the transaction leaves database defaults unchanged.

Publication inputs carry an audience and the account's privacy revision. Writes save content and its policy in the same transaction. A stale explicit Public choice fails with `PRIVACY_REVISION_CONFLICT`, so a saved draft or queued mutation cannot silently undo a subsequent privacy change. Omitting privacy on an old client's edit preserves existing policy. Old board/session visibility booleans cannot widen a newer resource policy, and stale location toggles cannot reveal an address; use the audience control to widen access. Resources created with only legacy booleans retain no policy override, so installed clients can still switch Public to Private and back. A modern audience/location choice or restrictive account session default establishes an override that legacy booleans cannot widen. A legacy playlist Public-to-Private transition also withdraws explicit public consent while retaining invited collaborators. Privacy-bearing queued publications still commit during a controls rollback, with revision checks unchanged. Mutations verify ownership under row locks; approval cannot race a resource ownership change.

Account deletion materializes restrictions before clearing author references. Content and resource policies survive as ownerless records, preventing private climbs, personal beta and restricted sessions from becoming public after deletion. Existing public published climbs can remain readable, but retain an internal `is_boardsesh_authored` marker: snapshot exports exclude them and first-ascent projection still resolves current tick permission instead of trusting a cached name. Imported manufacturer data is untouched. The transaction preserves numeric climb aggregates and retained board/history references, then broadcasts cache invalidation after commit.

`resource_privacy` overrides legacy visibility fields. Board/session access and location are checked separately. Revocation overrides inherited follower access. Switching an Unlisted board to Invite-only withdraws direct-link access. A legacy `board_sessions.is_public = false` without an override reads as Unlisted, and old clients' Private switch writes Unlisted; only an explicit audience asks for Invite-only. Listings (live sessions, nearby sessions, kiosk previews, and session cards in the session feed and Home) use the no-link rule, so an Unlisted session appears there only for its host and the people who joined it. The global comment feed and the activity feed are discovery too: a comment on an Unlisted session reaches them only for that host and roster (`listedSessionCondition`), since the comment carries the session id, which is its link. A comment on an Unlisted board, or a comment that references one, reaches them only for the people who already hold that board (its owner, an approved grant, or follower inheritance), since the global comment feed returns the board's UUID as the comment's `entityId`. The session's or board's own thread, votes and the notifications addressed to someone in the thread keep the link reading. A tick in a session the viewer cannot open as a card still follows its author: it lands on the climber's daily card for that day, without the session's name or roster. Readable logs outside the viewer's session cards stay on that daily card even when the same day also has an openable session; only logs already represented by a session card are excluded. The old client's "Show this session live" switch moves a session between Public and Unlisted in both directions. Inferred session splits copy privacy and grants; merges preserve the restrictive intersection, and that policy covers the session's name, notes and roster only. Moving ticks between sessions never rewrites their audience: reconciliation writes no `content_privacy` rows. Migration `0265_privacy_reconcile_tick_tombstones.sql` removes the Only-me rows earlier reconciliation stamped on ticks it moved into explicit sessions, and rewrites the session policies the legacy switch wrote as Invite-only after #6254 to Unlisted. Its precondition was confirmed by the owner on 2026-10-12: the flag (`BOARDSESH_PRIVACY_ENABLED`) was never enabled in production. Moving comments out of a restricted session still keeps them restricted.

## Reads, live updates and downloaded copies

Feeds, profiles, search, comments, votes, notifications, playlists, beta links, session views and board history authorize their current viewer. Ticks follow their author; a feed scoped to one board (trending, the session feed's board filter, the materialized feed's board filter) first requires access to that board. Board history and the Bluetooth holder name a climber by their account privacy alone, whatever session the event belonged to. Comments are capped by their thread, except for the item's owner and the people who replied in it. A gym's thread reads exactly when the gym does. `gym` shows a private gym only to its owner, its admin and editor members, and community admins or leaders whose role is global or covers a board type live at the gym (`userCanEditGym`); its comments, likes, notifications and feed entries stay with the same people (`gymVisibleCondition`, the SQL form of that rule). A plain gym member does not see them. A public gym's thread reads for everyone, signed in or not. Climb proposals are moderation on a published climb: the reason, vote tally and comment thread read for everyone who can read the climb, and only a private proposer's or resolver's id, name and avatar are withheld. Each comment in a proposal thread still follows its author's privacy, for the proposer too, so the first reporter does not read a later private reporter's words or name unless they follow them. The same rule decides whether the proposer's inbox names a private moderator or voter. Voting on a proposal needs the same read access to its climb as the listings; anything else reads as not found. Public web rendering and OG previews use anonymous backend authorization. Sensitive responses avoid shared persistent caches; sitemaps reauthorize persisted candidates before returning their URLs. Private profiles and settings are not indexed.

The authenticated `privacyChanged` stream carries an opaque Boolean, including on reconnect. It discloses no changed account or resource IDs. After a committed change, clients cancel requests, clear protected query snapshots and refetch. Live iterators recheck access even when no ordinary activity event arrives. Redis carries invalidation between backend instances.

Native infinite climb searches share identical cached rows only within the same privacy epoch. A fresh authorized response after withdrawal receives fresh row identities, even when its contents are unchanged, so list activation can accept it while rejecting retained rows and callbacks. Read provenance is shared across query observers; paging that still contains withdrawn pages does not authorize them again.

Every connected app reacts to every event, so the backend publishes on these commits only: switching the account between public and private; `setContentAudience` and `updateResourcePrivacy`; approving a follow request; removing a follower who was following; approving, revoking or inviting resource access when the grant's status changes; deleting an account; editing a comment, tick or playlist with an explicit audience; editing a playlist, session or board whose stored visibility actually flips, or a board whose location visibility changes; a tick save, edit or delete whose inferred-session regrouping takes access away (a merge whose intersected policy is narrower than one of its sources, content restricted to its author, or a tick moved under a narrower explicit session); a live session moving onto a wall that some viewer cannot read without a link (not public, or public with a revoked viewer), decided inside the move's transaction under a share lock on the wall's row, so an edit to that wall lands before the decision or waits for the move; and `updateClimb` with an explicit audience, which still logs as `source: "unattributed"` until another change in this series retires it. Edit screens that resend an unchanged `isPublic` with a rename publish nothing. These do not publish: following or unfollowing (users and setters), follow and access requests, cancelling or declining a request, the privacy onboarding and settings save unless the account switch flips (the default session audience only applies to sessions created later), renames, notes and description edits, saving a tick or editing one without an audience when regrouping narrows nothing (a merge of equal audiences, a split, a new session, and the backfill), and moving a live session onto a public wall or back onto one it already references. Every wall switch still re-derives the public kiosk previews, and live session streams recheck access on their next event. Deleting a board has never published, although it hides the board from everyone but its owner; that is a known gap. The app that made a follow change refreshes its own caches. A publish goes out as soon as its write commits, before the public kiosk previews are refreshed: that refresh does its own Redis and database reads and can fail, and a failure must not hold back the invalidation. Each publish writes one `[Privacy] privacyChanged published` log line with its `source` and a per-process running `count`, so the rate per call site can be read from production logs. The stream still yields once on every subscribe: installed app bundles stamp their offline catalogue viewer marker from that first event, so removing it waits for a client release that no longer depends on it.

On an event the native app withdraws other people's projections (profiles, feeds, sessions, logbooks, comments, notifications, boards, playlists, beta and any query root it does not recognise), refetches climb search lists that are on screen without blanking them (an off-screen one, a spray wall's search, or one whose key names no board is withdrawn in full), and leaves the viewer's own profile and unsynced ticks, offline download bookkeeping, developer tools and static reference data (grade scales, angles, the popular-config rail) alone. The website withdraws every cached client query except its auth-token and privacy-settings transport queries and drops the persisted cache (which only ever holds the viewer's own profile queries). It re-renders the server markup only on pages that server-render other people's protected content (walls, sessions, profiles, playlists, setters, gyms and climb pages); other pages keep theirs. It listens on the tab's one shared realtime socket, the same one live comment threads use.

Native and Expo web clear cached protected catalog rows and spray media on invalidation, while retaining the viewer's own ticks, outbox and drafts. Pull checkpoints reset so allowed rows can be fetched again. Local reads return their unavailable fallback during withdrawal; a failed purge fails closed. Online authenticated reads and cleared query refetches continue immediately through the server, without waiting for SQLite or enriching/rescuing from withdrawn local copies. A local repair failure does not turn a successfully saved privacy setting into an apparent save failure. A persistent viewer marker binds catalogue access to a SHA-256 digest of the credential last checked against the authenticated profile API; tokens are never stored in SQLite. The same credential can use downloads offline after restart. A missing marker, another account, or a changed credential requires online revalidation. In-process invalidation epochs discard older reads even after a replacement catalogue is ready. The current viewer's rows and every queued climb reference are preserved. Another account's draft without a positive server sync sequence is retained as possible unsynced work; if those protected rows remain, local catalogue reads stay blocked while server reads continue. Downloaded foreign drafts with a positive server sequence are replaceable cache, since `is_draft` is mirrored from the server and does not identify local work. In-progress editor drafts live in a separate preference store and are untouched. Revalidation can trigger a catalog replay, so measure reconnect bandwidth during rollout. The bridge serializes repairs, retains one trailing repair for events received during a run, and retries a failure after 1, 5 and 15 seconds while foregrounded and online. Schema/handle availability, reconnect and foreground resume a retained failure; account or handle replacement retires obsolete attempts. Successful repair wakes enabled downloads for authorized replay. A device that is offline cannot receive a revocation until it reconnects, and previously delivered files cannot be recalled from someone else's storage.

Native catalogue revalidation handles SQLite contention with the existing background write policy: at most three attempts with 250 ms gaps and a 20-second retry budget for each write task. Withdrawal of the persistent viewer marker completes before the authenticated profile request, including when an event arrives offline or backgrounded; authorization then waits for a foreground connection. An automatic token refresh during authorization triggers one additional profile request; only a digest stable across that authenticated response can authorize the catalogue. Credential checks also surround marker stamping and completion. A current read that finds an existing marker for an older token requests recovery; startup probes once the privacy bridge is installed so an earlier mismatch cannot be lost. Each catalogue transaction takes the immediate write lock before reading and retries on a fresh connection. Exhausted retries, non-lock errors and changed credentials keep catalogue reads blocked; personal ticks, drafts and pending mutations retain the same protection.

Solo queue persistence stores climb references, order and mirror choices, without copied climb details or attribution. Legacy snapshots are sanitized when read. A privacy or credential change retires Undo offers and older asynchronous queue work; current queue entries lose copied details until an authorized read restores them. The auxiliary playlist swipe track is cleared on withdrawal and is not persisted; reopening the playlist restores that track after checking its permissions. Drafts and the mutation outbox remain intact.

Playlist editing also withdraws copied climb details and retires outstanding edit callbacks. The active-board file stores only the selected wall reference, layout, local angle and device configuration. Names, owner details and location require a current authorized response; offline startup uses a generic board label. Privacy refresh retains the neutral wall configuration while catalogue withdrawal completes, so device pairing does not depend on copied identity details.

Kiosk previews, watch polling, session discovery and Live Activity pushes reauthorize current climb details. Quiet privacy changes withdraw copied kiosk and lock-screen content. APNs recipients are checked against current grants, and updates prepared before invalidation cannot follow the clearing push on the same server. Revoked sessions receive an empty, immediately dismissed Live Activity. The watch endpoint changes its sequence when redacting a climb and returns the existing session-ended response when session access is revoked, so installed watches clear their prior display.

Static snapshots now contain external, unowned catalog data only and carry `privacyVersion: 1` in manifest/artifact format 2. Shipped format-1 clients reject this changed dataset and use authenticated paged sync, so their old watermark logic cannot skip authored climbs. Authored content comes from the viewer-authorized API. Old public artifacts must be removed from managed origins and CDN caches before enabling controls. See [snapshot rollout](board-snapshots.md#account-privacy-and-snapshot-rollout) and [dataset contract](board-snapshots-dataset.md).

Privacy controls cover Boardsesh activity and account associations. Imported manufacturer setter names and first-ascent credits remain part of the external public catalog; making a Boardsesh account private does not rewrite those external credits. Independently imported manufacturer beta links follow the same rule. Both Boardsesh beta creation paths stamp the authenticated creator; upstream sync preserves that ownership on conflict, so a later import cannot turn a Boardsesh upload into an unowned public link. Reads hide the link from an external setter to a private Boardsesh account. First-ascent credits produced from Boardsesh ticks are checked against the current tick, account and resource policies before displaying an identity.

## Release sequence

1. Apply the generated migration and deploy backend/web read enforcement with `BOARDSESH_PRIVACY_ENABLED` unset. Read enforcement is always active; the flag gates settings and publication controls.
2. Regenerate format-2 privacy snapshots, replace manifests and withdraw older public artifacts and cached previews. Validate anonymous, owner, accepted follower, pending follower and removed follower reads against the primary database.
3. Ship native and Expo web clients with audience controls, cache withdrawal and the Settings → Privacy page. Verify stale client mutations preserve restrictions and stale public drafts are rejected.
4. Enable `BOARDSESH_PRIVACY_ENABLED=1` on the backend and web account issuer after backend enforcement and artifact cleanup are confirmed. Nobody is sent through a setup screen: existing accounts keep their setting and change it in Settings. The deprecated `privacyOnboardingVersion` field always reads 1, so app builds that still carry the retired setup screen never open it, and its input is accepted and ignored.
5. Watch denied reads, mutation errors, invalidation delivery and catalog replay cost. Roll back controls by disabling the flag while retaining enforcement and additive database tables; never roll back to a reader that ignores privacy.

Settings → Privacy holds the Public or Private choice, session defaults, a home-board review, follow requests and followers. Settings, approvals and audience labels are translated in English, Spanish, French and German. The desktop settings page hands off to the same Expo app settings, while surviving web profiles use the same follow approvals and private activity boundary.

## Regression coverage

The database privacy matrix exercises self, accepted and pending followers, strangers, Only me, explicit Public consent and stale revisions, parent resources, comment ancestors (including deleted ones), reply authors, the owner of each item type, private and public gym threads for every role `gym` checks, deleted-comment events on a live thread, private moderators and voters in a proposer's inbox, beta attachments, notifications and follower removal while checking aggregate retention. Separate session tests cover merges/splits, board history projection and invalidation during quiet subscriptions. Client tests cover publication revisions, cache withdrawal and snapshot compatibility; public preview and sitemap tests check current authorization rather than cached visibility.

Run the backend suites against their PostgreSQL/Redis test services. Do not run two independent backend test processes against the same database: each process resets its schema. The manual tester flows are in the worktree's `.boardsesh/qa-notes.md` and the PR test plan.

Social test tables must use the production `social_entity_type` enum. Using text instead hides PostgreSQL comparison and recursive UNION errors. The shared privacy helpers normalize incoming entity types to text because `content_privacy` also covers non-social types such as playlists and beta links. Real resolver tests cover unread notification counts, materialized activity feeds and bulk session votes with these enum columns.

The privacy matrix also covers empty inboxes, exact unread counts, read and other-recipient exclusions, aliased flat and grouped inboxes, private comment ancestors and retained ownerless policies.
