# Account, activity, session and home-board privacy

Implementation issue: [#6242](https://github.com/boardsesh/boardsesh/issues/6242), under the Boardz follow-up epic [#6238](https://github.com/boardsesh/boardsesh/issues/6238). Privacy applies independently of the Full/Minimal layout preference.

## What a climber chooses

| Setting | Choices | Default and effect |
| --- | --- | --- |
| Account | Public, Private | New accounts start protected until setup once controls are enabled. Before rollout they retain the legacy public default. Existing accounts keep their setting until they choose. Private activity is visible to its author and accepted followers. |
| Social item | Public, Followers, Only me | Private accounts default to Followers. A public exception needs confirmation; a later switch to Private invalidates earlier exceptions. |
| Session | Public, Followers, Invite-only | Public accounts default to Public; private accounts to Followers. Followers means accepted followers of the host. A private link requests access. |
| Home board | Public, Unlisted, Followers, Invite-only | New home boards start Invite-only without invitees. Unlisted permits a direct link, but excludes discovery. Owners may additionally inherit follower access. |
| Board location | Only me, Followers, Invited people, Everyone with board access | New boards hide location. Seeing a board does not necessarily reveal its address, coordinates, gym or distance. |

Account approval uses the existing `user_follows` relation for accepted followers and a separate pending request table. Following a private climber creates a request; it does not approve itself. Existing followers keep access when the account becomes private, and the climber can remove them. Approvals and removal use the target account's authority.

Item controls accompany tick, comment, climb, playlist and beta publication. Existing items have an editable audience indicator. Session posts use the session audience. An item's audience cannot widen access to its containing session, board, climb or comment thread. Joining a session or using Bluetooth does not approve access to another climber's activity. Profile name/avatar remain discoverable so someone can request a follow; activity, linked board identities and personal counts are withheld from unauthorized profile visitors.

Ticks continue contributing to numeric climb and board aggregates. Board history retains events with private attribution removed. Projections remove real account IDs, names, avatars, identifying comments and protected climb details. Where realtime protocols require participant IDs, the backend uses session-scoped opaque identifiers. An aggregate total is never a list of private climbers with stable pseudonyms.

## Enforcement and writes

`packages/shared/privacy` defines renderer-independent policy. `packages/db/src/queries/privacy.ts` expresses the policy inside queries, before pagination and counts. Backend runtime helpers in `services/privacy.ts` authorize individual resources. Policy reads use the primary database: a lagging replica cannot restore a revoked grant.

Session authorization first selects the session's primary and attached board IDs, then checks those boards. It also resolves legacy named-board and spray paths; a missing parent on those paths fails closed. A local PostgreSQL `EXPLAIN (ANALYZE, BUFFERS)` fixture with 2,500 boards and 25 sessions measured the primary/attached-board lookup at 0.7 ms, compared with 317 ms for scanning the board registry first; the old estimated cost also triggered JIT compilation. An account/content count over 10,000 climbs (1,000 authored) took 27 ms and used the policy, profile and follow indexes. These are fixture measurements, not production latency targets; profile feed and sync plans on representative data before increasing rollout.

Migration `0261_account_resource_privacy.sql` adds account privacy revisions and onboarding completion, content policies, resource policies/grants and follow requests. Legacy rows remain supported. New native and web account creation choose private defaults only once controls are enabled; backend-first deployment keeps legacy public defaults until users can manage approvals. Existing private choices are never reset when the flag is disabled, and a missing profile on an existing account remains public for compatibility.

Comment references use a bounded recursive query: every intermediate comment and its reply ancestors must be readable, and missing, cyclic or over-depth references fail closed. Reply ancestry must reach a root within 32 ancestors; deleting an ancestor's account cannot expose surviving replies. The global comment feed disables PostgreSQL JIT only inside its read transaction. A small local fixture returned three comments in 105 ms rather than 11 seconds; `EXPLAIN ANALYZE` attributed 10.9 seconds to JIT compilation. Permissions and pagination still run in SQL, and the transaction leaves database defaults unchanged.

Publication inputs carry an audience and the account's privacy revision. Writes save content and its policy in the same transaction. A stale explicit Public choice fails with `PRIVACY_REVISION_CONFLICT`, so a saved draft or queued mutation cannot silently undo a subsequent privacy change. Omitting privacy on an old client's edit preserves existing policy. Old board/session visibility booleans cannot widen a newer resource policy, and stale location toggles cannot reveal an address; use the audience control to widen access. Resources created with only legacy booleans retain no policy override, so installed clients can still switch Public to Private and back. A modern audience/location choice or restrictive account session default establishes an override that legacy booleans cannot widen. A legacy playlist Public-to-Private transition also withdraws explicit public consent while retaining invited collaborators. Privacy-bearing queued publications still commit during a controls rollback, with revision checks unchanged. Mutations verify ownership under row locks; approval cannot race a resource ownership change.

Account deletion materializes restrictions before clearing author references. Content and resource policies survive as ownerless records, preventing private climbs, personal beta and restricted sessions from becoming public after deletion. Existing public published climbs can remain readable, but retain an internal `is_boardsesh_authored` marker: snapshot exports and the board sync carry them with no first-ascent name or date, and first-ascent projection still resolves current tick permission instead of trusting a cached name. Imported manufacturer data is untouched. The transaction preserves numeric climb aggregates and retained board/history references, then broadcasts cache invalidation after commit.

`resource_privacy` overrides legacy visibility fields. Board/session access and location are checked separately. Revocation overrides inherited follower access. Switching an Unlisted board to Invite-only withdraws direct-link access. Inferred session splits copy privacy and grants; merges preserve the restrictive intersection. Moving ticks or comments out of a restricted session must not publish them.

## Drafts

A draft climb is returned to its owner and to nobody else. That covers the climb and everything read from it: its name, holds, setter, stats and grades rows, and whether it exists. The owner is the Boardsesh `user_id` on the climb. A draft with no owner is returned to no one.

In the online reads the rule sits beside the account and item audience, and is narrower. `contentVisibilityCondition` has no draft term: on its own it shows a public account's draft to every viewer and a draft nobody owns to everyone. `climbDraftVisibilityCondition` in `packages/db/src/queries/privacy.ts` is the rule, and `climbVisibilityCondition` is the two together. A query that returns a climb, or anything derived from one, uses that, or filters `is_draft = false` when it has no owner to serve. `is_draft` is nullable and NULL is not a draft, so the rule is written `IS NOT TRUE` / `IS TRUE`.

Where it holds:

- **Board sync and snapshot artifacts.** There it is one half of the publication rule, which also keeps an unlisted climb to its owner and applies no account or item audience to a published, listed climb. See [The publication rule](board-snapshots.md#the-publication-rule-6306).
- **Reads by reference.** Climb detail, per-angle stats and stats history, Boardsesh grades, the grade outlier analysis, playlist climbs, favourites, liked-climbs playlists, the live similar-climbs target, the caption scan, the session summary's hardest climb and its export, the board's hardest send, the gym's top climbs, the layout's live stats broadcast, and the public climb pages and REST routes on www (which have no viewer, so they serve no draft at all).
- **Lists.** Search, setter and profile pages, feeds, recommendations, similar climbs, popularity and sitemaps filter `is_draft = false`. The drafts list compares the row's `user_id` with the caller and nothing else.

A draft's owner is set where the draft is written. A climb set in Boardsesh carries its author. Both manufacturer imports stamp the account they run for: the account export import, and the linked-account draft import, which keeps an owner already on the row (`COALESCE(stored, incoming)`), so a re-import, a run with no account behind it, or a second Boardsesh account linked to the same manufacturer account cannot clear it or take the draft over. The catalogue sync never clears an owner either: an imported draft keeps its owner when the manufacturer publishes it. The draft import writes over stored drafts only, so it cannot take a published climb back to a draft or hand it to the importing account.

Drafts and unlisted climbs imported before the import stamped an owner have none, so nobody is returned them until they are given one. `vp run db:backfill-climb-owners` does that for the ones whose setter is linked by exactly one Boardsesh account on that board; it is a dry run unless `-- --apply` is passed, takes `--only drafts` or `--only unlisted`, and prints counts only. Climbs it cannot match stay without an owner. A draft also gains its owner the next time its setter's linked account re-imports it.

## Reads, live updates and downloaded copies

Feeds, profiles, search, comments, votes, notifications, playlists, beta links, session views and board history authorize their current viewer. Child content is capped by its parents. Public web rendering and OG previews use anonymous backend authorization. Sensitive responses avoid shared persistent caches; sitemaps reauthorize persisted candidates before returning their URLs. Private profiles and settings are not indexed.

The authenticated `privacyChanged` stream carries an opaque Boolean, including on reconnect. It discloses no changed account or resource IDs. After a committed change, clients cancel requests, clear protected query snapshots and refetch. Live iterators recheck access even when no ordinary activity event arrives. Redis carries invalidation between backend instances.

Every connected app reacts to every event, so the backend publishes on these commits only: switching the account between public and private; `setContentAudience` and `updateResourcePrivacy`; approving a follow request; removing a follower who was following; approving, revoking or inviting resource access when the grant's status changes; deleting an account; editing a comment, tick or playlist with an explicit audience; editing a playlist, session or board whose stored visibility actually flips, or a board whose location visibility changes; a tick save, edit or delete whose inferred-session regrouping takes access away (a merge whose intersected policy is narrower than one of its sources, content restricted to its author, or a tick moved under a narrower explicit session); a live session moving onto a wall that some viewer cannot read without a link (not public, or public with a revoked viewer), decided inside the move's transaction under a share lock on the wall's row, so an edit to that wall lands before the decision or waits for the move; and `updateClimb` with an explicit audience, which still logs as `source: "unattributed"` until another change in this series retires it. Edit screens that resend an unchanged `isPublic` with a rename publish nothing. These do not publish: following or unfollowing (users and setters), follow and access requests, cancelling or declining a request, the privacy onboarding and settings save unless the account switch flips (the default session audience only applies to sessions created later), renames, notes and description edits, saving a tick or editing one without an audience when regrouping narrows nothing (a merge of equal audiences, a split, a new session, and the backfill), and moving a live session onto a public wall or back onto one it already references. Every wall switch still re-derives the public kiosk previews, and live session streams recheck access on their next event. Deleting a board has never published, although it hides the board from everyone but its owner; that is a known gap. The app that made a follow change refreshes its own caches. A publish goes out as soon as its write commits, before the public kiosk previews are refreshed: that refresh does its own Redis and database reads and can fail, and a failure must not hold back the invalidation. Each publish writes one `[Privacy] privacyChanged published` log line with its `source` and a per-process running `count`, so the rate per call site can be read from production logs. The stream still yields once on every subscribe: installed app bundles stamp their offline catalogue viewer marker from that first event, so removing it waits for a client release that no longer depends on it.

On an event the native app withdraws other people's projections (profiles, feeds, sessions, logbooks, comments, notifications, boards, playlists, beta and any query root it does not recognise), refetches climb search lists that are on screen without blanking them (an off-screen one, a spray wall's search, or one whose key names no board is withdrawn in full), and leaves the viewer's own profile and unsynced ticks, offline download bookkeeping, developer tools and static reference data (grade scales, angles, the popular-config rail) alone. The website withdraws every cached client query except its auth-token and privacy-settings transport queries and drops the persisted cache (which only ever holds the viewer's own profile queries). It re-renders the server markup only on pages that server-render other people's protected content (walls, sessions, profiles, playlists, setters, gyms and climb pages); other pages keep theirs. It listens on the tab's one shared realtime socket, the same one live comment threads use.

A published climb is public whatever its author's privacy settings, so a privacy event leaves a downloaded catalogue board (Kilter, Tension, MoonBoard and the other manufacturer boards) in place. Its climbs, stats, grades, pull checkpoints, completion marker and holds index stay as they are, and a sync or download in flight carries on. Spray walls are different, because access to a wall depends on privacy: native and Expo web withdraw cached spray rows and spray media on invalidation, abort a spray pull already in flight, and reset those walls' pull checkpoints and completion markers so allowed rows are fetched again. The viewer's own ticks, outbox and drafts are retained throughout. Copied first-ascent credits in downloaded stats are cleared, and stay cleared until the server sends that row again. Local reads return their unavailable fallback while the repair runs; a failed repair fails closed. Online authenticated reads and cleared query refetches continue immediately through the server, without waiting for SQLite or enriching/rescuing from withdrawn local copies. A local repair failure does not turn a successfully saved privacy setting into an apparent save failure. A persistent viewer marker binds catalogue access to a SHA-256 digest of the credential last checked against the authenticated profile API; tokens are never stored in SQLite. The same credential can use downloads offline after restart. A missing marker, another account, or a changed credential requires online revalidation. In-process invalidation epochs discard older reads even after a replacement catalogue is ready. The current viewer's rows and every queued climb reference are preserved. Another account's draft without a positive server sync sequence is retained as possible unsynced work; if those protected rows remain, local catalogue reads stay blocked while server reads continue. Downloaded foreign drafts with a positive server sequence are replaceable cache, since `is_draft` is mirrored from the server and does not identify local work; a catalogue layout that loses one rebuilds its holds index. Another account's published climbs never block local reads. In-progress editor drafts live in a separate preference store and are untouched. Revalidation replays the downloaded spray walls only; a catalogue board gets its usual delta pull from the checkpoint it already had. The bridge serializes repairs, retains one trailing repair for events received during a run, and retries a failure after 1, 5 and 15 seconds while foregrounded and online. Schema/handle availability, reconnect and foreground resume a retained failure; account or handle replacement retires obsolete attempts. Successful repair wakes the sync scheduler, so spray walls replay under the current authorization. A device that is offline cannot receive a revocation until it reconnects, and previously delivered files cannot be recalled from someone else's storage.

Native catalogue revalidation handles SQLite contention with the existing background write policy: at most three attempts with 250 ms gaps and a 20-second retry budget for each write task. Withdrawal of the persistent viewer marker completes before the authenticated profile request, including when an event arrives offline or backgrounded; authorization then waits for a foreground connection. An automatic token refresh during authorization triggers one additional profile request; only a digest stable across that authenticated response can authorize the catalogue. Credential checks also surround marker stamping and completion. A current read that finds an existing marker for an older token requests recovery; startup probes once the privacy bridge is installed so an earlier mismatch cannot be lost. Each catalogue transaction takes the immediate write lock before reading and retries on a fresh connection. Exhausted retries, non-lock errors and changed credentials keep catalogue reads blocked; personal ticks, drafts and pending mutations retain the same protection.

Solo queue persistence stores climb references, order and mirror choices, without copied climb details or attribution. Legacy snapshots are sanitized when read. A privacy or credential change retires Undo offers and older asynchronous queue work; current queue entries lose copied details until an authorized read restores them. The auxiliary playlist swipe track is cleared on withdrawal and is not persisted; reopening the playlist restores that track after checking its permissions. Drafts and the mutation outbox remain intact.

Playlist editing also withdraws copied climb details and retires outstanding edit callbacks. The active-board file stores only the selected wall reference, layout, local angle and device configuration. Names, owner details and location require a current authorized response; offline startup uses a generic board label. Privacy refresh retains the neutral wall configuration while catalogue withdrawal completes, so device pairing does not depend on copied identity details.

Kiosk previews, watch polling, session discovery and Live Activity pushes reauthorize current climb details. Quiet privacy changes withdraw copied kiosk and lock-screen content. APNs recipients are checked against current grants, and updates prepared before invalidation cannot follow the clearing push on the same server. Revoked sessions receive an empty, immediately dismissed Live Activity. The watch endpoint changes its sequence when redacting a climb and returns the existing session-ended response when session access is revoked, so installed watches clear their prior display.

Static snapshots and the board sync follow the publication rule, not the account or item audience: a published, listed climb is in every artifact and in every device's pull, whoever set it, and a draft or an unlisted climb reaches its owner alone, through authenticated sync. First-ascent names taken from Boardsesh ticks are in neither. Artifacts carry `privacyVersion: 2` in manifest/artifact format 2. Shipped format-1 clients reject this dataset and use authenticated paged sync. Old public artifacts must be removed from managed origins and CDN caches. See [the publication rule](board-snapshots.md#the-publication-rule-6306) and [dataset contract](board-snapshots-dataset.md).

Draft-climb metadata is authorized before dependent consensus stats and modeled grades. Session cards, recaps, daily ranking and grade buckets cannot derive those fields from another setter's draft; an author-entered tick grade remains the tick's own content. A send logged before its catalog climb arrives keeps the existing Unknown Climb fallback. Exact-UUID saved-climb sync suppresses both first-ascent fields for current and deleted Boardsesh authors, matching reference sync.

Privacy controls cover Boardsesh activity and account associations. Imported manufacturer setter names and first-ascent credits remain part of the external public catalog; making a Boardsesh account private does not rewrite those external credits. Independently imported manufacturer beta links follow the same rule. Both Boardsesh beta creation paths stamp the authenticated creator; upstream sync preserves that ownership on conflict, so a later import cannot turn a Boardsesh upload into an unowned public link. Reads hide the link from an external setter to a private Boardsesh account. First-ascent credits produced from Boardsesh ticks are checked against the current tick, account and resource policies before displaying an identity.

## Release sequence

1. Apply the generated migration and deploy backend/web read enforcement with `BOARDSESH_PRIVACY_ENABLED` unset. Read enforcement is always active; the flag gates settings and publication controls.
2. Regenerate format-2 privacy snapshots, replace manifests and withdraw older public artifacts and cached previews. Validate anonymous, owner, accepted follower, pending follower and removed follower reads against the primary database.
3. Ship native and Expo web clients with audience controls, cache withdrawal and privacy onboarding. Verify stale client mutations preserve restrictions and stale public drafts are rejected.
4. Enable `BOARDSESH_PRIVACY_ENABLED=1` on the backend and web account issuer after backend enforcement and artifact cleanup are confirmed. Existing users see setup once; completion version 1 is stored on their account across devices.
5. Watch denied reads, mutation errors, invalidation delivery and spray-wall replay cost. Roll back controls by disabling the flag while retaining enforcement and additive database tables; never roll back to a reader that ignores privacy.

The UI asks for an explicit Public or Private choice during setup and offers session defaults and a home-board review. Cancelling setup does not mark it complete. Settings, approvals and audience labels are translated in English, Spanish, French and German. The desktop settings page hands off to the same Expo app settings, while surviving web profiles use the same follow approvals and private activity boundary.

## Regression coverage

The database privacy matrix exercises self, accepted and pending followers, strangers, Only me, explicit Public consent and stale revisions, parent resources, comment ancestors, beta attachments, notifications and follower removal while checking aggregate retention. Separate session tests cover merges/splits, board history projection and invalidation during quiet subscriptions. Client tests cover publication revisions, cache withdrawal and snapshot compatibility; public preview and sitemap tests check current authorization rather than cached visibility.

Run the backend suites against their PostgreSQL/Redis test services. Do not run two independent backend test processes against the same database: each process resets its schema. The manual tester flows are in the worktree's `.boardsesh/qa-notes.md` and the PR test plan.

Social test tables must use the production `social_entity_type` enum. Using text instead hides PostgreSQL comparison and recursive UNION errors. The shared privacy helpers normalize incoming entity types to text because `content_privacy` also covers non-social types such as playlists and beta links. Real resolver tests cover unread notification counts, materialized activity feeds and bulk session votes with these enum columns.

The privacy matrix also covers empty inboxes, exact unread counts, read and other-recipient exclusions, aliased flat and grouped inboxes, private comment ancestors and retained ownerless policies.
