# Actual App Router and configured-provider OAuth proof

Status: locally implemented and independently reviewed, 2026-11-05. This is a test-only follow-up to [#7289](https://github.com/boardsesh/boardsesh/pull/7289), advancing BA-03 in epic #6975. No production authentication path is adopted by this proof. Publication and final documentation review follow the measured validation below; production activation remains **NO-GO**.

## Scope and decisions

This BA-03 slice is a test-only capability proof. It invokes the application's actual App Router `GET` and `POST` exports and imports its actual configured Google, Apple and Facebook provider factories. Production auth options, routes, adapter, issuers, provider registrations and environment modes are unchanged. The existing public Pages-handler proof is useful prior evidence, not evidence that this wrapper or these provider configurations have passed.

Two execution modes will be labelled explicitly in the fixture: stock characterization with guarded test database I/O, and a fixture-only compound delegate with a mutation-denying adapter. Replacing callbacks and adapters inside the isolated request's test options does not wire production delegation. The compound remains one backend-owned PostgreSQL transaction, with exact provider-subject ownership, normalized reservation admission and durable flow consumption. It never chooses an owner for ambiguous identities or implicitly links by email. Existing linked owners retain their stored email and verification state. New-user verification policy is not decided by this proof.

Provider transport substitutes only external HTTP. Google and Apple use genuinely signed synthetic ID tokens and their configured browser client IDs, with real public NextAuth/openid-client validation. Facebook uses its configured OAuth token and Graph userinfo exchange; no fabricated Facebook ID token or mailbox-verification assertion is introduced. All network access is restricted to exact owned loopback listeners or explicitly substituted provider destinations. No real provider, SMTP, telemetry or production database is contacted.

## Planned implementation and decisive tests

1. Build an owned HTTP bridge that invokes the real App Router exports and supplies only Next's ambient headers/cookies I/O. Load the real `authOptions` before capturing fixture-only request options. Preserve configured provider defaults, wrapper cookie clearing, Expo state-bound returns and public NextAuth dispatch. The bridge is not a full Next server or deployed-ingress proof.
2. Exercise Google/Facebook GET callbacks and Apple form POST using real state, PKCE where configured, nonce where configured, one-use codes and registered redirect/client checks. Assert actual issued cookie identity, creation metadata, error redirects and no unexpected adapter mutations. Characterize cancellation, failed token exchange and invalid claims without weakening configured checks.
3. Bind fixture-only initiation intent to the source actor or explicit absence independently of callback-cookie delivery. Missing Apple Lax session cookies do not prove anonymous initiation. Wrong actor, same UID/different SID, stale/deleted source, repeated state and uncertain backend outcomes fail without session publication or clearing a newer login. A same-origin continuation may recover the initiating cookie, but cannot manufacture canonical freshness or generation evidence.
4. Prove compound ownership and publication boundaries with owned PostgreSQL roles: linked subject stability, free-key signup, occupied/ambiguous key denial, durable duplicate-flow rejection, concurrent requests, late event/encoder failures and exact issuance abort. Lost committed replies leave identity intact. Fixture-created lineage is synthetic proof data, never a claimed bridge for current production cookies.
5. If installed Chromium is usable, add a real browser HTTPS transport test with distinct provider/application sites showing SameSite=None flow-cookie delivery, SameSite=Lax session omission on cross-site Apple POST, and restoration on a same-origin GET continuation. Browser transport evidence and direct route-export evidence are reported separately. If unavailable, document the exact missing gate rather than replacing browser evidence with manually selected Cookie headers.

## Compound fixture plan

This new helper lives only in `current-store/__tests__/fixtures/app-router-compound.ts`, with focused tests alongside it. The caller supplies an owned local restricted LOGIN database pool and a captured expected projection authority; the helper owns only a bounded loopback HTTP listener. It uses the existing users, profiles, accounts, sessions, verification-token and foundation tables. It adds no schema, production export, environment mode or production issuer. `issueSource` uses the public NextAuth JWT encoder to seed explicitly synthetic source credentials with original authentication time either unknown or historical; neither a new JWT issue time nor rolling encoding becomes fresh authentication.

The source proof is a readable, purpose-signed synthetic JWS carried inside the real encrypted NextAuth JWE; clients treat it as opaque. Its signed UID/SID/generation/original-deadline/age binding must match the hash-bound database record. Intent and terminal-flow records have separate integrity MACs, so rewriting stored metadata cannot retarget a cleanup to a newer source. Source lifetime is one hour only for this fixture; it is not the released web lifetime or a proposed hourly login policy. Admission intent lasts at most 15 minutes; retained intent and terminal-flow evidence outlive that admission window through the possible child-source deadline.

The four private, constant-time-bearer-authenticated POST paths are `/intent`, `/compound`, `/abort` and `/validate`. Strict request schemas, body/deadline limits, manifest-first READ COMMITTED transactions, fresh database clocks and bounded admission/drain cleanup apply to every path. The fixture captures authority and input before awaits. Hash-namespaced intent, source and consumed-flow evidence is stored in existing receipt tables, never raw cookies, provider state, passwords or raw source secrets. Intent validity is at most the existing 15-minute state window; consumed-flow evidence survives through original state and source deadlines. This is bounded replay history, not an indefinite cleanup or production retention policy.

`/intent` records the verified generated state digest with its provider and either a valid source actor or explicit absence. A present cookie must prove its exact UID, SID, original deadline and current subject generation through synthetic persisted lineage; invalid or missing source evidence never becomes anonymous intent. `/compound` accepts provider identity only after the real public handler verifies it, rechecks the durable intent actor and exact callback actor, and resolves provider subject under the common fence. The backend helper trusts that authenticated delegate's provider assertion; it does not independently repeat JWT/JWKS or Graph verification. This differs from the earlier local-OIDC backend proof and is an explicit fixture trust boundary, not backend verifier adoption. Existing linked subjects retain UID and stored profile/verification even if claims change or email is absent. Current ambiguous membership can preserve a known linked owner without selecting a different owner. Unlinked subjects with an actor are denied; absent-actor free-key creation reserves and writes user, default profile and plain unique provider link atomically. Occupied keys do not auto-link. New users retain NULL verification in this proof. New source/session and flow consumption commit with that identity transaction.

Root-approved abort extension: each verified callback generates a private UUID `attemptId` before its RPC; query/form data cannot supply it. `/compound` requires and echoes that ID, and signed source and sealed winning-flow evidence bind it. `/abort` accepts a strict union of `{sourceProof}` or `{provider, flow, actorCookie, attemptId}`. The flow form authenticates the original durable intent's exact actor UID/SID/generation or verified explicit absence and targets only that attempt's captured source hash/UID. An abort from losing callback B must acknowledge a no-op when callback A already won the same flow; even a discarded definitive 409 cannot let B revoke A.

Pre-abort uses a separate, MAC-sealed **per-attempt** tombstone binding provider, flow, attempt ID and original intent hash. A valid existing intent is required; guessed or missing intents create nothing. Pre-abort B blocks late B while A remains eligible. Once A is admitted, the separate winning-flow record consumes the flow globally. Cancellation and winner evidence remain through their original admission/source deadlines; no cleanup can reopen a still-live attempt. Abort retains identity and terminal flow evidence, never deletes an account, and cannot clear a newer or sibling source. Repeated exact abort is bounded and idempotent.

Historical flow abort is negative authority only: its sealed intent includes the hash of the exact cookie authenticated at initiation. A constant-time match can clean up that flow after the initiating outer JWE expires, without treating it as a current actor. Intent creation, compound admission, validation and new issuance still require current eligibility. A different cookie, including a newer SID for the same user, cannot use this cleanup path. Missing retained intent for a known terminal flow returns unavailable and leaves the issuance intact rather than inventing evidence. The regression crosses the real pinned public decoder's expiry tolerance, then proves ordinary admission is denied while exact cleanup succeeds and another issuance survives.

Completion guarantees are deliberately separate: the wrapper can withhold a usable published cookie after uncertain compound completion; a reachable, acknowledged exact abort can revoke that issuance. If compound acknowledgement and abort delivery are both uncertain or unavailable, the fixture cannot promise physical inactivity. Tests cover A committing, B discarding its real 409 response, B's uncertain abort preserving A, known late-failure A abort, pre-abort B with A still eligible, lost compound reply followed by reachable exact-attempt abort, lost abort reply/repeated abort, wrong actor, same UID/different SID and newer issuance preservation. Additional focused PostgreSQL cases cover replay races, exact subject ownership, ambiguous/free keys, immutable source bindings, expiry/generation/deletion and atomic SQL-fault rollback. A separate independent security reviewer reviews this contract, implementation and fixes before final execution evidence is recorded.

### Focused compound validation

The final per-attempt helper selection passed **29/29 on owned PostgreSQL 18 in 14.53 seconds** (8.97 seconds in test bodies), and independently **29/29 on PostgreSQL 15 in 14.14 seconds** (8.82 seconds in test bodies). It uses a separately authenticated, nonowner LOGIN pool and existing generated test tables; owned roles, listeners and pools close cleanly while ordinary salted worker databases remain. Both new TypeScript files passed selected format/lint/type checks with zero warnings or errors. The qualifying backend task passed all **13 tasks, with 11 cache hits**. The independent reviewer approved the final helper and focused tests after re-reviewing historical abort, per-attempt isolation, retained evidence and exact SQL-fault assertions. Earlier 27-case checkpoints predate attempt isolation and are not final evidence for it; overall wrapper/browser review is separate.

The winning-A regression captures the exact persisted session row and source hash/SID, discards B's real 409 response body, sends B's attempt-bound abort and asserts A's row is unchanged and its original cookie still validates. It then acknowledges A's own abort and confirms identity and terminal-flow evidence remain. Separate pre-abort and concurrent cases show B's cancellation marker survives legitimate expired-row cleanup, rejects late B and leaves A eligible. This direct helper selection does not itself run the full App Router or lose a response before headers; the separate parent-owned wrapper/proxy tests establish their own transport boundaries.

The expiry case uses the real public NextAuth encoder/decoder and its pinned 15-second tolerance: an initiating JWE is accepted inside that window, then a real wait crosses it. Current validation and new intent reject it, while the sealed exact-cookie hash permits only the matching historical cleanup; another source remains valid. No application or database clock is faked. Tampered intent, terminal and source-generation/deadline metadata fail closed. A real profile CHECK violation is observed as SQLSTATE `23514` with the exact fixture constraint, and user/reservation/profile/link/source/winning-flow writes roll back before a fresh retry.

## Boundaries that remain closed

Production web OAuth still uses its existing direct Drizzle adapter, dangerous email auto-link option, verification update and profile event writes. Adopting a compound delegate must replace those together. This proof does not activate another writer, create production source receipts, validate old-cookie revocation history, migrate authority, establish IAM fencing, resolve existing collisions or enforce cutoffs across current validators/issuers.

Authenticated password set/change is not part of this slice. The current set-password endpoint has only a legacy session UID; keeping the requesting device requires genuine source SID/generation and original authentication-age evidence. The reviewed canonical Better Auth continuation cannot be transplanted by treating a JWT issue time or legacy `authSessionId` as that evidence.

### Provider fidelity and observed stock behavior

The actual configured Google, Apple and Facebook factories are loaded with fixture credentials. Their installed client paths validate synthetic RSA signatures/JWKS, issuer, audience, expiry and state for Google/Apple; the configured clients and local provider also exercise PKCE. These options configure no nonce check. Facebook uses its actual Graph userinfo path rather than a fabricated ID token. Returning linked subjects without email retain their owner. Stock characterization records the existing dangerous exact-email auto-link behavior and the second Facebook login's verification mutation without a provider verification claim. These are counterexamples to preserve as migration requirements, not behavior endorsed by this proof.

Independent review found that an initially generic discovery document selected Basic authentication for Apple. [Apple's public discovery](https://appleid.apple.com/.well-known/openid-configuration), checked 2026-11-05, advertises POST client authentication; the final fixture advertises only that method, rejects an Authorization header at its token endpoint, and asserts the actual observed POST method. Its synthetic client secret does not prove Apple client-secret JWT validation or a real provider registration.

[Google's public discovery](https://accounts.google.com/.well-known/openid-configuration) advertises authorization-response issuer checking. The final fixture includes that flag and the callback issuer; separate missing/wrong callback-issuer cases fail before any additional token request. They are independent from invalid signed ID-token issuer cases. Apple pairwise subjects and supported response modes follow its public metadata; discovery advertises PKCE methods only for Google. The local provider enforces S256 when the configured client sends it; this does not establish the real vendor's PKCE acceptance or production provider configuration. Public metadata was read separately for fixture fidelity; test exchanges contact only owned listeners.

The actual wrapper's Google/Apple Expo state-bound return and creation metadata, Apple cancellation, and chunked encrypted-session cookies are covered. The fixture's compound-precreated user makes stock NextAuth report `isNewUser=false`; an explicitly fixture-only receipt projection supplies the expected creation metadata. This proves the required seam, not an existing production receipt implementation.

### Browser transport and fixture-only continuation

The stock real-browser case uses distinct application/provider sites (`localhost` and `127.0.0.1`). The actual Apple POST sends SameSite=None state/PKCE cookies while omitting the seeded Lax session cookie. Stock processing replaces that browser login with the other subject's already-linked account. This shows why callback-cookie absence cannot establish anonymous initiation; it does not approve a new account-switch or linking policy.

The other three browser cases use an explicitly synthetic continuation. The bridge holds the Apple form POST for at most 60 seconds and sends a same-origin GET; that GET restores the browser's Lax cookie before a reconstructed callback invokes the real handler. A matching actor succeeds and retains its historical authentication age. A provider subject owned by someone else, or a same-user/different-SID callback actor, fails while preserving the current browser cookie. Negative cases require both actual compound-call counters and the unavailable response body, so an unrelated early failure cannot masquerade as actor validation.

Browser provider I/O is substituted only after the actual sign-in response is produced: its official provider Location is checked, then mapped to an owned provider page serving a real HTML form. The original Set-Cookie array is forwarded unchanged by Node, with byte-equality assertions. No Playwright API-request cookie jar or response fulfillment participates. Browser request allowlists and an external-DNS deny remain active. These are real browser cookie/redirect observations around a route-export bridge, not a full Next server, real Apple UI, Safari/iPhone, deployed ingress or production continuation service. In-memory continuation/intent state, distributed routing, restart behavior and production secret handling still require separate adoption work.

Four earlier browser runs failed before this transport was established. The doubtful assumption was that Playwright routing intercepts every redirect hop. The installed 1.62.1 public type documentation says only the first URL is intercepted in such a chain; attempting `route.fetch` also shared the browser context's API cookie jar. The final owned HTTP bridge removes both assumptions without raising the overall timeout or weakening the cookie assertions.

### Review fixes and publication boundaries

Independent checking caught and resolved a narrow TypeScript environment-input mismatch. A later PR review correctly identified that requiring GitHub markers for the standard port broke ordinary local backend tests. Normal suites now accept the repository's loopback test service on port 5433 as well as the separately owned 15475/15478 services, while retaining exact fixture-role, password and worker-namespace checks; CI impersonation is unnecessary. This session still runs actual database I/O only against the separately owned ports. The explicit browser config remains opt-in and validates its required owned admin URL before the normal test infrastructure runs, preventing an accidental shared-port startup in this workspace.

The first concurrent App Router compound batch exposed a losing callback revoking the winner. Classifying an acknowledged denial alone was insufficient: a discarded denial also makes the losing caller uncertain. The final private per-callback attempt ID, matching response echo, sealed winner receipt and separate aborted-attempt tombstone now distinguish those callers. The real discarded-409 regression preserves the winner's usable source. A received committed 200 body can also be discarded: the wrapper withholds its cookie, reaches an exact-attempt abort, retains the identity and preserves a sibling source. A private listener closed after intent registration preserves the original login and records unavailable cleanup. These are their stated received-body/closed-listener boundaries, not a claim to reproduce every pre-header network failure.

Real late event/encoder failures, security-generation changes and deletion before encoding deny publication in the tested windows. The reset-style barrier case commits a real security mutation, cutoff and event; it does not change a password or execute the public recovery flow. The separate recovery slice establishes actual reset atomicity. The deletion barrier case actually removes its owned fixture user. Every source validator and publisher is still fixture-only. Current production session reads, password/credential paths, native transfers, refresh, caches and WebSockets have not acquired this synthetic source validation. A process or network outage that prevents acknowledged cleanup can leave stored issuance evidence; no arbitrary-outage physical-revocation guarantee is made.

The second frontend reviewer caught a malformed-cookie classification gap: a bare reserved session-cookie name without `=` was truncated before classification and could look like anonymous initiation. The final parser classifies the raw reserved name first and fails closed. Actual sign-in requests carrying valid CSRF plus each bare secure/unsecure name must create no intent, identity or published cookie. This is a fixture correction; production routing is unchanged.

Both independent reviewers approved the frozen source and re-reviewed the fixes; the primary reviewer also completed the final PG15 selections. The post-fix aggregate typecheck passed. Final documentation review confirmed these scopes, measurements and remaining activation gates without an actionable finding.

### Reproducing the explicit browser proof

The normal `.test.ts` cases run in the backend project. The browser file deliberately uses `.proof.ts`, so ordinary backend CI does not select it or imply Chromium is installed. Its committed config requires an owned local test cluster and an installed Playwright browser; an explicit run without them fails.

```sh
BOARDSESH_AUTH_PROOF_DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:15478/boardsesh_backend_test \
  vp test run --config packages/backend/auth-proofs/app-router.vite.config.ts --reporter=agent
```

Use the separately owned PG15 cluster on port 15475 for the second database run. The config uses the owned test Redis listener on port 15476. These addresses are test-fixture contracts, not production connection settings.
