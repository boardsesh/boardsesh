# Staged web password delegation to the current backend store

This implementation-only BA-03 slice moves web registration and password verification together behind a default-off staging mode. It does not switch authority to Better Auth, migrate identities or complete the single-writer boundary. Production activation remains **NO-GO**.

## Contracts and ownership

`CURRENT_STORE_WEB_AUTH_MODE` defaults to `legacy`. Only the explicit `backend-staging` value selects delegation. Default-off mode does not require the new service secret, backend address, projection metadata or SMTP changes. A malformed enabled configuration, disabled backend, timeout, redirect or malformed reply cannot select legacy DB access or bcrypt as an availability fallback.

Enabled backend mode rejects `DEBUG_SQL=true` before command work because the shared database logger prints SQL bound parameters. Default-off mode still tolerates that flag. This is an explicit staging configuration guard, not a claim that production logging or observability has been independently audited.

| Setting | Owner and requirement in enabled mode |
| --- | --- |
| `CURRENT_STORE_WEB_AUTH_MODE` | Both services: explicit `backend-staging`; absent/empty/`legacy` retains the existing paths. |
| `CURRENT_STORE_AUTH_BACKEND_ORIGIN` | Web only: pinned origin, HTTPS except owned local development/test loopback. No public WebSocket fallback. |
| `CURRENT_STORE_AUTH_RPC_SECRET` | Both: at least 32 UTF-8 bytes, no surrounding whitespace, distinct from NextAuth and cron secrets. |
| `CURRENT_STORE_AUTH_PROJECTION_ID` | Backend: exact already-enforced projection ID. Configuration cannot create/enforce it. |
| `CURRENT_STORE_AUTH_WRITER_EPOCH` | Backend: exact positive writer epoch of that projection. |
| `EMAIL_VERIFICATION_ENABLED` | Backend password policy: only literal `true` requires verification. |
| `BASE_URL` / `NEXTAUTH_URL` | Web mail link origin: configured trusted canonical origin; only owned local development/test fallback is allowed. |

These values describe implementation prerequisites, not instructions to activate a deployment. The actual writer-role/issuer fence is a separate prerequisite that environment values and the enforced marker cannot establish.

The shared `@boardsesh/auth-protocol` package describes the two private POST commands, metadata and strict replies. It contains no credential policy, database code or secrets. The web client is server-only, uses a pinned configured backend origin and a distinct RPC secret, and correlates operation and request ID. Browser cookies, NextAuth secrets and native access tokens do not authorize these private commands.

The backend owns user, password, profile, normalized reservation, verification-token and command-replay writes. Every active command requires captured enforced projection metadata; that marker is a software prerequisite, not proof of a production role fence. No production activation or projection-building API is added. The bounded actual-role fixtures establish local test privileges only.

Web registration retains its existing Zod field bounds and raw validated name. It does not use the native parser's trimming or name normalization. Since BA-02 PR 2 it stores the address through the shared JS normalizer, the same form the reservation key uses. A trusted backend command generates the new user ID, reserves it and uses the existing bcrypt12 and identity inserts inside the same transaction.

Password sign-in uses the shared BA-02 address rule (`resolveAccountEmail` in `@boardsesh/auth-protocol/account-email`, read through `accountEmailCandidates` in `@boardsesh/db/queries/account-email`): rows storing the typed text exactly win; with none, the one row storing it in other capitals is used; several such rows name nobody and the sign-in is refused. It shares the native bounded comparison engine, checks every admitted hash and accepts exactly one matching owner. It does not retain the web route's arbitrary first-row choice for duplicate exact addresses. Native's existing LOWER-only lookup, bounds, dummy comparison and response contracts remain unchanged.

## Verification and mail compatibility

The password result carries the selected immutable user ID and that user's verification verdict. Request-local NextAuth options consume it without querying by email again. Neither a browser boolean nor another request's result can authorize sign-in. Invalid credentials remain separate from retryable service unavailability.

Registration's private mail plan contains the exact committed `users.email` as both recipient and legacy verification identifier. Since BA-02 PR 2 that committed address is the normalized form. The UUID token and its original 24-hour deadline commit with identity creation. Public registration JSON manually projects only the existing message, `requiresVerification` and conditional `emailSent` fields; it never proxies private mail data or user IDs.

Web retains the existing SMTP delivery adapter and template in this slice. Delivery occurs after the backend commit, and failed delivery retains the created account/token and the current successful-registration response. The mail plan must never enter browser JSON, NextAuth user/session/JWT metadata, logs, Sentry or exception text. Active mail delivery requires a trusted canonical origin or validated owned local origin; caller Host/body values cannot choose a credential-link destination.

The existing SMTP implementation remains unbounded. A bounded RPC request does not bound or cancel the subsequent SMTP send. This compatibility choice is not production-ready mail operations. Backend SMTP migration and hard cancellation require separate configuration evidence and an owned hung/drip-socket proof.

The current verification and resend consumers are still email-keyed, and verification can update multiple matching users. These are legacy tokens, **not UID-bound verification proofs**. Verification-enabled production activation remains blocked until a compatible UID-aware consumer/resend path or equivalent reviewed binding is implemented. Issued legacy links must remain safely usable for their original lifetime.

## Transactions, replay and races

An authenticated web server generates a fresh command request ID and timestamp; browser input cannot select an account ID, verification policy or token. A purpose-namespaced hash-only replay record in the existing no-users-FK `verificationTokens` table commits atomically with each authoritative outcome. Its retention exceeds the original timestamp's whole acceptance window plus skew and request budget. A committed request cannot be acknowledged again during that lifetime; after expired-record cleanup, the original timestamp remains rejected. This is bounded replay protection, not unbounded idempotency history: a trusted caller must never re-date or reuse an old ID. No automatic registration retry or idempotent success receipt is introduced. A lost reply may mean creation committed; it cannot authorize compensating deletion, a repeated success claim or an overwrite.

The backend's one-minute maintenance job (`background-job-reconcile`) deletes expired `ba03-web-auth:` records, at most 5,000 a run, in every mode, so records a staged mode left behind still go after it is switched off. With none it is one empty read. A prefix `LIKE` cannot use the text primary key under the production `en_US` collation, so each run reads the whole table: 32 kB on 2026-11-11, which is negligible. A much larger table would need a prefix index (`text_pattern_ops`) on `identifier`. It runs outside the commands because their database role may be append-only on this table. The same run removes deleted-address digests 90 days after the deletion.

Bcrypt comparison runs with no transaction open. The backend then takes the shared authority gate, validates the manifest, locks every `users` row the bounded address rule could name (the typed text and its other capitals, BA-02) `FOR KEY SHARE` in `users.id` order and, in a later statement, re-reads them, applies the same rule and rechecks every member's credential hash and cutoff generation before accepting. KEY SHARE excludes every credential writer, which takes `users FOR UPDATE` first, but not the foreign-key lock of a logbook sync page, so a sign-in never waits for one (BA-04 PR 3). Verification is read from the current selected user row. Serialization/deadlock failures are unavailable; code cannot continue with a stale comparison result. Unfenced old writers are not claimed to participate, and their phantom inserts or other bypasses remain an activation blocker.

The reply is a one-request UID/verification snapshot. It is **not an ongoing source credential or proof that later cookie publication is revocation-safe**. Reset after a successful backend verdict and before NextAuth JWE encoding can still produce an accepted cookie through existing validators. This slice does not add an unused signed lineage claim or claim to close that race. Backend-owned issuance lineage, every validator/cache, renewal and legacy writer adoption must close it before production activation.

## Web behavior and remaining gates

Both password entry points select the same mode. The NextAuth route records request-local unavailability before the library catches an authorization exception, preserves existing session cookies and returns a safe retryable result. Both login forms distinguish the allowlisted unavailable code from rejected credentials and use the existing retry message; errors and analytics never reflect raw backend messages or URLs. Registration success and subsequent auto-login failure remain separate outcomes.

The private controller clamps a rate-limited reply to a minimum one-second delay for both JSON and `Retry-After`. The shared limiter can report zero exactly at its reset boundary; this local adaptation preserves the strict protocol without changing the existing limiter's behavior elsewhere.

In staged mode the credentials callback allows each client 10 rejected passwords a minute before it reaches the backend, which applies its own limits on top ([Backend sign-in limits](#backend-sign-in-limits)). A client over its limit gets a 429 with `Retry-After` and the existing retry message. The key comes from `trustedClientRateLimitKey`: `CF-Connecting-IP` when the last `X-Forwarded-For` hop is a Cloudflare edge, otherwise that last hop, with IPv6 grouped by `/64`. Once `CLOUDFLARE_ORIGIN_PROOF_SECRET` is set, a Cloudflare last hop counts only with our zone's proof; without it the key is that hop. An edge request with no usable visitor address goes into one fixed bucket, whichever edge address carried it. Earlier hops are caller-written and never used. The limit is per web instance.

Only rejected passwords use up the 10. Each attempt is counted before NextAuth reads the body and given back when the password is right, so a parallel burst cannot all pass before any is counted, and a climber who signs in often is never limited. The limit runs before the submitted address is read, so the 429 is the same for every address.

Legacy mode applies the same limit and the same 429, because there every attempt runs bcrypt on the web process itself: about 200 ms each, unknown addresses included, so about 5 attempts a second from one client would fill its event loop. It keys only on a visitor a Cloudflare edge vouches for (`cloudflareVisitorRateLimitKey`: the last hop is a Cloudflare edge and `CF-Connecting-IP` is usable). With no such visitor it skips the limit and logs a warning at most once a minute. Once `CLOUDFLARE_ORIGIN_PROOF_SECRET` is set this changes: a request without our zone's proof is keyed on its last hop (or `unknown`) and never skips the limit, because real visitors carry the proof; only a proven request with no usable Cloudflare visitor still skips it. `trustedClientRateLimitKey` would instead return a value every caller can share there (`unknown`, the fixed edge bucket, or our own ingress's address if the web ingress appends that), which would cap the whole site at 10 rejected passwords a minute; the web side of requirement 1 below is not yet checked. If the warning shows up in production logs, www sign-ins are running without the limit. `register`, `verify-email`, `reset-password`, `forgot-password` and `resend-verification` use the same key in staged mode.

Two requirements hold before any staged mode is enabled:

1. Verify in production that the ingress appends the peer it observed as the last `X-Forwarded-For` hop. If it stops doing that, honest clients share one bucket while a forger can pick its own last hop, and by picking a Cloudflare address can pick its `CF-Connecting-IP` too. Checked for the backend on 2026-11-10 from Railway's network flows: its ingress peers are Railway edge IPv6 ULAs inside `fc00::/7`, which `isPrivatePeerAddress` trusts, so the backend's `getTrustedClientIp` reads the appended hop. The web service sits behind the same Railway edge; repeat the check against it before enabling a mode.
2. **Hard gate: the origin proof is live.** A last hop in Cloudflare's ranges proves only that the request crossed some Cloudflare edge. A Worker on any Cloudflare account that fetches the web's Railway domain leaves from a Cloudflare address, and for a destination that is not a Cloudflare zone Cloudflare lets the Worker set `CF-Connecting-IP` itself, so it could choose the address every limit keys on. The code check is built (`originProof` in `trusted-client-ip.server.ts`): a transform rule on our zone sets `X-Boardsesh-Origin-Proof` to a secret that the web holds as `CLOUDFLARE_ORIGIN_PROOF_SECRET` (at least 32 bytes, compared in constant time). Do not enable a staged mode until the rule and the variable are both set and checked, as in [Turning on the origin proof](#turning-on-the-origin-proof). #7766 tracks it.

Native login, staged web login and legacy web login all compare an address with no password against `ABSENT_PASSWORD_HASH` from `@boardsesh/auth-protocol/password-hash`, a fixed cost-12 hash. Every stored hash is cost 12 and none is ever rehashed, so a rejection takes as long whether or not the address has an account. New hashes are written at `PASSWORD_HASH_COST`, also 12. The two must stay equal until every stored hash is rehashed: raising only the write cost would leave old accounts cheaper to reject than unknown addresses. Legacy web login reads the user and its password hash in one joined query, so an unknown address, an OAuth-only account and a wrong password do the same database work before bcrypt. Until 2026-11-11 native login used a cost-10 stand-in against cost-12 stored hashes and answered an unknown address in about 50 ms against 198 ms for a wrong password, which showed which addresses have accounts.

OAuth linking, recovery, verification/resend, password set/change/reset, deletion, native/watch issuance and other credential writers remain later work. Production writer roles, service authentication, canonical origins, SMTP, collision handling, rollback and validator adoption remain unverified activation prerequisites. No production traffic, environment configuration, migration activation or identity reassignment is authorized by this slice.

## Backend sign-in limits

Until #7589 the backend's password command (`/api/internal/auth/current-store/password`, `handlers/current-store-web-auth.ts`) had one budget of 180 attempts a minute per process. Eighteen clients (IPv4 addresses or IPv6 `/64`s) at the web's 10 rejected passwords a minute each used it up, and then every email sign-in on that replica failed.

**Per-client limit.** A sign-in that carries a public client address now counts against that client only: 10 rejected passwords a minute, IPv6 grouped by `/64`, held in Redis so every replica shares it (`auth/current-store/password-login-limits.ts`). Such a sign-in does not touch the per-process budget. Each attempt is admitted by one Redis script before any database read: the script refuses when the client's minute already holds 10, otherwise it adds the attempt to the minute. A refused attempt is never counted, and a parallel burst cannot pass together: 15 at once from one client get exactly 10 compares. Each attempt is a field of the minute's hash, named by a random ID, so giving one back is an exact `HDEL`. Only a rejected password stays counted. A right password, a replay, a shed or abandoned compare, and a reply with no verdict all give the attempt back. The minute is fixed and aligned to the clock, and its key expires when the minute ends. A 429 carries the seconds left in the minute as `retryAfterSeconds` and `Retry-After`. The limit reads nothing about accounts, so an address with no account is counted and refused exactly like one with an account, and the 429 is identical.

**What the backend trusts as the client.** The backend's peer on this route is the web server, so it cannot see the visitor. It keys the per-client limit on the optional `clientAddress` field of the password command (`@boardsesh/auth-protocol`). The field must be a bare IPv4 or IPv6 address; anything else gets a 400. The backend believes it only because the command carries the `CURRENT_STORE_AUTH_RPC_SECRET` bearer, which only the web server holds.

**No usable client address.** A missing address, or one that is private, loopback, link-local or carrier-NAT (`reportedClientLimitKey`), is an ingress or a test harness, not a visitor. Keying on it would put every visitor in one bucket. Such a sign-in instead takes main's per-process budget: 180 a minute, every attempt counted, nothing given back. It is no weaker than before this change. Each one is counted (`passwordLoginMetrics`), and a `type: password_login_metrics` warning is logged at most once a minute with the count since the last one, so a misconfigured web side shows up in the logs.

**What the web sends.** The web sends `clientAddress` only when our own Cloudflare zone vouches for the visitor (`cloudflareVouchedVisitorAddress` in `trusted-client-ip.server.ts`): the last `X-Forwarded-For` hop is a Cloudflare edge, the request carries the right `X-Boardsesh-Origin-Proof`, and `CF-Connecting-IP` is a usable address. It sends that address whole; the backend groups IPv6 by `/64`. In every other case, including always while `CLOUDFLARE_ORIGIN_PROOF_SECRET` is unset or shorter than 32 bytes, it leaves the field out and the sign-in takes the per-process budget, as before #7589. An address the command schema would refuse, such as one with a zone index, is left out too, so it cannot turn a sign-in into a 400.

Production reaches the web as browser, Cloudflare (www is a proxied record), the Railway edge, then Next. A caller can also skip our zone and use the Railway domain directly, from an ordinary address or from a Cloudflare Worker:

- **A Worker on any Cloudflare account** reaches the Railway domain from an address inside Cloudflare's ranges and may write its own `CF-Connecting-IP`. Without the proof header it never gets a `clientAddress`. A Cloudflare last hop alone is not trusted.
- **An ordinary direct caller.** If the Railway edge appends the peer it saw, the caller's last hop is its own address, so nothing it writes is believed. If the edge appends its own address instead, no last hop is a Cloudflare edge and the web never sends `clientAddress`. Requirement 1 above is still not checked for the web service.
- **#7589 stays open for traffic that skips our zone.** Such sign-ins carry no `clientAddress`, so they all share the backend's 180-a-minute process budget. Eighteen direct-origin addresses at the web's 10 a minute can still use it up on a replica. That is the fail-closed choice: no caller can pick its own bucket.

#### Turning on the origin proof

Order matters: the rule first, then the variable. While the variable is unset, the web ignores the header and every limiter behaves as before.

1. Generate a secret of at least 32 bytes, for example `openssl rand -base64 48`. Keep it in the team password manager.
2. In the Cloudflare dashboard for `boardsesh.com`: Rules, Transform Rules, Modify Request Header, Create rule. Name it `boardsesh:origin-proof (owner-managed, holds a secret)`. Expression: `(http.host eq "www.boardsesh.com" and http.request.uri.path contains "/api/auth/")`. Action: Set static, header `X-Boardsesh-Origin-Proof`, value the secret. `contains` rather than `starts_with`, because middleware rewrites locale-prefixed paths such as `/es/api/auth/callback/credentials` to the same handlers. `vp run cf:apply` keeps rules it does not declare, so it leaves this one alone; it is not in `infra/cloudflare/config.ts` because that file holds no secrets.
3. On Railway, project production, service `boardsesh-web`: set `CLOUDFLARE_ORIGIN_PROOF_SECRET` to the same secret and redeploy. `infra/railway/config.ts` declares it by name only.
4. Sign in once through www. Then confirm the web service's log shows no `cloudflare_origin_proof_missing` warning for 10 minutes. That warning, at most once a minute with a count of unproven checks since the last one, means a request with a Cloudflare last hop arrived without the right proof: the rule is missing, misses a path, or holds another value. A Worker or another zone fetching the Railway domain also raises it, so an occasional one later is not by itself a fault.

**Rotation, with no gap.** Set `CLOUDFLARE_ORIGIN_PROOF_SECRET_NEXT` on `boardsesh-web` to the new value and redeploy; the web now accepts either. Change the Cloudflare rule's value to the new one. Then set `CLOUDFLARE_ORIGIN_PROOF_SECRET` to the new value, unset `CLOUDFLARE_ORIGIN_PROOF_SECRET_NEXT`, and redeploy.

The proof header never reaches Sentry: the web's server and edge configs delete it from every event, transaction and span (`redact-origin-proof.ts`), because `sendDefaultPii: false` still keeps request headers.

Once the variable is set, the existing limiter keys require the proof too (#7766). A request without it is keyed on its last hop, or on `unknown` with no hop, by `trustedClientRateLimitKey` and `cloudflareVisitorRateLimitKey` alike. The legacy sign-in limit therefore never skips it, whatever path it used or header it left out.

**Redis unavailable.** When Redis is not connected, or does not answer within 100 ms, each replica counts in its own memory against the same 10 a minute, as the backend's other Redis limiters do, rather than refuse every sign-in. With several replicas, a client can then get 10 rejected passwords a minute from each. The memory table empties when the minute turns and never evicts a client early. Once it holds 50,000 clients in a minute, a new client gets no place and takes the per-process budget instead, so spraying addresses cannot push out a client already being counted. A slow Redis may still run an admission whose answer missed the deadline, so that attempt's give-back also removes its field from Redis. A right password is therefore never left counted there. A give-back that cannot reach Redis leaves the attempt counted until the minute ends.

**Password compares.** bcryptjs is plain JavaScript on the event loop that also serves every WebSocket. A cost-12 compare takes about 200 ms on a 2026 laptop, in slices of up to 100 ms, and compares running at once stack their slices. The password command therefore runs one sign-in's compares at a time per process, one after another (`auth/current-store/password-compare-gate.ts`). That includes the stand-in for an unknown address, and all the compares for an address several accounts share (`password-identity.ts`, up to 8) in one slot. The shared address is never partly shed, and load cannot answer it 503 where an unknown address would get `invalid_credentials`. Waiting sign-ins form one FIFO queue of at most 16. A sign-in that arrives to a full queue gets a 503 `unavailable` reply with `Retry-After: 3` before any Redis key or database read. So does a sign-in that waits more than 2.5 s, well inside the web server's 8 s give-up; it never runs its compares. A sign-in whose caller disconnects while it waits leaves the queue without running its compares. Each such attempt is given back. The process throughput is the same as unqueued, about 5 compares a second, because a process has one thread to compare on.

This gate covers the staged web password command only. Registration, password reset and set-password hashes and every native compare still run beside it, so the event loop can still see several bcrypt slices at once.

**What this does not cover.**

- **Per-account guessing.** There is no per-account limit. A per-address cap, checked before the compare, would refuse the right password too. It would let one client hold several climbers' email sign-in shut indefinitely, and a password reset would not clear it. Native sign-in has no such cap either, so it would block no guessing while adding a denial of service. Guessing one account from many clients needs its own design, such as device recognition or a challenge, applied to native as well.
- **The other six commands.** `register`, `verify-email`, `resend-verification`, `forgot-password`, `reset-password` and `set-password` keep the per-process backstop: 60 a minute for registration and 180 for the rest.
- **Native sign-in.** Native keeps its per-instance socket-address limit and runs its compares outside the gate.
- **Capacity.** The legitimate peak sign-in rate is unmeasured, so whether one compare at a time per process with a queue of 16 is enough at peak is unknown.

`auth/current-store/__tests__/web-password-limits.test.ts` covers this over real HTTP, PostgreSQL and Redis:

- 21 clients use up their limits (210 rejected passwords, more than the old budget), and another climber still signs in.
- A parallel burst from one client gets exactly 10 compares.
- A right password is never counted, and an address with no account is limited like one with an account.
- Two instances share the limit.
- Sign-ins without a usable client address take the 180-a-minute budget, and the metric records them.
- With Redis not connected, each instance counts alone. With a Redis that never answers, each attempt still finishes in under 1.5 s. A late Redis answer is taken back from Redis.
- A full queue sheds before any Redis key is created.
- A wait past its deadline gets 503 with `Retry-After` and its attempt back.
- An abandoned sign-in never runs its compare.
- A shared address takes one slot and is never partly shed.
