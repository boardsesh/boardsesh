# Canonical browser to native handoff capability proof

This is a disposable BA-01 capability proof for [#6976](https://github.com/boardsesh/boardsesh/issues/6976), within [the accepted migration](better-auth-migration.md). No production callback, native endpoint, credential writer, client, or schema changes. The current released browser producer and legacy verifier remain unchanged.

`packages/backend/src/auth/prototype/canonical-handoff.ts` exposes two explicitly named prototype POST endpoints. `/prototype-canonical-handoff/issue` requires a genuine canonical Better Auth cookie. `/prototype-canonical-handoff/exchange` accepts the released clients' body `{ "transferToken": "…" }` and returns the existing `{ userId, jwt, refreshToken, expiresAt }` native pair through `createPrototypeNativeFacade`. Clients treat the transfer token as an uninterpreted string. The new token is a signed JWT with readable claims, not an encrypted token. Its format changes; this does not make mixed old and new server deployments compatible.

## Source and purpose binding

1. The issue operation acquires the common PostgreSQL lifecycle advisory fence `(6975, 1)` and runs a transaction-bound Better Auth authority. Its public `sensitiveSessionMiddleware` rereads the authoritative cookie session. This middleware establishes session validity, not freshness. A joined user/session lookup additionally checks the exact session ID, user ID, canonical token, expiry, and trusted revocation generation. No public request field supplies an owner or source session.
2. One captured `Date` determines issuance and exactly 120,000 milliseconds of expiry. The signed HS256 JWT has a dedicated synthetic handoff key, explicit `typ`, issuer, audience, version 1, purpose `canonical-browser-native-handoff`, source session ID, user subject, generation, random 256-bit nonce, and exact millisecond bounds. Standard JWT `iat` floors the captured issuance and `exp` rounds the exact expiry up to the enclosing second; redemption also checks the signed millisecond deadline and receipt, with **zero expiry grace**. Those standard rounding fields do not extend the 120-second acceptance horizon.
3. The existing disposable `verification` table stores a SHA-256 token identifier and immutable receipt metadata: purpose/version, owner, source session ID, generation, nonce hash, exact issuance/expiry, and nullable consumption time. Neither the exchange token, raw nonce, nor canonical cookie/token is persisted in the receipt. No schema or dependency is added. The synthetic handoff key is copied before awaits, must contain at least 32 bytes, and must differ from the native signing key. No legacy verification key is read by this adapter.
4. Cookie-less native exchange acquires the same fence through the existing native facade's `withIssuanceTransaction`. It verifies the signature and strict claims, locks the matching receipt, checks exact unused receipt metadata, and rechecks that **the same canonical source session** is still live and eligible. An optional valid canonical cookie must match both the user and exact source session ID and itself remain eligible. Another user's cookie or a different live same-user login rejects without consuming the receipt or minting credentials. This is a deliberate stale-tab choice: a browser that moved to another canonical login starts a new handoff, even when the account ID stayed the same. Cookie-less native exchange remains valid while the original source is live; token-only exchange does not require a browser cookie.
5. Consumption and the existing native issuance run in one SQL transaction. Every unsuccessful HTTP result rolls back both; pending auth cookies are stripped. Actual global and caller-plugin after-hook `APIError` denials return 403 in this handoff path and are independently covered; no provider-redirect status behavior is assumed here. A response becomes available to the caller only after commit. A translated failure after actual native mint restores the unused receipt, source expiry, and refresh state, and returns no native pair. A successful commit followed by lost network delivery is consumed permanently: retry rejects, and a still-valid browser session must start another handoff.

Receipts retain their consumed tombstones in the bounded proof database. Deleting an expired receipt would fail closed because exchange also requires that receipt. A production retention and indexing policy remains adoption work. SHA-256 hashing is appropriate here because tokens/nonces are high-entropy credentials, not passwords.

## Authentication age and security mutation

This is an ordinary session transfer, not password verification, provider authentication, or a freshness upgrade. It creates **no new canonical session**. Existing old sessions remain old. Actual unknown-age legacy bridge sessions retain epoch creation, null original authentication time, and their lineage; native access tokens omit `auth_time`. Existing proven authentication time remains unchanged through handoff and refresh. The existing native facade extends the accepted native session/refresh lifetime to its established 90-day policy; that does not change authentication age or make sensitive session APIs usable.

Reset, source signout, account deletion, source expiry, and generation changes prevent redemption. Exchange cannot fall back to another session or recreate a revoked source. If exchange commits first during reset, logout, or deletion, that mutation removes the source and its native refresh descendants; returned access and refresh credentials then reject. If reset commits first, a waiting exchange rejects. Expiry is checked after waiting for the fence.

The user's 2026-11-04 decision keeps the current device signed in after authenticated password set/change using a **new** canonical session, while revoking the original session and all other credentials. Both real lifecycle operations are exercised here: previously issued handoffs/native pairs reject; a new handoff from the replacement cookie succeeds with the new generation and preserved original authentication time. Forgotten-password reset still removes that continuation. A genuinely new canonical password login after reset can issue a handoff. The old source-less legacy transfer remains denied after security mutation, even with newly rolled issuance timestamps. Its verifier is unchanged.

## Pinned supported APIs and source

The proof uses exact Better Auth 1.7.17, its public exports, the real Drizzle adapter, and disposable PostgreSQL. No authority or cryptographic verifier is mocked. It calls:

- `createAuthEndpoint`, `sensitiveSessionMiddleware`, and `getAuthoritativeSessionFromCtx` from `better-auth/api`; actual canonical session cookies come from `auth.api.signInEmail` or the independently tested legacy bridge's public cookie helper.
- The existing `createPrototypeNativeFacade(...).withIssuanceTransaction` and its existing token issuer/validator/refresh implementation. This adapter adds no password/provider verifier, native JWT policy, refresh store, or new session creation path.
- The previously proved public password change/server-only set-password operations and forgotten-reset handler, plus public `context.internalAdapter.deleteUser` under the same lifecycle fence for the deletion test. The set-password case uses trusted fixture removal of an existing credential before invoking the real set-password API; it does not repeat provider authentication coverage.

Pinned installed source reviewed: `better-auth/dist/api/routes/session.mjs` (`getAuthoritativeSessionFromCtx`, `sensitiveSessionMiddleware`, `freshSessionMiddleware`), `better-auth/dist/api/routes/sign-in.mjs`, and the public `better-auth/api` exports. The middleware's lack of freshness enforcement is intentional for this ordinary handoff. Strict origin and CSRF checks are explicitly pinned on, including under the test environment where the stock default otherwise bypasses origin checking. Requests copy URL, method, headers, and body before waiting for the fence. Real browser CORS/cookie deployment is not simulated by these in-process requests.

## Evidence and remaining adoption gates

`packages/backend/src/auth/prototype/__tests__/canonical-handoff.test.ts` covers real HttpOnly canonical cookies, exact persisted source binding, native wire shape, old and unknown age, origin/actor rejection, strict public body, two-authority one-use concurrency, instance recreation, lost response, exact expiry and expiry while queued, signature/purpose/version/nonce/source/key substitution, receipt corruption, actual post-mint rollback, late policy failure/cookie stripping, reset/logout/deletion races, same-user source substitution, new login after reset, and both password continuation operations.

Final author validation on 2026-11-04: **43/43 passed on PostgreSQL 15** at local port 15475 (8.07 seconds test time), **43/43 passed on PostgreSQL 18** at local port 15477 (8.18 seconds), scoped `vp check` clean, and full backend TypeScript check clean. This includes the exact optional browser-session binding and real global/caller-plugin policy denial regressions. Each run used a fresh disposable database and completed teardown. Independent security review is recorded separately in the implementation ledger after its verdict.

This demonstrates a **future supported producer capability**. It does not prove that the current production browser callback already runs inside the writer fence or emits canonical provenance. The legacy producer still drops returning-user lineage; its source-less limitation remains documented in [the legacy transfer proof](better-auth-transfer-proof.md).

Production adoption still requires backend route and callback ownership, key provisioning/rotation, issuer/version rollout and mixed-server compatibility, real www/auth CORS and cookie deployment, native/Expo deep-link and lost-response UI, rate and payload limits, scalable fencing, and durable client account-generation checks. A stale native client that changed local accounts while an exchange was pending cannot be inferred from a cookie-less opaque request; the server proves the token's source identity, and clients must prevent delayed responses from replacing a newer local account. No client generation assertion is invented by this proof. Published responses also cannot be atomically delivered over the network with the SQL commit; the documented consumed-after-lost-response behavior is deliberate.
