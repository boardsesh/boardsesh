# Backend-owned UID-bound password recovery

Status: implemented and independently reviewed, 2026-11-05. Credential delegation remains default-off. Capability headers, shared web/mobile telemetry redaction and fixed legacy diagnostics apply unconditionally. Focused backend, public-consumer, frontend/privacy, full web/mobile, type and bundle checks pass. Live framework checks retain the explicit development-cache and early-redirect privacy counterexamples below. Production activation remains **NO-GO**.

## Scope and existing contracts

Move the existing forgot-password issuer and reset-password consumer together behind the default-off current-store backend transport. Keep the public URLs and installed clients. A successful reset issues no session, token pair, authentication freshness or cookie. The accepted policy is that account recovery revokes every first-party credential and partner connection; this slice can commit the credential change, current refresh-row revocation and durable cutoff/event intent together. Today's web/native JWT validators, caches, WebSockets, other issuers and partner consumers do not all enforce that intent, so this is not effective all-session revocation or rollout approval.

| Surface | Released behavior to preserve or explicitly replace in staging |
| --- | --- |
| `packages/web/app/api/auth/forgot-password/route.ts` | POST, best-effort per-instance IP limit 5/60 seconds, 1,500 ms minimum response time on validation/rate/success/error. Zod email is used as submitted; the UI trims it but the server does not normalize it. Unknown users and OAuth-only users return the same generic 200 as a sent mail. Current issuer uses a random UUID, stores its SHA-256 hex under `password-reset:<email>`, replaces all rows with that identifier and sets a one-hour deadline. SMTP happens after commit; SMTP failure still returns generic 200. |
| `packages/web/app/api/auth/reset-password/route.ts` | Same independent limit and minimum floor. Legacy body is `{email, token, password, confirmPassword}`: Zod email, UUID token, password 8–128 JavaScript string units, exact confirmation. No password trimming or Unicode normalization; bcrypt cost 12 and its existing 72-UTF-8-byte truncation behavior remain. Invalid/expired links return 400; success returns the existing message and marks only a NULL `emailVerified`. No session is issued. |
| Current ownership and atomicity gaps | Both routes look the address up with the BA-02 rule: exact first, then the one row storing it in other capitals; an address several rows share, or two rows store as the same text, sends no link and resets nothing. Legacy reset validates the email-keyed token before its transaction, later reselects the current owner, writes credentials and deletes all reset rows for that email. It has no immutable UID evidence, atomic one-use claim, cutoff, mutation event or refresh revocation. A unique current address or user creation timestamp cannot prove the original owner of an old token. |
| Web and installed clients | Web reset and installed native/Expo reset screens accept any nonempty token and email hint. Native `auth.ts` and Expo `auth.web.ts` call these public web endpoints with the existing flat body; every 2xx means success and neither recovery function writes or clears credentials. Keep an email query hint in new mail for these clients, without granting it authority. |
| Mail and UI | The shared password-reset template already URL-encodes token and email, displays a one-hour lifetime and sends plaintext plus HTML. Reset UI navigates to login after success. The existing reset page is noindex; its description displays the query email, which is only an untrusted hint. |

The 1,500 ms floor is a minimum, not proof of constant-time responses or protection from slow SMTP timing. Existing per-instance rate limiting is not a distributed production abuse control. In staged mode the forgot-password and reset-password limits key on the trusted client address, not the caller-written first `X-Forwarded-For` hop; see the [password delegation doc](./better-auth-web-password-delegation.md). Legacy/default-off credential validation and write behavior remain; privacy headers and fixed-category diagnostics protect both modes. New capability links must never enter the legacy writer.

## Transport and dispatch

Reuse `CURRENT_STORE_WEB_AUTH_MODE=legacy|backend-staging`, the existing explicit backend origin and distinct RPC secret, authority configuration, SQL-parameter-logging prohibition, strict body/response limits, deadlines and request freshness/replay rules. No new mode, service key or public request metadata is needed. A mode is an adoption selector, not a safe mixed-version rollback plan.

Add fixed private operations `forgot-password` and `reset-password` to `@boardsesh/auth-protocol`. Keep required JSON `protocolVersion: 2` and all four existing operation DTOs unchanged. An old backend must reject an unknown new operation/path before any nonce or domain write; the new client maps that rejection to unavailable, with no local fallback or automatic retry. A new backend rejects missing/wrong versions before any write. Prove both mixed directions. Adding new operations does not make unmodified old public readers capable of consuming new tokens.

The new raw capability is `pr1_` followed by 43 base64url characters from 32 random bytes. Store only a purpose-separated SHA-256 hash. Classify `/^pr\d+_/i` before the old UUID validator and before legacy/default-off dispatch: disabled or unsupported versions return retryable 503 without querying or changing their receipt; malformed supported syntax has a finite invalid-link outcome and never falls back. Keep new token length bounded. Unsupported historical formats beyond the transport limit return 503 untouched rather than being declared invalid.

The forgot command accepts a required unknown payload for backend-owned legacy email validation. Its authoritative reply is `accepted`, optionally containing a strict private mail plan tagged `uid-password-reset-v1` with the exact committed recipient, raw token and original ISO deadline. It contains no database identifier or browser authority. The public adapter manually projects only the existing generic message. Canonical mail origin must be validated before RPC or any write. Web sends the mail after commit using the shared template; no backend SMTP configuration or new SMTP transport is introduced.

The reset command accepts the public payload for backend-owned password/confirmation validation. For `pr1_`, ignore the supplied email hint when resolving or authorizing the account; the immutable receipt determines UID and delivered identity. Preserve the hint in actual mail and existing clients' body for compatibility. Legacy classification still needs its exact submitted email to find the original email-keyed record, but never queries a current user. Private reset outcomes are `reset`, `invalid_or_expired`, `legacy_unbound` and fixed transport/domain errors. Public success and invalid-link messages/statuses stay the released 200/400 contract; live legacy provenance uncertainty and backend/SQL/protocol uncertainty return fixed safe 503. A repeated private request ID is uncertain/replayed, never a cached success.

Retain both public rate limits and minimum floors. Clamp any positive protocol `Retry-After` representation consistently at its exact reset boundary. SQL deadlock/serialization, timeout, unknown acknowledgement and malformed replies are unavailable; never reuse an old hash result in a partial retry. Unknown commit is not permission to retry automatically or delete a committed account.

## Additive schema

Add only `auth_password_recovery_state` and `auth_password_recovery_tokens` in a dedicated auth schema module, exported through the existing schema entrypoint. Generate the migration, journal and snapshot with `vp exec drizzle-kit generate` from `packages/db`; do not hand-write migration SQL.

The durable state has `(user_id, purpose='password-reset')` as its primary key, nonnegative issuance generation and updated timestamp. It has no users foreign key and no expiry. Receipt cleanup must not reset it. The receipt has a purpose-separated token-hash primary key, immutable UID, purpose, original delivered email, accepted JS-normalized email key, subject/security generation, purpose issuance generation, one captured database `issued_at`, original `expires_at`, and exclusive consumed/superseded terminal timestamps. It references only its durable purpose state with RESTRICT, never users with cascade. Keep the active partial unique index on UID/purpose and terminal state, not volatile time; expired active rows are explicitly superseded before insertion. Check hash syntax, purpose, generations, nonempty identity fields and a positive lifetime of at most one hour. Retain an expiry index.

Raw delivered email is immutable provenance. A harmless case/trim-only stored-address normalization remains acceptable for the same UID, accepted normalized key, trusted reservation owner/sole membership and unchanged generations. Do not fold dots, plus tags or provider aliases. A true key or owner change rejects the receipt. Cleanup and retained email/UID policy remain separate operational gates; no cleanup/import command is added.

## Issuance and redemption

Forgot captures immutable command/authority inputs before awaiting. Under READ COMMITTED and the manifest-first common fence, claim the private nonce, recheck freshness and current trusted projection basis, and resolve a sole-owned current key/member/user with an existing password credential and no deletion cutoff. Missing, OAuth-only, already ambiguous or ineligible owners return the same accepted result without mail; stale/missing authority basis is unavailable, not an invented owner. Do not choose a member of an ambiguous group. Keep current email-input validation but use the accepted normalizer for reservation identity; preserve the actual committed recipient's case and plus suffix.

Lock the UID/purpose state, advance its durable generation, supersede only active **new** receipts for this UID/purpose, and insert the new receipt with a one-hour deadline from one PostgreSQL clock capture. Do not delete or supersede legacy email-keyed records. Nonce, purpose state and receipt commit together. SMTP is outside the transaction. Agent decision: absent/ineligible outcomes and postcommit SMTP failure all produce the same generic public 200; diagnostics use only a fixed category/new fixed error without the original exception or cause. SQL/protocol/authority uncertainty is 503. Existing unbounded SMTP remains an activation gate.

Reset first captures token/password/authority and an immutable receipt binding. Preliminary reads confer no authority. Require a credential-bearing bound UID; a deleted credential does not silently become an OAuth password-set command. Snapshot the current hash and mapping around bcrypt as a defense against an in-flight legacy credential change. A legacy write completed before that snapshot can still bypass generation bookkeeping until all writers are fenced; this defense does not close that gate. Hash the unchanged submitted password with bcrypt cost 12 **outside** the global manifest lock.

In the final transaction, acquire the manifest before any participating identity/cutoff write, claim the nonce and recheck freshness. Follow one documented lock order through UID user, reservation/membership, credential, subject cutoff, durable purpose state and exact receipt. Forgot reads the key's owner without a lock to know which user row to lock first, then locks and re-checks the reservation; a key that gained an owner after that read sends nothing. Since BA-04 PR 3 the user row comes before the reservation, the order account deletion uses, so a reset or forgot waiting on a climber's row never holds the reservation the deletion needs next. Recompare the captured immutable receipt, original deadline and credential hash/mapping; recheck current UID, sole-owned key/basis/member, subject/purpose generations, deletion and terminal state. Read the actual database clock after lock/hash waits. A conditional terminal update must establish unconsumed, unsuperseded and strictly unexpired ownership.

Commit receipt consumption, durable purpose generation advancement, the actual UID-only credential UPDATE, NULL-only email verification, `recordSecurityMutation(kind='password-reset', domains=['first-party','partner'])`, and UPDATE of all currently unrevoked refresh rows for that UID in the **same outer transaction**. The mutation helper receives the expected subject generation from the receipt and a server-controlled unique operation ID. Any error aborts password, receipt, nonce, generations, cutoff/event and refresh changes. Existing verification and recovery receipts carrying the old subject generation then fail their own consumer checks. Preserve any preexisting verification timestamp. Publish no successful response until commit; issue no JWT, cookie or session and do not clear the caller's cookie locally.

The existing refresh rotator and other password/provider issuers do not yet acquire this authority fence. A row update alone cannot establish full issuance-family closure: an already-running issuer may mint after it, and old JWT/cache/WebSocket validators ignore the cutoff. The lifecycle tests exercise participating recovery interleavings, current stored refresh-row updates and the real native refresh rotator racing a reset; they do not execute validator/cache/WebSocket paths after reset. Those remaining gaps are source-reviewed limitations, not closed or runtime-characterized consumers. A refresh rotation cannot outlive the reset's revocation. The first lock in its transaction is `requireHumanSubjectForIssuance`, a `FOR KEY SHARE` on the `users` row, which conflicts with the reset's `FOR UPDATE` on that row and is taken before the rotation touches any refresh row. A rotation that gets the lock first commits before the reset proceeds, so the reset's refresh UPDATE sees the new row and revokes it. A rotation that arrives second waits on that SELECT until the reset commits, then finds its token revoked, returns 401 and inserts nothing. The real rotator is exercised against both orders. This closes refresh rows only: a staged reset still does not end existing web session cookies or native JWTs, because no validator reads `auth_subject_cutoffs.revoked_through`. They keep working until they expire, and enforcing the cutoff is BA-04 PRs 2 and 3. Participating lock contention or a mixed legacy deadlock must abort and return unavailable, never continue from a stale hash. Authenticated password set/change and its accepted keep-current-device policy are outside this reset-only slice.

## Legacy provenance and rollback

For an unversioned submitted token within supported bounds, compute the released SHA-256 hash and read only the exact `password-reset:<submitted-email>` legacy row. A matching expired row or no match returns the existing invalid/expired result without cleanup. Do not delete another purpose's record through a submitted identifier, and do not let `prN_` fall back to legacy token lookup.

Until BA-02 (#4847) makes Postgres keep one account per address, a matching live row returns `legacy_unbound`/503 with its row and original deadline intact, whatever the current owners. Once a valid unique index on exactly `lower(email)` exists (BA-04 PR 4 checks the catalog, not a flag), a live link binds to the one account holding its address and resets it like a `pr1_` receipt: same password policy, security mutation, refresh revocation and verified stamp. It binds only when the reservation is `owned` by that account and no other row lowercases to the address; a shared address stays `legacy_unbound` and a retired one is invalid. The link keeps its original deadline, checked again after every lock wait, and a deadline more than an hour away is refused because the old route never issued one. It works once: the old row is left untouched, because command roles only append to `verificationTokens`, and a replay record keyed by a hash of the row marks it used. A link issued before the account's latest recorded security mutation (deadline minus one hour before `revoked_through`) is dead, as a receipt from an older subject generation is. Only staged writers record one: a staged reset, change, set or deletion. The legacy `/api/internal/set-password` route writes no cutoff, so a link issued before that kind of set still works, as it does in legacy. The submitted address must match the row exactly, so another address, even the same one in another case, is invalid.

Current source issues one-hour legacy links, but that is not evidence that every already-issued record has that deadline. Test a matching legacy row with an original seven-day deadline, including address reassignment and new UID-bound forgot issuance, and retain it unchanged. Production adoption requires proven original-owner import provenance, or all old issuers stopped plus a bounded wait based on the **actual maximum original outstanding deadlines**. No import, cleanup, lifetime shortening or identity reassignment is performed here.

Updated consumers must recognize new capabilities while mode is disabled. Actual unmodified public replicas remain a rollout blocker, and capable readers must stay available through every issued deadline even if issuance stops. Returning to a legacy writer can restore unfenced mutation. Mode flags are not a rollout/rollback protocol.

## Capability privacy

Reset URLs contain a bearer secret and an email hint. Exact and localized reset-page rules follow the global Next header rules to configure `Referrer-Policy: no-referrer`, private/no-store caching and existing noindex protection. Both public POST response wrappers apply privacy headers to every outcome without setting or clearing auth cookies. Framework header precedence and rendered responses require separate checks, beyond the route helpers. These protections apply in both modes and cover legacy links as well as `pr1_` links.

The pinned Next development renderer replaces rendered-page `Cache-Control` with `no-cache, must-revalidate` after configuration headers; that permits browser storage with revalidation and is not `no-store`. All five owned-local reset pages exhibited this development-only override while retaining both CDN no-store headers, no-referrer and noindex. The page already reads request headers through `getLocale()`, making it dynamic. A pinned production response-sender regression checks its dynamic-cache no-store fallback and preservation of configured recovery headers without building or starting a production server. That bounded check is not a full production-render or deployed-ingress proof. No custom server or dependency patch changes Next's development behavior.

The actual owned-local trailing-slash first hops at `/auth/reset-password/`, `/fr/auth/reset-password/` and `/es/api/auth/reset-password/` returned automatic 308 redirects with none of the configured referrer, cache, CDN-cache or robots headers. Configuration-helper tests evaluate the rules but do not reproduce that early redirect. These are measured privacy counterexamples, not passed protection checks. Mail links continue to use the canonical path without a trailing slash. Agent decision: retain existing global routing rather than replace its canonicalization for this slice; production activation requires validated ingress or a separately reviewed scoped framework fix covering every first-hop capability redirect. The final canonical response cannot establish the missing first-hop policy. API responses continue to require no-store, and the live probe permits the exact development-page cache override only on rendered 200 pages with both CDN no-store headers.

The source audit found PostHog SDK enrichment with full current URLs and referrers: a safe pathname passed to pageview was insufficient. Sentry browser HttpContext, navigation breadcrumbs and request/span fields likewise retained query data; its production-host instrumentation is independent of analytics consent. Shared redaction now runs at the web PostHog and browser/edge/server Sentry boundaries and in the mobile Sentry hooks. Consented recovery events can still be collected; URL/query/body content is redacted before emission, including referring URLs, queued properties and structured or serialized credential bodies in event and flags processing. Existing user/device filters, captured-value normalization and chunk fingerprints remain. Ad pixels already exclude auth paths.

Agent privacy decision: a recognized raw or encoded forgot/reset URL loses its **entire query and fragment** in telemetry, including campaign/source metadata and nested URLs in that suffix. Associated detached query strings, maps, tuples and aliases become `[redacted]`. Reserved standalone `prN_` capabilities also receive the free-text guard; unrelated URLs carrying neither a recovery URL nor that reserved capability remain byte-for-byte unchanged. Structured and serialized recovery bodies redact credential fields. This is not arbitrary secret detection in free text. Actual mail links, UI URLs and installed-client payloads are not rewritten.

Review exposed unsafe assumptions in partial parameter decoding, encoded delimiters, nested URLs and shared object aliases. The final URL redactor uses fixed patterns and whole-suffix replacement, with no dynamic regular expressions or recursive URL interpretation. The ASCII percent-encoded body field-name classifier uses a stack reduction: each input character is pushed once and each reduction removes entries, giving linear O(n) work without a depth cap. This bound describes field-name classification, not a claim that the structured-event traversal uses no recursion. Fixed strings/new fixed errors replace original JSON/SMTP/SQL exceptions in diagnostics in **both** modes; original causes, message envelopes and submitted payloads are not forwarded. Local SDK protections do not prove external ingress/access-log privacy; deployment logging remains a gate.
