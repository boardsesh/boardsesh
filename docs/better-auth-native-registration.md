# Staged normalized reservations for native registration

Status: implemented for default-off staging, with independent source review and PostgreSQL QA passed on 2026-11-05. This follows [UID verification](./better-auth-uid-verification.md) in BA-03. The preceding PR's main CI and auxiliary image builds passed before publication of this slice. Production activation remains **NO-GO**; this does not complete BA-03 or establish the production writer/issuer fence.

## Contracts and decisions

Use one reserved-password identity insertion stage for web registration and an independently opted-in native registration path. The caller owns the transaction. The shared stage checks the enforced manifest, validates reservation basis, generates the immutable user ID, reserves the normalized key and calls the existing identity inserter. Native retains the existing `generateTokenPair(userId, tx)` in that same transaction. Publish the response only after commit. Add no new schema, issuer or generic callback framework.

`current-store/reserved-password-registration.ts` implements that stage. Its prewrite `exists` discriminant lets a web caller commit the already-claimed negative command receipt without catching a SQL failure. A native caller has no transport nonce. SQL/trust failures still abort the outer transaction. `authority-configuration.ts` shares only the captured authority and parameter-logging guard; each transport selects its own opt-in and validates its own credentials separately. The native adapter's optional database argument supports owned authenticated test pools; no request body or header chooses that database.

Introduce `CURRENT_STORE_NATIVE_REGISTRATION_MODE=legacy|reserved-staging`, defaulting to `legacy`. Native adoption must not be implicitly selected by the web flag or require its RPC secret. Reuse captured authority configuration and reject enabled `DEBUG_SQL=true`. Check authority before the legacy exact-email precheck can return an early conflict, then check it again under the final transaction gate.

Trust precedence is explicit: stale or mismatched reservation basis is retryable 503; only a current trusted occupied key is an existing-account 409. The web caller must commit its already-claimed command nonce with an authoritative 409 inside its transaction. A native request has no transport nonce and may return its conflict after rollback. No account owner is selected from a collision group.

An exact-email precheck returning no prepared hash does not bypass that final decision: both callers still lock the key and validate its basis. An exact existing user with no reservation is incomplete authority and returns 503. This intentionally tightens the staging web path too; a legacy direct write cannot turn an inconsistent projection into an authoritative conflict. Neither caller repairs, promotes or reassigns that projection. Bcrypt runs with no transaction open; the final stage checks authority again afterward under the shared gate and takes the address's creation lock before reading its reservation, so two registrations for one key queue there (BA-04 PR 3).

Installed clients still send `{email,password,name?}` without protocol versions, request IDs, authority metadata or RPC secrets. They consume every 2xx as an immediate flat `{jwt,refreshToken,expiresAt,userId,accountCreation?}` and store tokens before optional creation metadata validation. Preserve 201 and usable tokens even when verification is enabled; store `emailVerified:null` as before. Do not introduce a verification-required success envelope.

Keep native field validation and error copy, trimmed/lowercased email, trimmed name, exact password bytes, bcrypt12, the existing seven-day JWT and refresh issuer, and the UID-matching creation receipt. Its timestamp remains an exact millisecond UTC value. Existing native password login keeps its current LOWER-only stored-email lookup and bounded password comparison; stored-whitespace login gaps remain an activation concern.

The intentional staging safety change is that any current trusted occupied normalized key, including mixed-case, whitespace or ambiguous groups, prevents a second registration. This does not merge, delete or reassign an account. Existing production collisions and every unfenced writer remain separate gates.

Return sanitized fixed errors: preserve generic 500 for signing/internal failures and use 503 for authority/infrastructure uncertainty. New staged errors must not reach the legacy raw exception logger with bound password hashes or other private values. Non-2xx and network failures leave installed clients' existing credentials untouched. Ordinary CORS, validation and rate-limit contracts remain supported.

The enabled path reports only fixed failure categories. It never passes the original SQL, parameters, exception, cause or private values into logs/Sentry. Internal failures use a new constant-message `Error`; authority, Drizzle/SQL and recognized driver availability failures use a fixed warning and `{error:'Service temporarily unavailable'}`. Successful creation keeps the legacy flat response, including when verification is required. This adapter adds no mail issuance, security mutation event, session-generation field or ongoing revocation consumer. Existing password-verdict/issuance races remain separate work.

## Required verification

1. Actual public native HTTP handler, existing signing and non-owner PostgreSQL LOGIN connections; both verification flags produce compatible tokens and matching receipt owners.
2. Actual mobile `registerWithCredentials` and auth-store, substituting only native host and SecureStore I/O: 201 stores the new pair; 409/503 preserve the old pair.
3. Two native instances and web/native normalized-key races, current and stale reservation states, blocked groups and hostile body metadata.
4. Missing signing secret and refresh-insert failure roll back identity, credentials, profile, reservation and refresh rows together; lost acknowledgement followed by retry yields one account and 409, without cached tokens or compensating deletion.
5. Minimal fixture grants, web conflict nonce persistence, both independent opt-ins, enabled unavailable configuration and unchanged existing native/web regressions.

Fixture grants cover only the required reads, inserts and row-lock UPDATE privileges; they confer no ownership, role membership, grant options, DELETE or TRUNCATE. Testing these permissions does not establish actual deployed IAM or an issuer fence. No runtime role transfer or new production pool credentials are configured by this slice; the ordinary server retains its configured database client.

The backend fixture uses two native HTTP listeners with independently authenticated pools for the same restricted LOGIN role, plus a separate web LOGIN role. It is one Node process, not a process-restart or deployed-replica proof. Native grants are SELECT/INSERT on users; INSERT on credentials, profiles and refresh rows; SELECT/UPDATE on the manifest and cutoffs for row locks; SELECT/INSERT/UPDATE on reservations; and SELECT/INSERT on reservation members. It needs no web RPC secret, command-nonce, verification-receipt or event-table permission. Actual DELETE/TRUNCATE attempts are denied. The web fixture alone adds command-nonce SELECT/INSERT. Owned roles are transactionally tracked before commit, all pools are closed, and each cleanup stage attempts only those tracked roles while retaining sanitized failures.

## Measured validation

The final author PostgreSQL 18 run passed **85/85 across three files in 23.29 seconds**: 22 new native cases plus the existing 31 web-password and 32 UID-verification cases. Independent PostgreSQL 15 verification passed the same **85/85 in 30.39 seconds**, with clean teardown. The shared-helper regressions verify that stale or missing key evidence is unavailable and a trusted occupied key still commits the web caller's one negative command nonce. The final native-only selection also passed 22/22 in 16.03 seconds before that combined run.

The new native cases use actual public HTTP, real bcrypt and signing, restricted LOGIN connections, independent native pools, both verification flags and hostile extra body metadata. They cover native/native and web/native key races, occupied/blocked groups, exact-email stale/missing projection evidence, independent opt-ins, post-bcrypt authority change without a held global manifest lock, disabled configuration and minimal privilege enforcement. Missing signing configuration rolls the whole command back with generic 500. A real refresh INSERT CHECK failure rolls identity, profile, credential, reservation, membership and refresh persistence back with 503. A real reservation-read permission outage likewise yields 503 with zero identity changes, one fixed warning and no call to the legacy raw exception logger.

The author actual-mobile selection passed **9/9 on PostgreSQL 18 in 12.83 seconds** (8.13 seconds of cases); the independent PostgreSQL 15 run passed **9/9 in 20.73 seconds** (12.91 seconds of cases). Both completed owned-role, listener and child teardown; salted `SKIP_TEST_INFRA` worker databases remain retained. The final nine-file source/test selection passed checking with zero warnings or errors and a clean diff check. It invokes real `auth.ts`, auth-store and receipt parsing over real native HTTP/PostgreSQL, substituting only native host and SecureStore I/O. Both verification flags store the real token pair and UID-matching receipt. Actual 400/409/429/500/503 and an initial socket failure preserve the seeded old credential pair and generation. There are no mobile production, native package, Metro or iOS changes. These tests do not prove behavior on a real app/device or Bluetooth hardware.

Two lost-response checks have distinct scope. The backend test discards a committed 201 response body and verifies that a fresh retry returns 409 with one identity/refresh row and no cached tokens. Separately, the real mobile consumer receives the 201 headers and loses the body: its existing implementation throws during `response.json()` outside the fetch catch, before writing storage. The old pair remains unchanged, the committed account remains, and a deliberate manual retry returns 409. Both discard/loss checks observe the 201 headers; they are not proof of an unknown commit acknowledgement before headers. This does not claim that every body-read failure returns a structured network result, or that local storage-write failures preserve credentials. Missing/foreign optional metadata behavior remains covered by existing standalone parser tests, not fabricated producer responses in this HTTP proof.

Initial backend TypeScript and the six-file runtime selection passed with zero warnings/errors. The first PostgreSQL run found test-only wrapped-error and historical-manifest fixture mistakes; those were corrected without changing the issuer or relaxing authority checks. The factor also preserves the existing fixed `Unsafe current-store auth SQL logging` error contract. JWT `iat`, signed expiry, response expiry and refresh expiry are independently bounded by the real request window: the unchanged issuer reads clocks separately, so an exact `exp-iat` equality would overstate its contract.

The full required TypeScript graph passed all **59 tasks** with task concurrency limited to two, followed by a final **13-task backend** check after the consumer tests were frozen. The first default-concurrency attempt aborted in the task runner with a Rust worker stack overflow; it produced no TypeScript diagnostic. Its originating unchanged profile-stats task passed in isolation before the full retry. Repository checking passed formatting for 9,698 files and linting for 9,167 files with **zero errors and 623 existing warnings**. No dependency, lockfile or production mobile code change was needed.

The final independent legacy regression selection passed **184/184 across nine existing files on PostgreSQL 18 in 20.73 seconds**. It covers five native authentication suites, password identity, the foundation, the public NextAuth handler and local OIDC. These cases are distinct from the 85 backend/shared and nine actual-mobile cases above: 278 cases across 13 files in total, without counting the repeat PostgreSQL runs twice.

The local HTTPS development environment loaded this branch and its tester QA notes. The actual public native registration endpoint returned 400 for an invalid address without writing an identity; the mounted private web registration RPC returned its default disabled response. These live checks do not opt the shared development database into the reserved mode. Its transaction and compatible-client behavior are exercised in the isolated authenticated PostgreSQL fixtures above.

Independent source, test and permission review approved the final candidate after re-reviewing the authority precedence, error sanitization, separate-pool and clock-boundary fixes. This is implementation-only approval for default-off staging.

No mobile production, Bluetooth or iOS changes are planned. The requesting-device password-change policy is unchanged and outside this slice. All other credential writers, issuer/validator revocation, reset races, projection preparation, real role access and safe rollback remain production gates.

This plan authorizes no production activation, token import, account reassignment or data deletion.
