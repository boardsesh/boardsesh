# Staged normalized reservations for native OAuth

Status: implemented and independently reviewed for default-off staging on 2026-11-05. This follows [native password registration](./better-auth-native-registration.md), the [accepted migration](./better-auth-migration.md) and [BA-03 #6977](https://github.com/boardsesh/boardsesh/issues/6977). Production activation remains **NO-GO**. This is one endpoint adoption, not a claim that every installed-client OAuth path uses the new writer.

## Remaining writer inventory and sequence

| Area | Current source and retained gap |
| --- | --- |
| Provider identity | Legacy `backend/src/handlers/native-auth.ts::findOrCreateOAuthUser` resolves the subject, otherwise links the first exact-email match or creates a user/profile/provider account. Its conflict-ignored link insert is not followed by confirmation of its persisted owner. The explicit staged route now uses the reserved service below. Web `auth-options.ts` still exposes DrizzleAdapter user/account create/update/delete/link/unlink, enables dangerous email linking, writes verification in `signIn`, and inserts profiles in `events.createUser`. |
| Recovery | Web `api/auth/forgot-password/route.ts` finds the one account the address names (BA-02 rule: exact first, then one row in other capitals, refusing several) and writes a SHA-256 reset token keyed on its stored address. `reset-password/route.ts` checks the token outside its credential transaction, reselects that one owner the same way, writes bcrypt and verification, and deletes all reset rows for that email. Original UID, atomic consumption and revocation intent remain absent. |
| Authenticated passwords | Web `api/internal/set-password/route.ts` trusts the current NextAuth session, inserts bcrypt and marks the email verified. A session alone does not prove fresh provider/mailbox authentication. No separate authenticated change-password endpoint was found. The user's keep-current-device decision requires a proven requesting SID and replacement/continuation, not an exception based on a current timestamp. |
| Deletion | Backend `graphql/resolvers/users/mutations.ts::deleteAccount` owns a large retried product-erasure transaction and post-commit cleanup. Its users DELETE cascades accounts, passwords and refresh rows but does not record the foundation cutoff/event. Product tombstones, photo erasure, analytics jobs and existing lock order must remain intact. |
| Other writers and consumers | Backend board-presence and location-sync create system users; fixture/admin scripts retain direct writes. `middleware/auth.ts` accepts JWE/JWS and positively caches for 60 seconds without checking user/cutoff state. HTTP Yoga, upload/export/import/session handlers and WebSocket contexts consume that result; open sockets retain their authenticated boolean. Web NextAuth/SSR/ws-auth, native refresh/exchange/revoke and watch pairing are additional issuer/validator boundaries. |

No current user-facing first-party provider unlink or email-change endpoint was found. The NextAuth adapter still exposes those mutation methods, so they remain in the fence inventory. Aurora board-account linking is a different credential domain.

This slice adopts native Apple/Google account resolution and creation using its existing transaction and token issuer, with no new schema or session-revocation consumer. Recovery issuance/consumption should follow as a coherent UID/purpose/key/generation-bound pair with atomic cutoff/outbox intent. Authenticated set/change and deletion then need authenticated-actor/continuation and validator adoption before any revocation-safe activation claim. One RPC per NextAuth adapter method remains insufficient: its create-user/profile/link ordering is not one transaction, as the [public-handler proof](./better-auth-nextauth-public-handler-proof.md) records.

## Configuration and installed contract

Use `CURRENT_STORE_NATIVE_OAUTH_MODE=legacy|reserved-staging`, default `legacy`. This is one explicit switch for both native providers, not provider-specific switches. The existing registration flag never activates OAuth. A combined mode would require precedence and contradictory-flag rules during configuration coexistence; the separate explicit selector keeps current registration behavior stable. Consolidation belongs to the later all-writer authority cutover.

This selector is not a safe rollback mechanism. Switching back to a legacy writer while other paths reserve keys can restore unfenced direct writes. Actual mixed-version capability fencing and mutation-safe rollback remain independent activation gates.

The new selector reuses captured projection ID, normalizer version, writer epoch and the enabled `DEBUG_SQL=true` rejection. It requires no web RPC secret. Disabled mode ignores the new authority requirements. Invalid or unavailable enabled configuration returns fixed 503 and never invokes the legacy resolver. The ordinary body remains `{provider,identityToken,nonce?,name?}`; no protocol version, requested UID, projection or RPC metadata is accepted as authority.

Keep Apple/Google provider IDs, pinned JWKS URLs, accepted audience/issuer variants, RS256, current clock tolerance and installed nonce behavior. Keep the existing native issuer and refresh persistence inside the same transaction, and the flat HTTP 200 token pair with optional UID-matching creation receipt. Existing-account receipts use the original user's creation timestamp and `accountCreated:false`; new accounts use their actual new timestamp and `true`.

The staged verifier additionally requires `exp`; pinned JOSE otherwise validates that claim only when present. It validates runtime subject shape instead of relying on the JWT TypeScript type. A missing matching JWKS key is retryable availability uncertainty, including cache/cooldown rotation, rather than a proved bad signature. A wrong signature against a known key remains 401. Valid cached keys can still verify during an upstream outage; cold/required-key lookup failures do not imply cached verification must fail. Legacy mode keeps its existing verification options and error contract.

An unlinked valid provider subject hitting an occupied current key returns HTTP 409 with fixed, non-identifying copy: `This sign-in method is not linked to that account. Use your existing sign-in method.` This is not an invalid-token 401 and contains no address, UID, subject or database detail. Missing email for a genuinely new subject keeps the current 401/no-email contract. Authority/SQL/JWKS availability failures use 503; genuine signature/claim/nonce failures use the existing fixed 401; signing/internal failures retain generic 500. All staged logging uses constant categories and never forwards original JWT/JWKS/SQL exceptions or claims.

## Subject and reservation transaction

Capture trusted configuration, verified claims and forwarded display-name fields before awaits. Perform a short enforced-authority preflight before provider verification; perform no provider network request under the final global lock. Final resolution starts by locking the enforced manifest **before the first subject lookup**.

Read `accounts` directly by exact `(provider, providerAccountId)`, preserving subject bytes and case. Do not use an inner join that could turn a dangling existing link into apparent permission to create a new account. For a present subject, capture its owner inside the gate, lock/re-read the account and user, and reject ownership change/disappearance rather than following a new owner across a wait.

| Linked account evidence | Staged result |
| --- | --- |
| Current owned key, sole member and owner are the exact linked UID | Admit that UID; do not rewrite email, name, verification or provider ownership. |
| Current `blocked_ambiguous` key includes the exact linked UID and current stored key agrees | Admit that UID by subject ownership. Do not choose the group's email owner or force unaffected linked accounts to log out. |
| Missing/stale basis, missing membership, another owned UID or inconsistent current identity | Retryable 503, without minting or creating another identity. |
| Confirmed deleted subject cutoff | Deny minting. A missing linked user without a deletion proof is unavailable instead. Neither case falls through to new-account creation. |
| Current `blocked_invalid` or inconsistent deleted reservation | Safe unavailability pending identity resolution; never derive a new owner from it. |

Changed, unverified or omitted provider email does not alter an established link. The linked path uses its existing stored identity and supports returning Apple tokens without email/name. It does not require newly fresh authentication or manufacture an authentication-age claim.

For an absent subject, require a valid new email using the shared existing native email parser/normalizer, preserving dots/plus suffixes. The email-only parser was extracted from native registration without changing its error copy, normalization or password handling. Runtime `sub` must be a nonblank string of at most 1,024 UTF-8 bytes; the service does not trust the TypeScript JWT type or normalize the subject. The bound is an explicit staging admission limit to audit before rollout, not a measured production fact.

Any current trusted occupied key, including ambiguous, deleted or invalid state, returns 409 without linking or choosing an owner—even when the provider asserts a verified email. Stale basis returns 503 before the conflict decision. A free key permits one server-generated UID, reservation/member, user, profile and provider account. Insert the provider row with an ordinary unique INSERT/checked RETURNING, never conflict-ignore followed by assumed-owner issuance. A conflicting unfenced legacy insert aborts all new identity/reservation/refresh writes and returns unavailability; any retry must repeat complete resolution.

Keep new-user verification derived from the verified provider claim, and preserve forwarded-name behavior. Call unchanged `generateTokenPair(uid, tx)` after successful resolution in that same transaction. Publish only after commit. Add no password, verification mail, provider-token storage, transport nonce, security-mutation event or new JWT claims.

## Actual-client and verification contracts

The actual low-level mobile OAuth function already treats non-2xx as failure before storing credentials. Its hook has an important separate behavior: **iOS falls back to browser OAuth for every non-cancel native backend failure**, including 400/409/503. That browser flow still reaches the old web adapter. Android displays the existing generic OAuth failure. A native-only guard therefore cannot establish all-path collision refusal for installed iOS clients. Preserve that behavior and test it; do not force an app update or silently disable fallback. Backend enabled-mode failures themselves must never invoke the old resolver as an availability fallback.

1. Exercise the actual public handler and actual JOSE `createRemoteJWKSet`/`jwtVerify` with generated RSA/JWKS. Substitute only HTTP I/O for the exact pinned Apple/Google JWKS URLs, keep real loopback HTTP on captured original fetch, reject other remote requests, and add no production URL/issuer seam. Cover issuer, audiences, expiry, wrong algorithm, runtime subject shape, new-email validity, nonce/hash behavior, invalid signature and JWKS/config outage classification. Existing legacy-verifier behavior remains characterized separately.
2. Use independent non-owner LOGIN pools for same-subject/different-email races and different-subject/same-key races, plus web/native-password competition. Assert one stable subject owner, no unverified-email duplicate, returning no-email/changed-email support, unchanged existing profile/verification, and preserved provider-specific receipt attribution. Test current ambiguous membership, stale/missing basis, dangling/deleted links and owner change after an observed lock wait.
3. Inject actual provider unique-conflict, profile/refresh INSERT and signing failures. Require complete rollback and no successful response; prove no ignored insert can mint an assumed owner. Check original-error redaction, enabled no-fallback, both opt-ins' independence, and unchanged native validation/rate/CORS/status behavior. Fixture permissions are scoped to required identity/provider inserts and row locks; no production grant transfer is implied.
4. Reuse the actual mobile auth/auth-store HTTP probe for 200 success and 409/503/storage preservation, mocking native SDK/SecureStore I/O only. Extend the existing real React hook tests for Apple/Google failure statuses including 400/401/409/503, proving iOS browser dispatch and Android generic errors. Keep direct real-client HTTP evidence distinct from separately mocked provider-bridge hook tests. Root runs the required mobile type/test/bundle checks for test-only mobile edits.
5. Run current native/provider/password, shared registration/verification and public NextAuth proof regressions on PostgreSQL 15 and 18. Independent source/test review must re-review actionable fixes before publication. Measured results follow below.

## Gates that this slice cannot close

Provider ID-token validity and a new native JWT `iat` are not original authentication age. The unchanged issuer/current validators do not consume the new cutoff. A committed intent alone cannot revoke legacy JWE/JWS, renewed refresh tokens, transfer/pair codes, cached validation or authenticated sockets. Reset/issuance races and requesting-device password continuation remain separate work; this endpoint must not advertise revocation safety.

Deleting a user currently cascades away `accounts`. Absence of a current link cannot prove that a subject never belonged to a deleted owner, especially after a provider email changes. This slice provides no durable provider-subject deletion history, import provenance or global re-registration policy. Existing all-writer, deletion and historical-owner gates remain open.

Autonomous work can implement and test the service, mode, actual crypto/client proofs, sanitized failure handling and documentation locally. Production projection/collision measurements, role memberships/owners/alternate routines, old issuer shutdown, configured real provider registrations, SMTP/origins, all reader replicas, web fallback adoption, safe rollback and retained-key/provider-history policy are not established by these fixtures. No production credential/configuration read or mutation, identity import, data deletion, reassignment, Bluetooth or iOS runtime change is authorized.
