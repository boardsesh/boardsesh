# Account-bound first password after email confirmation

This path implements the approved Apple-only account continuation in epic #6975. `CURRENT_STORE_FIRST_PASSWORD_MODE` defaults to `legacy`, which leaves its private route disabled. The web broker, Settings entry, confirmation page and mail template are implemented behind the code-owned `publicFirstPasswordReady()` gate, which remains false. No production mail or browser activation is performed by implementation validation.

Eligibility comes from the actual current browser selection and its caller-held credential. The selected identity store must have no password, at least one Apple provider, and no other provider. The locked shared user supplies the recipient. Its normalized email reservation must be owned by that same fixed UID in the current projection with exactly one matching membership. An address never selects, merges or remaps an account.

The confirmation is a dedicated `first-password` purpose. Its maximum five-minute lifetime is also capped by the original source credential, browser binding and replacement intent. The backend captures the private auth RPC secret as an internal, domain-separated HMAC key for purpose/projection/normalizer/UID/normalized-email binding. A command cannot supply the recipient, binding, key, purpose or an alternative UID. Rotating the RPC key may invalidate pending confirmations; this does not rotate the separate deleted-email key.

## Preparation and publication

Request uses an admitted eligibility preflight, a browser replacement-intent transaction, then a freshly admitted challenge transaction. This sequence is not one atomic request. The preflight refuses an already stale or ineligible actor before intent mutation. Final challenge issuance rechecks current source, email/reservation ownership, selected password absence, Apple-only inventory and authority. Superseding an active challenge scrubs its prepared bcrypt hash and preparation state.

The request returns a **private mail plan** to an authenticated backend service caller. The backend does not invoke delivery. The web broker passes only the fixed backend recipient and confirmation token to the shared email transport; browser JSON contains neither. The confirmation URL carries its token and operation selector in a fragment, with no email or UID. The client removes the fragment before reading pending state. GET requests perform no mutation; the private read command admits actual possession and returns only pending/prepared metadata, deadline and cursor.

Preparation checks the actual actor and confirmation token before bcrypt work, hashes outside transactions, then locks and rechecks all eligibility and challenge bindings under a new authority receipt. It stores only the pending bcrypt hash and opaque hashes; the selected password remains absent and the challenge unconsumed. The prepared reply retains the original SID, authentication time or unknown age, provenance and expiry. It predicts the existing email-verification timestamp, or the stored preparation clock for the confirmed current address, without changing the shared user yet. It proposes a canonical opaque token only to the private issuer.

The web broker uses the shared non-OAuth issuer and provider publication-response builder to construct the exact generation+1 continuation cookie and complete buffered response **before** invoking finalize. The actual observed old proof is retained. Both the operation carrier and future proof must fit the existing cookie/header budgets before a password can be finalized. A lost finalization response returns unavailable without retry, abort, credential reconstruction or candidate-cookie publication.

## Public browser presentation

The five presentation routes are under `/api/internal/auth/first-password/`: `context`, `request`, `read`, `submit` and `acknowledge`. Configuration selects their exact HTTPS Host and Origin; forwarded headers and request URLs cannot select a mail origin. POST bodies have byte, UTF-8, streaming and five-second bounds. Only actual primary-admitted source possession selects the account-level request limiter. A stale Settings UID/SID or actor context refuses before challenge creation or mail delivery.

The short-lived HttpOnly/Secure/SameSite=Lax operation cookie uses a separate HKDF/AES-GCM purpose. It contains command capabilities and original source metadata, never a source/candidate bearer, password, confirmation token or email address. Its local deadline can only shorten the backend challenge, original source or binding deadline. Capturing its metadata clock after the private reply avoids treating RPC latency as a stale challenge; it never changes authentication provenance. The complete projected Cookie header must fit 8,192 bytes before mail delivery, with all unrelated cookies retained in the calculation.

Submit re-admits the exact original account before and after preparation. The next-request acknowledgement requires both physically observed old and current version-named proof cookies, the sealed preparation, exact generation+1/SID/age/expiry and a fresh primary read. It returns no credential or cleanup cookie. The Settings request component is keyed by UID/SID and aborts pending work during layout cleanup, so an old account's response cannot request mail or show success for a new account. The confirmation page retires pending work on unmount and never retries an uncertain submission automatically.

This utility page is noindex and excluded from the sitemap and product analytics. Shared telemetry redaction also removes its complete query/fragment, nested referrer copies and structured `confirmationToken` fields, including before a client effect can clear the URL. The actual installed PostHog enrichment test runs offline; email validation mocks delivery.

Finalize owns one physical transaction. It re-admits the actor, authority, current email/reservation, Apple-only selected inventory, absence of a selected password, confirmation challenge, browser intent and preparation token. It prepares the browser replacement using the actual candidate, stamps the confirmed email through the selected authority, inserts the selected password, performs the existing password-set generation/mirror operation, revokes native and partner credentials, rotates canonical possession while preserving the requesting SID/age/expiry, commits the browser replacement with the same transaction's unforgeable password-set receipt, and consumes/scrubs the challenge. An existing verified timestamp remains unchanged; otherwise the exact stored preparation clock matches the prebuilt profile. This makes the new password usable when the existing sign-in email-verification policy is enabled. The final database-clock check follows all writes. A late refusal rolls back email metadata and every other write in that transaction.

Email confirmation is not provider reauthentication. Successful setup does not refresh the source session's authentication age and creates no provider reauthentication receipt. Linking or unlinking afterward still requires entering and comparing the new password, or another independently qualified proof, within the existing five-minute provider policy.

## Recovery and stored material

Recovery acknowledges only the exact caller-held candidate hash, original actor hash, intent/preparation/recovery tokens and currently admitted selected primary. It never reconstructs, returns or persists a raw bearer. Primary unavailability returns unavailable, including after a successful commit. Recovery is capped at two minutes and at the original challenge/source/binding deadline. A commit near confirmation expiry can have a shorter ACK window; expiry never permits another mutation.

Generated migration `0314_first_password_challenges` adds the single 33-column receipt table. It stores no raw source/candidate, confirmation/recovery/preparation token, email address or plaintext password. The pending bcrypt hash exists only while prepared and is cleared on commit or supersession. The user FK uses ON DELETE CASCADE and ON UPDATE NO ACTION, so explicit account deletion removes pending material and the old challenge cannot replay. Browser selection tombstones retain their existing separate deletion behavior.

The existing awaited per-minute maintenance hook scrubs abandoned expired preparations through the same qualified profile4 pool. It never uses the content handle or adds a timer, principal or DELETE grant. Each transaction observes at most 25 candidates and checks a 750 ms database-clock work budget between locking stages, with one-second statement and 100 ms lock bounds. It takes the authority gate, sorted original/current selected users, binding, intent and challenge locks in that order. Busy rows are skipped for the next tick; phase and actual database expiry are rechecked before clearing only the pending preparation fields into terminal state. Current active confirmations, committed ACK receipts, unrelated accounts and browser selection tombstones are preserved. Existing worker shutdown drains this awaited bounded task before closing the credential pool.

Scrubbing continues with profile4 configured after first-password mode returns to `legacy`. Keep the reviewed profile4 inclusion and pool available during that rollback. Drain/scrub expired pending hashes before downgrading to a profile that removes challenge-table access. No production maintenance scheduling or configuration is performed by this code change. The credential profile deliberately has no account/challenge DELETE or general maintenance capability.

## Database capability and private transport

`private-first-password-v1` is an explicit reviewed superset of `private-provider-v1`. It adds only SELECT/INSERT/UPDATE on `auth_first_password_challenges`. It retains the pinned existing revoke-only partner function and narrow predicate/revocation grants, with no raw token reads, partner issuance, users DELETE, challenge DELETE, TRUNCATE or MAINTAIN. The exact new column/default/index/CHECK/FK catalog shape is statically pinned. Old profiles refuse the additional grants. Every profile also refuses actual PUBLIC table or column grants within its protected capability/side-effect closure, even when those grants do not enlarge the writer's effective rights.

The same authenticated credential LOGIN and bounded cached pool serve explicitly compatible web/browser/provider/first-password requests. Contract selection is known-version configuration and is included in cache identity. Profile4 is not a second per-handler LOGIN or a content-database fallback. Qualification is a read-only observation, not a grant operation or a replacement for retiring old principals and issuers.

The service-only `/api/internal/auth/current-store/first-password/v1/*` handler checks mode, private RPC authentication, method/content type, strict DTO, path and freshness before pool work. It bounds each actual source/candidate to 16 KiB UTF8 and request/reply bodies to 64 KiB. Missing JWE reader configuration refuses before pool acquisition; canonical actors do not require `NEXTAUTH_SECRET`. Account-bound costly work is rate-limited only after actual source admission. No source claims or asserted email binding are trusted from an intermediary.

## Owned qualification and remaining gates

The core has 22 actual-PG flow cases plus the independently reviewed 18 policy/eligibility cases. These cover both stores, JWE/canonical possession, forward mirroring on/off with mandatory canonical rollback copies, original age/SID/expiry, affected versus unrelated partner state, actual new-password comparison after setup, wrong inputs without writes, current owned email drift, supersession scrubbing, account-deletion cascade/no replay, exact ACK expiry/primary removal and observed advisory-locked final-write expiry rollback. Separate scrub controls cover active/unrelated preservation, fixed batch progress, an observed per-write delay consuming the database-clock budget, locked-user skip/retry, a later deleted selection, both actual held-finalizer expiry races, default/rollback profile selection and awaited drain/private errors. The generated 0314 leaves every older SQL/snapshot byte unchanged and appends one journal entry. The canonical user-reference deletion contract explicitly includes and rejects removal/change of the new incoming FK.

The dedicated serial first-password role/HTTP task runs only on the fresh owned current canonical journal. It retains the complete historical and provider proof phases, then executes the new restricted-LOGIN cases and existing web/browser/provider HTTP positives under profile4. It has its own JUnit artifact and does not enter service-free default projects. Synthetic fixture grants are not production provisioning.

The broker/UI/mail composition now has source-level tests for actual JWE/canonical continuation publication, account changes, exact ACK possession, cookie capacity, RPC timing, uncertain replies, StrictMode/unmount behavior and shared telemetry. Actual supported-browser/email delivery, the public/private HTTP join, current-device rolling-cookie qualification, full writer/issuer retirement, live role/pool qualification and production rollout/rollback acceptance remain tracked in #7430. Public readiness stays false until that qualification is recorded.
