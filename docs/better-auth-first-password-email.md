# Account-bound first password after email confirmation

This path implements the approved Apple-only account continuation in epic #6975. `CURRENT_STORE_FIRST_PASSWORD_MODE` defaults to `legacy`, which leaves its private route disabled. This doc covers the backend core and the shared mail template. The www layer (the Settings card, the confirmation page, five browser routes and their broker) was removed in #7596 before it was ever switched on; see [Web layer](#web-layer-removed-in-7596). It will be rebuilt on the shared-domain session described in [better-auth-browser-session.md](better-auth-browser-session.md). No production mail or browser activation is performed by implementation validation.

> **Re-keyed by #7596 B5c2.** Every command acts for the first-party web session www presents (the canonical token; a legacy NextAuth cookie gets `canonical_session_required` and must be bridged first), read by `readFirstPartySession` under the account's `users` lock. No browser binding, browser intent, cursor or candidate credential remains. The same session token must make every step, including the one that completes the emailed confirmation link. Finalize keeps that session's id, token, sign-in time and expiry and moves only its generation (`keepCanonicalAfterSecurityMutation` with the `password-set` receipt); every other first-party credential ends. The NOT NULL binding columns hold `browser_binding_hash` = SHA-256 of `["provider-security-web-session-v1", sessionId]`, `browser_version` 0, `browser_intent_hash` derived from the challenge, and `browser_binding_expires_at` = the session's expiry at request; `proposed_credential_hash` and `candidate_credential_hash` hold the presented token's hash. The backend refuses to start with `CURRENT_STORE_FIRST_PASSWORD_MODE=backend-staging` unless `AUTH_BROWSER_SESSION_MODE=better-auth` (`AUTH_FIRST_PASSWORD_BROWSER_SESSION_REQUIRED`). Where a paragraph below mentions the binding, the replacement intent, a cursor or a candidate, that part no longer applies.

Eligibility comes from the actual current web session and its caller-held credential. The selected identity store must have no password, at least one Apple provider, and no other provider. The locked shared user supplies the recipient. Its normalized email reservation must be owned by that same fixed UID in the current projection with exactly one matching membership. An address never selects, merges or remaps an account.

The confirmation is a dedicated `first-password` purpose. Its maximum five-minute lifetime is also capped by the original source credential. The backend captures the private auth RPC secret as an internal, domain-separated HMAC key for purpose/projection/normalizer/UID/normalized-email binding. A command cannot supply the recipient, binding, key, purpose or an alternative UID. Rotating the RPC key may invalidate pending confirmations; this does not rotate the separate deleted-email key.

## Preparation

> **Partly superseded by #7596.** The browser publication steps here (the generation+1 continuation cookie, the version-named proof cookies, the binding deadline and `publicFirstPasswordReady()`) belong to the browser binding design that is being removed. A5 deletes this web layer and B5 rebuilds it on the new session. Eligibility, the challenge, the finalize transaction, maintenance and the database profile are the backend core and stay. See [better-auth-browser-session.md](better-auth-browser-session.md).

Request is one transaction since B5c2: challenge issuance admits the session and checks current source, email/reservation ownership, selected password absence, Apple-only inventory and authority. Superseding an active challenge scrubs its prepared bcrypt hash and preparation state.

The request returns a **private mail plan** to an authenticated backend service caller. The backend does not invoke delivery. Its caller passes only the fixed backend recipient and confirmation token to the shared email transport (`sendFirstPasswordConfirmationEmail` in `packages/shared/email`). The confirmation URL points at `/auth/confirm-first-password` and carries its token and operation selector in a fragment, with no email or UID. Since #7596 www serves no such page and nothing calls the template; the rebuilt web layer will. GET requests perform no mutation; the private read command admits actual possession and returns only pending/prepared metadata, deadline and cursor.

Preparation checks the actual actor and confirmation token before bcrypt work, hashes outside transactions, then locks and rechecks all eligibility and challenge bindings under a new authority receipt. It stores only the pending bcrypt hash and opaque hashes; the selected password remains absent and the challenge unconsumed. The prepared reply retains the original SID, authentication time or unknown age, provenance and expiry. It predicts the existing email-verification timestamp, or the stored preparation clock for the confirmed current address, without changing the shared user yet. It proposes a canonical opaque token only to the private issuer.

## Web layer (removed in #7596)

> **Partly superseded by #7596.** The five routes, the operation cookie and the proof-cookie acknowledgement in this section are the web layer that A5 deletes and B5 rebuilds. `/auth/confirm-first-password` may answer 404 in between; it serves no live flow today. The finalize transaction paragraph is backend core and stays, apart from its browser replacement step. See [better-auth-browser-session.md](better-auth-browser-session.md).

The www half of this flow never went live: a code-owned `publicFirstPasswordReady()` gate returned `false`. #7596 removed it because it published a version-named browser proof cookie and depended on the browser binding, both of which that issue deletes. What went:

- the five `/api/internal/auth/first-password/*` routes (`context`, `request`, `read`, `submit`, `acknowledge`). They answered 503 and now answer 404.
- the `/auth/confirm-first-password` page. It could only show an "unavailable" or "invalid link" message and now answers 404. Its product-analytics exclusion went with it.
- the Settings "Add a password" email card for Apple-only accounts. It never rendered; those accounts keep the ordinary set-password form.
- the web broker, its command client, its sealed operation cookie and the `settings.firstPassword.*` copy in all five locales.

What stays: the backend core below, the `first-password-v1` protocol, the `auth_first_password_challenges` table, the mail template, and the shared telemetry redaction in `@boardsesh/text-redaction`, which still strips the confirmation path's query and fragment and any `confirmationToken` field.

## Finalize

Finalize owns one physical transaction. It re-admits the actor, authority, current email/reservation, Apple-only selected inventory, absence of a selected password, confirmation challenge, browser intent and preparation token. It prepares the browser replacement using the actual candidate, stamps the confirmed email through the selected authority, inserts the selected password, performs the existing password-set generation/mirror operation, revokes native and partner credentials, rotates canonical possession while preserving the requesting SID/age/expiry, commits the browser replacement with the same transaction's unforgeable password-set receipt, and consumes/scrubs the challenge. An existing verified timestamp remains unchanged; otherwise the exact stored preparation clock matches the prebuilt profile. This makes the new password usable when the existing sign-in email-verification policy is enabled. The final database-clock check follows all writes. A late refusal rolls back email metadata and every other write in that transaction.

Email confirmation is not provider reauthentication. Successful setup does not refresh the source session's authentication age and creates no provider reauthentication receipt. Linking or unlinking afterward still requires entering and comparing the new password, or another independently qualified proof, within the existing five-minute provider policy.

## Recovery and stored material

Recovery acknowledges only the exact caller-held candidate hash, original actor hash, intent/preparation/recovery tokens and currently admitted selected primary. It never reconstructs, returns or persists a raw bearer. Primary unavailability returns unavailable, including after a successful commit. Recovery is capped at two minutes and at the original challenge/source/binding deadline. A commit near confirmation expiry can have a shorter ACK window; expiry never permits another mutation.

Generated migration `0314_first_password_challenges` adds the single 33-column receipt table. It stores no raw source/candidate, confirmation/recovery/preparation token, email address or plaintext password. The pending bcrypt hash exists only while prepared and is cleared on commit or supersession. The user FK uses ON DELETE CASCADE and ON UPDATE NO ACTION, so explicit account deletion removes pending material and the old challenge cannot replay. Browser selection tombstones retain their existing separate deletion behavior.

The existing awaited per-minute maintenance hook scrubs abandoned expired preparations through the same qualified profile4 pool. It never uses the content handle or adds a timer, principal or DELETE grant. Each transaction observes at most 25 candidates and checks a 750 ms database-clock work budget between locking stages, with one-second statement and 100 ms lock bounds. It takes the authority gate, the challenge's own user and then the challenge lock, in that order; since B5c2 it reads no binding or intent row. Busy rows are skipped for the next tick; phase and actual database expiry are rechecked before clearing only the pending preparation fields into terminal state. Current active confirmations, committed ACK receipts, unrelated accounts and browser selection tombstones are preserved. Existing worker shutdown drains this awaited bounded task before closing the credential pool.

Scrubbing continues with profile4 configured after first-password mode returns to `legacy`. Keep the reviewed profile4 inclusion and pool available during that rollback. Drain/scrub expired pending hashes before downgrading to a profile that removes challenge-table access. No production maintenance scheduling or configuration is performed by this code change. The credential profile deliberately has no account/challenge DELETE or general maintenance capability.

## Database capability and private transport

`private-first-password-v1` is an explicit reviewed superset of `private-provider-v1`. It adds only SELECT/INSERT/UPDATE on `auth_first_password_challenges`. It retains the pinned existing revoke-only partner function and narrow predicate/revocation grants, with no raw token reads, partner issuance, users DELETE, challenge DELETE, TRUNCATE or MAINTAIN. The exact new column/default/index/CHECK/FK catalog shape is statically pinned. Old profiles refuse the additional grants. Every profile also refuses actual PUBLIC table or column grants within its protected capability/side-effect closure, even when those grants do not enlarge the writer's effective rights.

The same authenticated credential LOGIN and bounded cached pool serve explicitly compatible web/browser/provider/first-password requests. Contract selection is known-version configuration and is included in cache identity. Profile4 is not a second per-handler LOGIN or a content-database fallback. Qualification is a read-only observation, not a grant operation or a replacement for retiring old principals and issuers.

The service-only `/api/internal/auth/current-store/first-password/v1/*` handler checks mode, private RPC authentication, method/content type, strict DTO, path and freshness before pool work. It bounds each actual source/candidate to 16 KiB UTF8 and request/reply bodies to 64 KiB. Missing JWE reader configuration refuses before pool acquisition; canonical actors do not require `NEXTAUTH_SECRET`. Account-bound costly work is rate-limited only after actual source admission. No source claims or asserted email binding are trusted from an intermediary.

## Owned qualification and remaining gates

The core has 22 actual-PG flow cases plus the independently reviewed 18 policy/eligibility cases. These cover both stores, JWE/canonical possession, forward mirroring on/off with mandatory canonical rollback copies, original age/SID/expiry, affected versus unrelated partner state, actual new-password comparison after setup, wrong inputs without writes, current owned email drift, supersession scrubbing, account-deletion cascade/no replay, exact ACK expiry/primary removal and observed advisory-locked final-write expiry rollback. Separate scrub controls cover active/unrelated preservation, fixed batch progress, an observed per-write delay consuming the database-clock budget, locked-user skip/retry, a later deleted selection, both actual held-finalizer expiry races, default/rollback profile selection and awaited drain/private errors. The generated 0314 leaves every older SQL/snapshot byte unchanged and appends one journal entry. The canonical user-reference deletion contract explicitly includes and rejects removal/change of the new incoming FK.

The dedicated serial first-password role/HTTP task runs only on the fresh owned current canonical journal. It retains the complete historical and provider proof phases, then executes the new restricted-LOGIN cases and existing web/browser/provider HTTP positives under profile4. It has its own JUnit artifact and does not enter service-free default projects. Synthetic fixture grants are not production provisioning.

The web broker and UI tests went with the web layer in #7596. The mail template keeps its own test (`packages/shared/email/src/__tests__/first-password-email.test.ts`), and the shared redaction keeps its tests. Actual email delivery, the public/private HTTP join, full writer/issuer retirement, live role/pool qualification and production rollout/rollback acceptance remain tracked in #7430 and wait for the rebuilt web layer.
