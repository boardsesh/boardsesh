# Account-bound first password after email confirmation

This path implements the approved continuation for accounts without a password in epic #6975 (Apple-only at first; any account with a Google or Apple identity since the decision of 2026-11-18 on #7596). `CURRENT_STORE_FIRST_PASSWORD_MODE` defaults to `legacy`, which leaves its private route disabled. This doc covers the backend core, shared mail template and rebuilt www flow. The old binding-based www layer was removed before activation; B5e2 rebuilt first-password setup on the shared-domain session. See [Web layer](#web-layer) and [the browser-session contract](better-auth-browser-session.md). No production mail or browser activation is performed by implementation validation.

> **Re-keyed by #7596 B5c2.** Every command acts for the first-party web session www presents (the canonical token; a legacy NextAuth cookie gets `canonical_session_required` and must be bridged first), read by `readFirstPartySession` under the account's `users` lock. No browser binding, browser intent, cursor or candidate credential remains. The same session token must make every step, including the one that completes the emailed confirmation link. Finalize keeps that session's id, token, sign-in time and expiry and moves only its generation (`keepCanonicalAfterSecurityMutation` with the `password-set` receipt); every other first-party credential ends. The NOT NULL binding columns hold `browser_binding_hash` = SHA-256 of `["provider-security-web-session-v1", sessionId]`, `browser_version` 0, `browser_intent_hash` derived from the challenge, and `browser_binding_expires_at` = the session's expiry at request; `proposed_credential_hash` and `candidate_credential_hash` hold the presented token's hash. The backend refuses to start with `CURRENT_STORE_FIRST_PASSWORD_MODE=backend-staging` unless `AUTH_BROWSER_SESSION_MODE=better-auth` (`AUTH_FIRST_PASSWORD_BROWSER_SESSION_REQUIRED`). Where a paragraph below mentions the binding, the replacement intent, a cursor or a candidate, that part no longer applies.

Eligibility comes from the actual current web session and its caller-held credential. The selected identity store must have no password and at least one Google or Apple identity, every identity row this user's at this generation with a subject (`isFirstPasswordInventory`; decision of 2026-11-18 on #7596, widening the Apple-only rule of 2026-11-13). A Facebook row beside Google or Apple does not block; a Facebook-only account stays not eligible (its own open owner decision in #7430). Set-password keeps refusing while provider security is staged, so a sign-in cookie alone still cannot create the factor that later proves freshness. The locked shared user supplies the recipient. Its normalized email reservation must be owned by that same fixed UID in the current projection with exactly one matching membership. An address never selects, merges or remaps an account.

The confirmation is a dedicated `first-password` purpose. Its maximum five-minute lifetime is also capped by the original source credential. The backend captures the private auth RPC secret as an internal, domain-separated HMAC key for purpose/projection/normalizer/UID/normalized-email binding. A command cannot supply the recipient, binding, key, purpose or an alternative UID. Rotating the RPC key may invalidate pending confirmations; this does not rotate the separate deleted-email key.

## Preparation

> **Historical publication design removed.** B5c2 re-keyed preparation/finalization to the first-party session and B5e2 rebuilt www. There is no generation+1 continuation cookie, browser binding or proof-cookie acknowledgement. Eligibility, challenge handling, the finalize transaction and capability profile remain; the requesting session keeps its token.

Request is one transaction since B5c2: challenge issuance admits the session and checks current source, email/reservation ownership, selected password absence, the Google-or-Apple inventory and authority. Under the same `users` lock it applies a durable mail cap: an account with 5 challenges issued in the last hour, or 10 in the last 24 hours (counted from `issued_at`), is refused the way the per-process limit of 3 a minute is (503), with no row written and no mail plan. Superseding an active challenge scrubs its prepared bcrypt hash and preparation state.

The request returns a **private mail plan** to an authenticated backend service caller. The backend does not invoke delivery. Its caller passes only the fixed backend recipient and confirmation token to the shared email transport (`sendFirstPasswordConfirmationEmail` in `packages/shared/email`). The confirmation URL points at `/auth/confirm-first-password` and carries its token and operation selector in a fragment, with no email or UID. Since #7596 www serves no such page and nothing calls the template; the rebuilt web layer will. GET requests perform no mutation; the private read command admits actual possession and returns only pending/prepared metadata and the deadline.

Preparation checks the actual actor and confirmation token before bcrypt work, hashes outside transactions, then locks and rechecks all eligibility and challenge bindings under a new authority receipt. It stores only the pending bcrypt hash and opaque hashes; the selected password remains absent and the challenge unconsumed. It predicts the existing email-verification timestamp, or the stored preparation clock for the confirmed current address, without changing the shared user yet. It mints no token: the presented session continues through finalize, and the prepared row records that token's hash as the credential that continues.

## Web layer

B5e2 rebuilt `/api/auth/first-password/*` (request, status, confirm, recover),
`/settings/first-password` and `/auth/confirm-first-password` on the first-party
session. The page and routes require `AUTH_BROWSER_SESSION_MODE=better-auth` and
`CURRENT_STORE_FIRST_PASSWORD_MODE=backend-staging`; see
[the browser-session contract](better-auth-browser-session.md#settings-and-first-password-on-www-b5e2)
for exact responses and confirmation behavior. www calls
`sendFirstPasswordConfirmationEmail` with the planned recipient and token;
the operation key is a digest of the challenge token.

The former five `/api/internal/auth/first-password/*` routes, binding broker,
versioned proof cookies and `publicFirstPasswordReady()` were removed by #7596.
They are not the rebuilt public flow. The backend `first-password-v1` protocol,
challenge table, mail template and shared capability redaction remain.
Implementation tests do not establish actual email delivery or authorize rollout.

## Finalize

Finalize owns one physical transaction. It re-admits the presented session, authority, current email/reservation, eligible Google/Apple selected inventory, absence of a selected password, confirmation challenge and preparation token. It stamps the confirmed email through the selected authority, inserts the selected password, performs the existing password-set generation/mirror operation, revokes partner credentials, keeps the requesting session in place (same id, token, sign-in time and expiry, new generation) with the same transaction's unforgeable password-set receipt, ends every other web session, lineage, native refresh token and pending reset or verification link of the account, and consumes/scrubs the challenge. No cookie is written. An existing verified timestamp remains unchanged; otherwise the exact stored preparation clock matches the prebuilt profile. This makes the new password usable when the existing sign-in email-verification policy is enabled. The final database-clock check follows all writes. A late refusal rolls back email metadata and every other write in that transaction.

Email confirmation is not provider reauthentication. Successful setup does not refresh the source session's authentication age and creates no provider reauthentication receipt. Linking or unlinking afterward still requires entering and comparing the new password, or another independently qualified proof, within the existing five-minute provider policy.

## Recovery and stored material

Recovery answers only the same live session at the generation the commit gave it, with the original challenge, preparation and recovery tokens. It returns that generation and never reconstructs, returns or persists a raw bearer. Primary unavailability returns unavailable, including after a successful commit. Recovery is capped at two minutes and at the original challenge and session deadline. A commit near confirmation expiry can have a shorter ACK window; expiry never permits another mutation. A retried `finalize` after a lost reply answers `already_set`.

Generated migration `0314_first_password_challenges` adds the single 33-column receipt table. It stores no raw source/candidate, confirmation/recovery/preparation token, email address or plaintext password. The pending bcrypt hash exists only while prepared and is cleared on commit or supersession. The user FK uses ON DELETE CASCADE and ON UPDATE NO ACTION, so explicit account deletion removes pending material and the old challenge cannot replay. Browser selection tombstones retain their existing separate deletion behavior.

The existing awaited per-minute maintenance hook scrubs abandoned expired preparations through the same qualified profile4 pool. It never uses the content handle or adds a timer, principal or DELETE grant. Each transaction observes at most 25 candidates and checks a 750 ms database-clock work budget between locking stages, with one-second statement and 100 ms lock bounds. It takes the authority gate, the challenge's own user and then the challenge lock, in that order; since B5c2 it reads no binding or intent row. Busy rows are skipped for the next tick; phase and actual database expiry are rechecked before clearing only the pending preparation fields into terminal state. Current active confirmations, committed ACK receipts, unrelated accounts and browser selection tombstones are preserved. Existing worker shutdown drains this awaited bounded task before closing the credential pool.

Scrubbing continues with profile4 configured after first-password mode returns to `legacy`. Keep the reviewed profile4 inclusion and pool available during that rollback. Drain/scrub expired pending hashes before downgrading to a profile that removes challenge-table access. No production maintenance scheduling or configuration is performed by this code change. The credential profile deliberately has no account/challenge DELETE or general maintenance capability.

## Database capability and private transport

`private-first-password-v1` is an explicit reviewed superset of `private-provider-v1`. It adds only SELECT/INSERT/UPDATE on `auth_first_password_challenges`. It retains the pinned existing revoke-only partner function and narrow predicate/revocation grants, with no raw token reads, partner issuance, users DELETE, challenge DELETE, TRUNCATE or MAINTAIN. The exact new column/default/index/CHECK/FK catalog shape is statically pinned. Old profiles refuse the additional grants. Every profile also refuses actual PUBLIC table or column grants within its protected capability/side-effect closure, even when those grants do not enlarge the writer's effective rights.

The same authenticated credential LOGIN and bounded cached pool serve explicitly compatible web/browser/provider/first-password requests. Contract selection is known-version configuration and is included in cache identity. Profile4 is not a second per-handler LOGIN or a content-database fallback. Qualification is a read-only observation, not a grant operation or a replacement for retiring old principals and issuers.

The service-only `/api/internal/auth/current-store/first-password/v1/*` handler checks mode, private RPC authentication, method/content type, strict DTO, path and freshness before pool work. It bounds each actual source/candidate to 16 KiB UTF8 and request/reply bodies to 64 KiB. Missing JWE reader configuration refuses before pool acquisition; canonical actors do not require `NEXTAUTH_SECRET`. Account-bound costly work is rate-limited only after actual source admission. No source claims or asserted email binding are trusted from an intermediary.

## Owned qualification and remaining gates

The core has 22 actual-PG flow cases plus the independently reviewed 18 policy/eligibility cases. These cover both stores, canonical possession (a legacy cookie is refused with `canonical_session_required`), the requesting session kept with the same token, forward mirroring on/off with mandatory canonical rollback copies, original age/SID/expiry, affected versus unrelated partner state, actual new-password comparison after setup, wrong inputs without writes, current owned email drift, supersession scrubbing, account-deletion cascade/no replay, exact ACK expiry/primary removal and observed advisory-locked final-write expiry rollback. Separate scrub controls cover active/unrelated preservation, fixed batch progress, an observed per-write delay consuming the database-clock budget, locked-user skip/retry, a later deleted selection, both actual held-finalizer expiry races, default/rollback profile selection and awaited drain/private errors. The generated 0314 leaves every older SQL/snapshot byte unchanged and appends one journal entry. The canonical user-reference deletion contract explicitly includes and rejects removal/change of the new incoming FK.

The dedicated serial first-password role/HTTP task runs only on the fresh owned current canonical journal. It retains the complete historical and provider proof phases, then executes the new restricted-LOGIN cases and existing web/browser/provider HTTP positives under profile4. It has its own JUnit artifact and does not enter service-free default projects. Synthetic fixture grants are not production provisioning.

The old binding broker and its UI tests were removed in #7596; current www route/UI coverage belongs to the rebuilt B5e2 flow. The mail template keeps its own test (`packages/shared/email/src/__tests__/first-password-email.test.ts`), and the shared redaction keeps its tests. Actual email delivery, the public/private HTTP join, full writer/issuer retirement, live role/pool qualification and production rollout/rollback acceptance remain tracked in #7430; the rebuilt web layer alone does not close them.
