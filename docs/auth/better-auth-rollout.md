# Better Auth rollout: every switch, and the order to turn them on

Parent: [epic #6975](https://github.com/boardsesh/boardsesh/issues/6975), rollout issue BA-09 [#6983](https://github.com/boardsesh/boardsesh/issues/6983). Owner steps with paste-ready commands live in runbook issue [#7430](https://github.com/boardsesh/boardsesh/issues/7430).

This file answers one question: what can change how sign-in works in production, and in what order. It was written from the code (`grep` for `CURRENT_STORE_`, `AUTH_`, `PARTNER_OAUTH`, `BROWSER_DELEGATION` and `developer-console`), not from the older docs.

## The state today

- **Nothing in the repo sets any switch below.** Check Railway for the live values; do not assume them from this file.
- **The owner flips every switch.** Agents prepare commands and read production. They do not change production variables, flags or the database.
- **Only `PARTNER_OAUTH_MODE` is checked by value in `infra/railway/config.ts`** (web service: it must be `off`, `hold`, `allowlist` or `open`). `WEB_DATABASE_URL` is declared there as an optional secret: absence is fine, only an unfilled placeholder is reported. No plan catches a typo in any other row. The code does: an unknown value throws at startup or on the first request, except where the row says "reads as off".
- **Unset, empty or `legacy` means off** for every `CURRENT_STORE_*` mode and for `AUTH_WATCH_PAIRING_MODE` and `AUTH_BROWSER_SESSION_MODE`.
- **Changing a mode never closes a code gate.** Section "Code gates" lists the ones that refuse regardless of environment.

Where a row says **Both**, set it on the web service and the backend service. **Backend** means the `boardsesh-backend` service (the workers run the same image).

Connected apps (Settings, Disconnect) works in every mode, `off` and `hold` included.

`PARTNER_OAUTH_SECRETS` rotation also affects webhooks. Current and still-valid
previous signing secrets are re-sealed under the first key on delivery and by
a sweep of up to 100 settings per maintenance run, scheduled every minute,
while old versions remain configured. Elapsed time alone does not prove completion.
Keep the old sealing versions until every current and still-valid previous
secret has been re-sealed, including idle/disabled endpoints; verify the sweep
and investigate resealing warnings before retiring a version. Retain any old
versions still required for token/cursor compatibility too. An unreadable
previous signing secret is skipped if the current secret can sign; an
unreadable current secret retries and settles `signing_unavailable` after ten
attempts, without counting against endpoint health. It is therefore unsafe to
describe key retirement as costing only cursors. Webhook signing-secret
rotation's 24-hour overlap is a separate promise from sealing-key rotation.
O1's historical concurrent-index prebuild remains unconfirmed; its production
receipt and required evidence are recorded in
[integration-platform.md](../integrations/integration-platform.md#milestones-24-implementation-decisions-2026-11-17).

## 3. Staged writer modes (`CURRENT_STORE_*` and `AUTH_WATCH_PAIRING_MODE`)

Each moves one kind of credential write from the old path into the backend's current-store service. All are off by default. A staged writer needs the section 2 values and an `enforced` authority, so **none can work until `activate` runs** (it cannot today). The backend also refuses to start with any of them on while `AUTH_CUTOFF_ENFORCEMENT=observe`, and with `AUTH_IDENTITY_MIRROR=on` unless the native modes are `reserved-staging`.

| Switch | Where | Values (default) | Turning it on | Also needs | Back out |
| --- | --- | --- | --- | --- | --- |
| `CURRENT_STORE_WEB_AUTH_MODE` | Both | `legacy`, `backend-staging` (`legacy`) | Web registration, password sign-in, email verification, forgot and reset password go to the backend. | RPC secret, backend origin on web, projection id and epoch, deleted-email key. Blocked on #7589 (one client can use up the login budget). | Web `legacy` first, then backend. |
| `CURRENT_STORE_WEB_OAUTH_MODE` | Both | `legacy`, `backend-staging` (`legacy`) | Google and Apple web sign-in identity writes go to the backend, with durable flow binding. | Same as above, plus `NEXTAUTH_SECRET` on the backend | Web `legacy` first, then backend. |
| `CURRENT_STORE_WEB_CREDENTIAL_PROOF_MODE` | Both | `off`, `compatible`, `required` (`off`) | The backend issues a signed proof of each web sign-in. `compatible` is **backend only**: the web throws if it runs in it. `required` makes the web reject any sign-in without a proof. | An enforced authority (see section 2) | Both `off`. Order: backend `compatible`, then both `required`; back out in reverse. |
| `CURRENT_STORE_SET_PASSWORD_MODE` | Both | `legacy`, `backend-staging` (`legacy`) | Fresh-sign-in set-password goes to the backend, keeping this device signed in and revoking the others. | Proof mode `required`; mandatory once `AUTH_IDENTITY_MIRROR=on` | Set `legacy`. |
| `CURRENT_STORE_WEB_SIGNOUT_MODE` | Backend (web forwards when staged) | `legacy`, `backend-staging` (`legacy`) | Web sign-out writes a per-session denial. | Cutoff enforcement `enforce`, RPC secret. **The backend refuses to start with `backend-staging`** while historical issuer retirement and old no-SID safety are unproven. The refusal is unconditional: this writer's no-SID path (`signOutLegacyWebSession`) still cuts off the whole account, which is not approved. `better-auth` does not need this mode. | Set `legacy`. |
| `CURRENT_STORE_WEB_SESSION_MODE` | Backend | `legacy`, `backend-staging` (`legacy`; another value answers 503) | The backend issues first-party web sessions (#7596): the staged password command accepts `webSession` and returns a session for the account it verified, revoking the presented one, and `/api/internal/auth/current-store/web-session/v1/session`, `/signout`, `/bridge` and `/access` answer (`/access` is where a session rolls), staged set-password accepts a canonical session, which keeps its token, and the backend accepts the 15-minute browser access token `/access` signs (audience `boardsesh-browser`) on GraphQL and WebSockets; off, such a token is not accepted. That covers the presented cookie and its own rotations, not an independent older copy of the same login, which has another id; NextAuth's sign-out today is no different. That is why this mode is not behind the activation block on `CURRENT_STORE_WEB_SIGNOUT_MODE`, whose no-SID path cuts off the whole account. www calls the password command with `webSession`, `/session` and `/signout` only under `AUTH_BROWSER_SESSION_MODE=better-auth` (B1c); `/bridge` on a `GET /api/auth/session` that carries only a legacy cookie (B2b, limited to 20 a minute per client address); and `/session`, `/bridge` (without writing a cookie, in its own budget of 20 a minute per client address) and `/access` from `/api/internal/ws-auth` (B3b). | `CURRENT_STORE_WEB_AUTH_MODE=backend-staging` for login; RPC secret, projection id and epoch, deleted-email key, cutoff enforcement `enforce`; `NEXTAUTH_SECRET`, `AUTH_BRIDGE_TOKEN_SECRET` and `AUTH_LEGACY_BRIDGE_UNTIL` for `/bridge`, and `AUTH_BROWSER_ACCESS_TOKEN_SECRET` for `/access` and the tokens it signs, and `AUTH_BROWSER_SESSION_COOKIE_SECRET` on the backend for partner consent, which then also reads the first-party session cookies (503 without them). ## 4. Authority switches (BA-04)

| Switch | Where | Values (default) | Turning it on | Needs first | Back out |
| --- | --- | --- | --- | --- | --- |
| `AUTH_IDENTITY_MIRROR` | Backend | `off`, `on` (`off`) | Every credential write also writes the canonical Better Auth tables in the same transaction, so the import has nothing to chase. | Startup checks, each refusing with one code (table in [better-auth-identity-mirror.md](./better-auth-identity-mirror.md#preconditions)): delegated set-password, staged native writers, the configured projection and epoch, the qualified `AUTH_IDENTITY_DATABASE_URL` LOGIN, the mirror's tables, an `enforced` current-store manifest, a verified fence, and both code gates below (`IDENTITY_COPY_CODE_GATES_OPEN`, `ACTIVATION_CODE_GATES_OPEN`). **So the backend refuses to start with `on` today.** After an authority switch it boots inert instead (copies nothing, mirrored credential writes refuse, a Sentry error per boot) until redeployed with `off` or the new epoch. | `off`. ### Session tokens at rest

`auth_session.token` stores the SHA-256 digest (base64url) of a session token,
never the token (`auth/authority/session-token.ts`). The reader hashes the
presented token and looks the digest up, so a copy of the table (a dump, the DR
standby, a backup) authenticates nothing. Every writer stores the digest: the
legacy bridge, the native refresh binding, the security-mutation token
rotation, the provider continuation and both staged provider sign-ins.

A bridged session's token is not random: it is
base64url(HMAC-SHA256(key, "boardsesh-bridge-token-v1:" + session id)), with
the key derived from `AUTH_BRIDGE_TOKEN_SECRET`. Every bridge of the same
legacy login answers the same token and leaves one row. A row whose stored
digest is not the derived one (rotated by a password change, written before
this rule, or derived under an older secret) is never re-keyed: the bridge
answers `denied`.

A row written before this change holds a clear token, and the reader no longer
accepts it: that session is signed out. Nothing in the repo sets
`AUTH_LEGACY_BRIDGE_MODE=on` or any staged provider mode, so no such row should
exist in production, but code cannot prove it. **Before turning on
`AUTH_LEGACY_BRIDGE_MODE`, `CURRENT_STORE_PROVIDER_SECURITY_MODE`,
or `CURRENT_STORE_FIRST_PASSWORD_MODE`,
the owner confirms the table is empty**
(read-only):

```sql
SELECT count(*) AS rows, count(*) FILTER (WHERE expires_at > now()) AS live FROM auth_session;
```

Both must be 0. If not 0, stop and ask before turning a mode on: a bridged row
written before this change can never hand its legacy login a working token
again, and deleting the row alone makes the bridge deny that login.

## Shared password-guess counter: web wiring (#7656)

The backend PR #7783 and its web follow-up share one counter. The web never
writes `auth_password_guess_windows` or holds its digest key. Set
`AUTH_ACCOUNT_GUESS_LIMIT_MODE=observe` on **both web and backend** only after
the documented connection budget and recognition seeding preconditions hold.
Unset, empty or `off` leaves the web counter unused. `enforce` remains blocked
by the backend's four named gates; merging either PR does not authorize a mode
change. The ordinary per-client sign-in limits still apply.

Legacy NextAuth resolves the email with its existing lookup, verifies a device
cookie for that account, then asks the backend to reserve before bcrypt. A
right password or an unfinished comparison gives the reservation back once.
Rejected passwords stay charged. Every private reserve, give-back and clear
has a 400 ms total deadline; unavailable calls keep today's sign-in behavior
and produce a bounded, credential-free diagnostic. The staged password path
forwards the cookie to the backend and preserves its full daily-window 429.

`AUTH_DEVICE_TOKEN_SECRET` seeds a host-only, HttpOnly browser cookie after an
admitted password, Google, Apple or native-transfer login. Session reads and
sign-out do not rewrite it. Completed resets clear the email counter and seed
recognition for the exact reset owner without creating a login. The backend
only adds this token to a reset reply when the authenticated private caller
sends `x-boardsesh-reset-device-token: 1`. Older web callers receive their
original strict reply even during a backend-first rollout or rollback. New web
callers tolerate an older backend that ignores this header and returns no token.

Recognition does not remove the native reset-owner gate: the reset browser is
recognized, but a different phone may still hold a voided device token. Keep
enforcement off until that accepted policy and the load evidence are resolved.

4. **Writer modes (section 3).** #7430 says the exact order will be recorded there before any switch, so none is fixed here. The dependencies are: proof `compatible` before `required`; `required` before set-password; fixed-owner order before location sync; native modes `reserved-staging` before the mirror. Turn on one mode at a time and watch it before the next.
5. **Mirror:** `AUTH_IDENTITY_MIRROR=on`. Refused at startup until the `LEGACY_WEB_IDENTITY_WRITERS` and activation code gates close and every database precondition holds; the boot log then says `[IdentityMirror] Qualified at writer epoch <n>`. After any authority switch, redeploy at once with `off` (switch to Better Auth) or the new `CURRENT_STORE_AUTH_WRITER_EPOCH` (switch back); until then the backend runs inert.
6. **Import:** with `AUTH_IDENTITY_DATABASE_URL` (the writer LOGIN on `pgdr.boardsesh.com`) and `AUTH_IDENTITY_MIRROR=on` in the operator shell, `vp run auth:import-identities -- plan --confirm-host pgdr.boardsesh.com --key-file ~/Private/boardsesh-ba04/digest-key --checkpoint ~/Private/boardsesh-ba04/checkpoints` (read-only, the default), then the same with `import --batch 200 --pause-ms 100`. Refusal codes are in [better-auth-identity-import.md](better-auth-identity-import.md#preconditions). Reconcile read-only afterwards and 24 hours later.
7. **Switch:** `AUTH_LEGACY_BRIDGE_MODE=shadow`, then `on` once web sign-out is staged and generation revocation is allowed. Before generation revocation, `AUTH_WATCH_PAIRING_MODE=source-bound-staging`.
